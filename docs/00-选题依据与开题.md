## 1. 选题背景与意义

- [x] **中小规模教学/实验环境的私有云管理需求**
  - 高校课程实验、毕业设计与小型研发团队的测试环境，虚拟机规模通常在 **3～30 台**量级：数量不足以证明重型云平台的部署成本，又多到无法靠每人 SSH 上去敲 `virsh` 维持秩序。
  - 这类环境的真实诉求是：多人共享一台（或少数几台）KVM 宿主机时，有统一的 Web 入口、有角色与权限边界、有操作留痕，而不是把宿主机 root 口令在同学之间传阅。

- [x] **现有方案（OpenStack、Proxmox）资源占用高、部署复杂，难以在受限硬件落地**
  - **OpenStack**：官方安装指南给出的最低配置即 controller 节点 4GB 内存 + compute 节点 2GB；社区实践对 all-in-one 环境普遍建议 **16GB 内存起步**。其组件数十个（nova/neutron/cinder/glance/keystone…），部署需 DevStack/Kolla-Ansible 等工具链，对 3～30 台虚拟机的管理诉求而言运维成本严重倒挂。（来源：<https://docs.openstack.org/install-guide/environment.html>）
  - **Proxmox VE**：是**完整发行版**，要求作为整机系统直接安装到物理机（官方最低 2GB 内存仅覆盖 OS 与基础服务，尚未计入客户机开销），自带的管理面无法拆出来复用到一台已有的 Linux 宿主机上。（来源：<https://www.proxmox.com/en/products/proxmox-virtual-environment/requirements>）
  - **virt-manager / Cockpit**：定位是**单机手工工具**——无 REST API、无审计留痕、无多用户角色，重在做完即走的图形化操作，不适合作为多人共享的常驻平台。

- [x] **家庭/实验室自建 KVM 集群的实际管理痛点**
  - 建机流程重复手工：建盘 → 写 XML → define → 装 cloud-init → 配网络，每一步都依赖操作者记忆与纪律；
  - 无操作留痕：谁删了哪台机器、谁回滚了快照，事后无从追溯；
  - 无失败语义：`virsh clone` 之类的命令「执行成功」不代表结果符合语义（本文在增量克隆上实测踩中这一点，见 §3.3 方法论）；
  - 无监控融合：虚拟机指标散落在宿主机上，没有与告警、看板的联动。

- [x] **选题意义：轻量化、低成本、可落地**
  - **轻量**：单个 Go 二进制（约 **27MB**）内含 REST API、前端静态托管与 Prometheus exporter，实测常驻内存约 **36MB**、冷启动约 **200ms**，可与业务虚拟机共存于同一台宿主机而不挤占虚拟化资源；
  - **真实 KVM 落地**：管理面经 go-libvirt 直连本机 libvirt（unix socket），生命周期操作落在真实 KVM 域上，非模拟实现；
  - **审计可追溯**：全部管理操作经审计中间件留痕（谁/何时/对什么/结果），配合 RBAC 角色边界，满足多人共享环境的合规底线；
  - **可推广**：同一形态适用于教学实验室、家庭实验室与小团队内部云，是「重型云平台」与「单机手工工具」之间的空档地带。

## 2. 国内外研究现状

> 素材来源：各项目官方文档与 [10-参考项目研究.md](10-参考项目研究.md)。

- [x] **重型开源云平台：OpenStack / oVirt**
  - **OpenStack**：事实上的开源 IaaS 标准，组件生态完整，但规模与复杂度面向公有云/大型私有云——部署涉及数十个服务与消息队列、数据库等基础设施，版本升级与排障门槛高。在中小环境属于「为了管 20 台虚拟机先养一个运维团队」。
  - **oVirt**：采用 engine + hosts 架构，engine 管理节点本身需要独立虚拟机与数据库承载，架构偏重；且上游社区在 Red Hat 转向 OpenShift Virtualization 后活跃度明显下降，选型风险高。

- [x] **一体化发行版：Proxmox VE**
  - 基于 Debian 的完整虚拟化发行版，自带 Web 管理面，功能覆盖广、社区成熟，是家用/中小环境的主流选择。
  - 形态限制：必须作为**整机系统**部署（不能装进已有 Linux 的管理面）；HA 需要多节点集群与仲裁支撑，单节点场景无从谈起；权限体系以预置角色为主，缺少本平台这类按「是否构成对客户机的写入通道」语义判定的只读角色（见 §3.3 创新点 2）。

- [x] **轻量级开源 KVM 管理面板（WebVirtCloud 等，详见 [10-参考项目研究.md](10-参考项目研究.md)）**
  - virt-manager / Cockpit：单机手工工具，前已述及。
  - WebVirtCloud、vmdashboard、KvmDash 等社区面板：普遍停留在基础 CRUD（建机/开关机/控制台），功能单薄——无操作审计、无异步任务系统（耗时操作同步阻塞 HTTP 请求）、无会话跟踪、无删除保护等生命周期安全设计，直接用于多人共享环境会同时碰到「不可追溯」与「误操作不可恢复」两类问题。

- [x] **本文定位：差异化（轻量单二进制 + 审计/RBAC + 异步任务 + 监控融合）**
  - 面向 **3～30 台虚拟机规模**的实验室/小团队，在 OpenStack（过重）与 virt-manager 类工具（过轻）之间取位：
    - **部署形态轻**：单二进制 + 内建 exporter + 静态前端托管，无外部管理面依赖；
    - **管理语义全**：异步任务（202 + 轮询）、操作审计、RBAC 只读角色、控制台会话跟踪与收敛；
    - **生命周期安全**：真实 linked clone、删卷三重守卫与引用拦截（见 §3.3 创新点 3）；
    - **可观测**：与 Prometheus/Alertmanager/Grafana 监控栈融合，历史性能曲线以 Prometheus 为历史库。

## 3. 主要研究内容

- [x] **KVM 虚拟化层纳管（libvirt / go-libvirt 直连）**
  - 经 `digitalocean/go-libvirt` 以 unix socket 直连 libvirt 守护进程（无 CGO、无 C 头文件依赖），虚拟化连接由全局 `LIBVIRT_URI`（默认 `qemu:///system`）决定；
  - 封装层 `service/virt/` 统一连接探活与断线重建、错误包装（`%w` 保留错误链）、libvirt 状态到平台状态（`running/shut off/paused/error`）的映射，使上层业务不直接接触 libvirt 细节。

- [x] **平台核心功能：宿主机登记与状态采集、VM 生命周期、镜像、审计**
  - 宿主机登记、SSH 连通性探测（ping）与实时状态/资源采集；
  - VM 全生命周期（创建/启停/重启/删除/克隆，真实 KVM 域）、镜像模板与基于云镜像建机、存储池/卷/网络/快照管理、cloud-init 免密初始化、硬件热管理（磁盘/网卡/CPU/内存）；
  - 耗时操作（创建/删除/克隆/优雅关机）异步化：任务队列 + worker 池，接口返回 202 + 前端轮询；
  - 操作审计中间件（谁/何时/对什么/结果）+ 查询与分布统计 + 三类控制台链路的会话跟踪。

- [x] **前后端架构（Go + Vue3）**
  - 后端 Go + Gin + GORM + MySQL8，统一响应 `{code, message, data}`；
  - 前端 Vue 3（Composition API）+ Vite + Element Plus，构建产物由 Go 二进制直接静态托管；
  - JWT 认证 + admin/viewer 角色，WebSocket 链路（noVNC token、SSH 终端桥、串口桥）复用同一套鉴权。

- [x] **创新点：操作审计可追溯 / 轻量单二进制部署 / 存储生命周期安全设计**
  - 详细论证与代码实证见 §3.3「创新点与方法论」。

## 3.1 系统边界与范围判据（防跑题锚点）

> 论文题目关键词是**「私有云管理平台」**，而非「虚拟机管理工具」。所有功能取舍以是否支撑以下三个贡献点为判据：

| 贡献点 | 含义 | 支撑功能 |
|---|---|---|
| ① 轻量单二进制 | 单二进制、低资源、内建监控融合、单机管理节点 | 内建 Prometheus exporter（`/metrics`）与监控栈融合、前端静态托管与降级启动、虚拟化连接经全局 `LIBVIRT_URI` 指向本机（默认 `qemu:///system`）或指定 libvirt 端点 |
| ② 真实 KVM 落地 | 非模拟，生命周期自动化 | VM 建/启停/删、镜像模板、存储池、网络 |
| ③ 操作审计可追溯 | 谁/何时/对什么/结果 | 审计中间件 + 查询 + 分布统计、角色权限 |

**与单机管理工具（virt-manager/Cockpit）的差异**：它们重在「单机全功能手工操作」；本平台重在「API 标准化 + 异步任务 + 审计留痕 + 监控融合」。XML 直接编辑属工具思维，本平台以「结构化表单 + 模板」为主，原始 XML 编辑作为高级能力补充——这本身就是可写的设计点，不是减分项。

> **范围声明（单管理节点）**：本文平台为**单管理节点**形态——虚拟化连接由全局 `LIBVIRT_URI` 配置决定，
> 默认指向本机 `qemu:///system`。**跨宿主机虚拟化操作**（`qemu+ssh://` 远程连接与按 host 维度的连接池）
> 明确列为后续工作（docs/08 §2.3），不在本文实现范围内；本文聚焦单管理节点上的**完整功能闭环与工程加固**
> （稳定性 / 安全 / 正确性三轮加固与测试建设）。写作时应避免表述为「已实现多宿主机虚拟机管理」。

## 3.3 创新点与方法论

> 素材来源：docs/08 §1（三轮加固与工作总结）、docs/06（系统测试与验证，反证实验）、docs/05 §6.7（增量克隆实现）。

### 3.3.1 创新点

与同类工作对比，本平台的创新不在「调用了新 API」，而在**部署形态、权限语义与生命周期安全**三个维度的工程设计，每条均有代码与实验实证：

1. **轻量单二进制部署形态**
   - 单个 Go 二进制同时承担 REST API、前端静态产物托管与 Prometheus exporter（`/metrics`，VM/宿主机/存储池/任务 4 类指标），无需独立的管理面节点或独立监控采集器；
   - 静态产物按 `<exeDir>/web/dist` → `<exeDir>/static` → `<cwd>/web/dist` → `<cwd>/static` 四候选探测定位，全未命中时**降级为 API-only 模式**启动（`go run` 开发态不再因找不到产物而退出）；
   - 资源实测：二进制约 27MB、常驻内存约 36MB、冷启动约 200ms；Docker 镜像产物 51.5MB（Go 1.25-alpine 多阶段构建，时区内嵌）；
   - 与 §2 对比：OpenStack 需数十组件与独立管理节点，Proxmox VE 是整机发行版——本平台的单二进制 + 监控栈融合形态填补了两端之间的空档。

2. **语义级 RBAC 与操作审计**
   - 写权限判定**不按 HTTP 方法、而按语义**：`GET /api/vms/:id/terminal` 与 `GET /api/vms/:id/serial` 虽是 GET，建立的是对客户机的双向写入通道（串口在多数云镜像上直接就是 root TTY），对 viewer 角色一律 403；图形控制台（noVNC）保留但由 `vnc-token` 接口下发 `view_only` 标志，前端禁用键鼠——「只读角色」由此才名副其实，而非仅靠方法名约定；
   - 全部管理操作经审计中间件留痕（操作者/时间/对象/结果），配合会话注册表对三类控制台链路（VNC/SSH/串口）的可观测与强制断开，形成「谁在用、用了什么、能不能断」的完整闭环（实证：docs/08 §1 RBAC 只读角色条目、docs/06 安全验证 45 条用例）。

3. **存储生命周期安全设计**
   - **真实 linked clone**：子卷经 `StorageVolCreateXML` + 卷 XML 声明 `<backingStore>` 实现（等价 `qemu-img create -b`），而非名不副实的 `StorageVolCreateXMLFrom`（`virsh vol-clone`，实测为全量数据拷贝、子卷无 backing file）；克隆机 UUID 与全部网卡 MAC 重新生成，杜绝同网段 ARP 冲突；
   - **删除三重守卫**：删卷前依次检查——池外文件、`images` 表登记的共享基镜像（基于云镜像建机是直接引用不拷贝）、仍被子卷当 backing file 的父盘（数据来自 `virt.ListBackingRefs` 父卷→子卷依赖表）；命中任一即跳过删除；
   - **引用计算 409 拦截**：删卷接口先行计算引用（域磁盘 source 枚举 + 镜像表精确匹配 + backing 依赖），任一命中返回 409 与中文原因，前端展示「在用」徽标与确认详情；
   - **保留原因回传**：删除任务的执行结果带 `kept_volumes` 数组（哪些卷没删、为什么没删），用户可见而非只进日志——「宁可留一个垃圾文件，不可损坏在用磁盘」的设计取向落实到交互层。

### 3.3.2 方法论：「调用了哪个 API」不构成功能语义的证明

第三轮正确性加固中发现的三个「不报错的错误」，共同指向一条方法论命题：**一个功能的语义必须由其外部可观测结果反证，而不能由「调用了哪个 API / 是否无报错」证明。**

- **案例一（增量克隆名不副实）**：README 与多篇设计文档长期把「增量克隆」列为核心特性，代码确实调用了一个名字看起来完全正确的 libvirt API——`StorageVolCreateXMLFrom`（等价 `virsh vol-clone`），注释还写着「libvirt 自动写 qcow2 backing file」。但实测该 API 做的是**全量数据拷贝**：子卷 `qemu-img info` 无 `backing file` 行、`vol-dumpxml` 无 `<backingStore>` 节点。且因为整盘拷贝出来的虚拟机同样能正常开机，该缺陷在相当长时间内**从未暴露**。修复（改用卷 XML 声明 `<backingStore>`）之后，把三条外部命令固定为该功能的验收方式：子卷 `qemu-img info` 有 `backing file:`、`virsh vol-dumpxml` 有 `<backingStore>`、`qemu-img check` 报 `No errors were found on the image`——功能语义由独立于实现的外部证据背书。
- **案例二（克隆机 MAC 沿用源机）**：spec 浅拷贝只复制切片头，网卡的 MAC 原样沿用源机；libvirt 会拒绝重复 UUID 却不校验 MAC，错误直到两台虚拟机同时开机、同网段 ARP 冲突时才显现。修复方式是把配置派生抽成**不依赖 libvirt 连接的纯函数**（`buildCloneSpec`：深拷贝 Disks 与 Interfaces、重生成 UUID、逐块网卡换 MAC），从而可单元测试断言「两块网卡 MAC 全部重生成且不污染源 spec」——错误发生在纯函数层即可拦截，而不是等系统级联调时才暴露。
- **案例三（误删共享卷不可恢复）**：真正实现 backing chain 之后，删除父盘意味着所有子机磁盘不可恢复且无法重建引用——这类错误的代价是**不可逆**的，因此不能等到错误发生再补救，必须在设计上把破坏性操作约束为「**保留优先**」而非「删干净优先」，并把保留原因（`kept_volumes`）回传给用户，让「没删干净」成为可见、可审计的正常结果而非静默失败。

由此形成两条可复现于后续工作的设计取向：其一，**配置派生逻辑一律抽纯函数、以单测断言语义**（MAC/UUID 重生成、XML 生成等），使「正确性」可机器验证；其二，**破坏性操作以「保留优先」为默认取向并回传原因**，使「安全」不依赖操作者的小心。这两条与「外部可观测结果反证功能语义」一起，构成本文工程方法论的三块基石（详见 docs/08 §1、docs/06 第 5、6、9 章）。
