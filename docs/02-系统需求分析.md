## 1. 系统目标与定位

- [ ] 轻量级私有云管理平台（面向个人开发者、高校实验室与小型团队的 Linux 主机）
- [ ] 核心：基于 KVM 的虚拟机统一管理（单管理节点：宿主机登记与状态采集 + 本机 `qemu:///system` 虚拟化操作）
- [ ] 针对四类管理问题提供系统化解法：创建流程繁琐 → 云镜像一键创建与自动初始化；命令行/桌面工具局限 → 浏览器统一入口与跨设备网页控制台；状态不直观 → 仪表盘看板与监控告警；共用无授权无审计 → 三级角色 + 资产授权 + 操作留痕
- [ ] 满足「可管、可控、可追溯」

## 2. 角色与权限

- [x] admin（管理员）：全部操作权限，含 SSH 终端与串口控制台
- [x] operator（操作员）：**虚拟机全生命周期操作**（启停 / 删除 / 克隆 / 快照 / 硬件调整 / XML 编辑）与**三类控制台**（VNC / SSH / 串口——SSH 与串口是其职责内的操作通道）；不可触碰用户管理、审计、系统设置，也不可变更宿主机 / 存储 / 网络 / 镜像等基础设施（基础设施只读）
- [x] viewer（只读运维）：**完全只读**——可访问全部读接口，可打开图形控制台但仅供观看（view_only）
- [x] 权限控制方式（JWT 角色 + `AdminMiddleware` / `OperatorMiddleware` / `NonViewerMiddleware` 三道闸）
- [x] 监控可见级别：监控中心四端点（实时告警 / 告警历史 / file-sd 抓取目标预览 / Grafana 探活）对 viewer 一律 403——实时告警的 labels 与 file-sd 目标都会枚举全部运行中虚拟机的名称与 IP，属**资产名单**，只读角色不得见

场景对应（个人自用 + 小组共用两种形态）：**主机主人/实验室管理员 = admin**（管平台与基础设施）、**小组成员/学生 = operator**（操作被授权的虚拟机）、**检查者/教师 = viewer**（只读旁观运行状态与操作记录）。

「只读」在本系统中的判定标准不以 HTTP 方法为唯一依据。浏览器发起 WebSocket 连接时只能使用
GET 方法，因此 SSH 终端（`GET /api/vms/:id/terminal`）与串口控制台（`GET /api/vms/:id/serial`）
在协议层表现为读请求，实质上却建立了对客户机的**双向写入**通道：前者是完整的 SSH shell，
后者直连虚拟机串口，在多数云镜像上即 root TTY。若仅按方法放行，只读角色便可经由控制台
取得客户机内的任意写权限，与角色语义矛盾。故权限需求明确为：

| 通道 | 协议层方法 | 实质语义 | admin | operator | viewer |
|---|---|---|---|---|---|
| 读接口（列表 / 详情 / 统计） | GET | 读 | ✓ | ✓ | ✓ |
| 虚拟机变更（增删改、启停、克隆、快照） | POST/PUT/DELETE | 写 | ✓ | ✓ | ✗ 403 |
| 基础设施变更（宿主机 / 存储 / 网络 / 镜像） | POST/PUT/DELETE | 写 | ✓ | ✗ 403 | ✗ 403 |
| 图形控制台（VNC） | POST 取 token | 观看（键鼠可禁用） | ✓ 可操作 | ✓ 可操作 | ✓ **只读观看** |
| SSH 终端 | GET（WebSocket） | **写**（shell） | ✓ | ✓ | ✗ 403 |
| 串口控制台 | GET（WebSocket） | **写**（串口 TTY） | ✓ | ✓ | ✗ 403 |
| 监控中心（告警 / 历史 / file-sd / Grafana 状态） | GET | 资产名单 | ✓ | ✓ | ✗ 403 |
| 用户 / 审计 / 设置 | 全部 | 敏感 | ✓ | ✗ 403 | ✗ 403 |

图形控制台的只读性需在客户端实现：VNC（RFB）协议本身不提供只读模式，服务端无法单向裁剪
输入通道，因此由后端在签发 token 时下发 `view_only` 标记，前端据此以 noVNC 的 `view_only`
模式加载，禁用键盘与鼠标事件。

### 2.1 VM 资产授权（借鉴堡垒机 JumpServer 4A 模型）

「能登录平台」与「能看到哪台虚拟机」是两个层级的问题。三级角色只回答前者，本节需求回答后者：
**授权（分配）是一等实体**，核心语义是「**授权决定可见性**」。

- [x] `vm_grants` 授权表：user_id × vm_id 唯一；`expires_at` 可空 = 长期有效，过期授权在查询判定时即时视为不存在（无需清扫协程），行保留可查授权历史
- [x] 可见性收敛：非 admin 对任何虚拟机的访问（列表 / 详情 / 规格 / 克隆源 / 快照 / 三类控制台 / 历史曲线）都要求持有未过期授权；**未授权一律 404 查无此项**（不泄露存在性，而非 403）
- [x] admin 不受授权约束；授权管理 API（`/api/vms/:id/grants` 三端点：列表 / 分配 / 收回）仅 admin 可用
- [x] 授权联动：建机 / 克隆任务自动授权发起人；删除虚拟机时回收其全部授权
- [x] 前端在虚拟机详情页提供「授权管理」面板
- [x] 与 JumpServer 的差异（刻意取舍）：不做 用户组 × 资产树 × 账号 × 动作 的四维矩阵，单宿主机场景一张平面表足够——多级模型的重是它的场景，不是它的好

### 3.13 v3 扩展需求：运维面板能力差距（2026-09 迭代）

前述 3.1–3.12 解决的是「虚拟机本身」的管理问题。v2 完成态做差距复盘时发现：真实宿主机上的
工作负载早已不止 KVM 域——Docker 容器与各类自托管中间件同样需要管理入口，而这类需求正是
运维面板类产品（1Panel、Portainer）的主场。据此以三个成熟产品为对标做差距分析，推导出 v3
扩展需求集：

- **1Panel**（GPLv3，本项目参考其设计模式而非引入代码）：以「容器多 tab 管理 + 声明式应用商店
  （数百应用一键安装）+ 计划任务 + 工具箱」覆盖 Linux 服务器运维全流程。差距结论：v2 平台
  对宿主机上的容器负载零视角，把一套中间件交付给使用者需要一长串命令行操作，周期性运维
  （备份/快照）靠人记。
- **Portainer**：容器面板的交互基线——容器终端、跟随日志、资源占用实时列、批量启停。差距结论：
  容器管理若要做，这四项是「及格线」而非加分项。
- **JumpServer**：资产授权模型已在 v2 吸收（见 §2.1），v3 不再扩展。

由差距推导的功能需求如下（全部已落地，实现模块以代码为准）：

| 需求 | 需求描述 | 对应模块 |
|---|---|---|
| 容器管理 | 宿主机上的容器 / 镜像 / 网络 / 卷 / compose 编排（项目级启停）统一查看与操作；容器终端（进入容器内 shell）、日志查看（跟随/下载/tail 行数）、资源占用实时统计、悬空镜像与容器清理。与虚拟机管理并列构成「KVM 域 + Docker 容器」双运行时统一面板 | `service/dockerx`、`handler/docker*.go`、`DockerList.vue` |
| 应用商店 | 把「部署一套中间件」收敛为一键安装：声明式应用包（元数据 + 动态表单定义 + compose 模板占位），安装前端口预检、异步任务安装、卸载保留数据目录 | `service/appstore`（`conf/appstore` 内置 20 个应用） |
| VM 应用 | 未运行 Docker 的虚拟机同样需要一键装软件：经 SSH 在客户机内幂等执行安装脚本（已装检测自动跳过） | `service/apps` |
| AI 运维助手 | 用自然语言查询平台状态、获得运维建议：OpenAI 兼容 API 代理，API Key 只存服务端；可注入平台环境摘要（VM/容器/告警统计）使助手「看得懂这台服务器」；助手只读、无任何写操作能力 | `handler/ai.go` |
| SSH 凭据托管 | 文件管理与应用安装都需要虚拟机口令，反复手填繁琐且易经聊天工具泄露：AES-256-GCM 加密落库（主密钥运行时注入 + 每条记录随机盐），消费方在后端解密使用、明文不出服务端 | `service/secretbox` + `service/vmssh` + `handler/vm_credentials.go` |

| 公告板与拓扑图 | 面向全员的公告展示（登录页 + 仪表盘公开可读）；宿主机-存储池-虚拟机从属关系可视化 | `handler/announcement.go`、`Topology.vue` |

### 4.1 安全需求（细化）

平台以 root 级能力操作宿主机的虚拟化资源，一旦被越权驱动，影响面不限于平台自身数据。
故安全需求按「攻击者可控的输入 → 该输入最终流向哪个解释器」逐条约束：

| 输入 | 流向的解释器 | 需求 |
|---|---|---|
| 路径参数 `:id` | SQL（GORM 内联条件） | 必须先解析为数值主键再进入查询，禁止以字符串形态构造条件 |
| 存储池路径、卷名与格式、网络名与网关 | libvirt XML 定义 | XML 必须由结构化序列化生成（元字符自动转义），并在接口层限制取值域 |
| 宿主机 `ssh_ip` | 外部进程 argv（`ping`） | 必须限定为 IP 或保守主机名，禁止以连字符开头（会被当作命令选项） |
| Web 终端首帧的 SSH 目标 | 出站网络连接 | 必须限定在平台管理的私有网段内，禁止主机名（防 DNS 解析到公网与 DNS rebinding） |
| JWT 的 `alg` 头 | 签名验签逻辑 | 必须锁定为签发时所用算法，防算法混淆 |
| 密钥与口令 | 配置与日志 | 生产模式（`SERVER_MODE=release`，且为**默认值**）禁止使用空密钥或命中弱密钥黑名单的 JWT 密钥（内置默认值与 compose 示例弱值均拒绝启动），并拒绝 `CORS_ORIGINS=*`；明文口令不得进入日志 |

### 4.2 可靠性需求（细化）

- Web 框架的 panic 恢复机制只覆盖 HTTP 请求处理链，**不覆盖任何自行启动的 goroutine**。
  平台的后台 worker、定时清扫器与 WebSocket 转发协程均在请求链之外，须各自具备恢复能力，
  且恢复后仅向用户暴露中文友好文案，原始 panic 值与调用栈只进服务端日志。
- 并发写同一 WebSocket 连接在所用库中属未定义行为并直接 panic，须由统一封装保证写入串行化。
- 后台任务队列在积压时不得无上限地增加等待协程，须有明确的等待上界与失败反馈。
- 前端构建产物缺失属于开发期常态，不应导致后端进程退出。

### 4.3 正确性与数据安全需求（细化）

安全需求（4.1）防的是外部攻击者，本节约束的是平台自身实现错误造成的数据损坏。这类问题的共同特征是
**不报错、不崩溃**，只在特定操作序列下暴露，因此需求上必须明确「怎样才算做对」而非「调用了什么」。

| 需求 | 判据（可验证） | 反例（若不约束会怎样） |
|---|---|---|
| 功能语义须可被外部工具验证 | 「增量克隆」的判据是产出的 qcow2 文件有 backing file：`qemu-img info` 有 `backing file:` 行、`virsh vol-dumpxml` 有 `<backingStore>` 节点、`qemu-img check` 无错误 | 平台调用了名字与「克隆」相关的 libvirt 接口即宣称实现，实际是全量拷贝、无 backing file，功能名不副实且无人发现 |
| 复制出的实体须重新生成全部唯一标识 | 克隆机的 UUID 与**每块网卡的 MAC** 都与源机不同，且格式合法 | libvirt 拒绝重复 UUID（会立刻暴露）但**不校验 MAC**，MAC 沿用源机不会报错，直到两台同时开机才 ARP 冲突、网络双双不可用 |
| 破坏性操作按「保留优先」设计 | 删除虚拟机只清理本机独占的卷；属于其他实体的共享卷（增量克隆父盘、镜像库登记的基镜像）必须保留 | 误删父盘导致 backing chain 断裂，所有子虚拟机磁盘不可读且不可恢复；误删基镜像留下 `images` 表悬挂记录 |
| 「没做某个操作」也要可观测 | 被保留的卷及其中文原因须回传到任务结果并写入服务端日志 | 用户以为删干净了，实际残留文件；或以为删除失败，实际是刻意保留 |
| 同一语义在多层间只有一种写法 | 状态字面量由常量定义，各层引用同一批取值 | `vms.status` 列默认值写成 `shut_off`（下划线）而映射函数返回 `shut off`（空格），落到默认值的记录在前端无法匹配任何状态 |

> 需求层面的取舍也一并明确：「保留优先」会产生孤儿文件（父盘的全部子卷删完后它已无人引用却仍在池里）。
> 这是可接受的——垃圾文件可事后清理，损坏的在用磁盘不可恢复。孤儿卷清理已作为增强需求落地
> （存储池页「清理孤儿卷」，零引用才删）。
