## 1. 系统目标与定位

- [ ] 轻量级私有云管理平台（面向实验室/小型私有云）
- [ ] 核心：基于 KVM 对多宿主机 + 虚拟机统一管理
- [ ] 满足「可管、可控、可追溯」

## 2. 角色与权限

- [x] admin（管理员）：全部操作权限，含 SSH 终端与串口控制台
- [x] viewer（只读运维）：**完全只读**——可访问全部读接口，可打开图形控制台但仅供观看
- [x] 权限控制方式（JWT 角色 + `AdminMiddleware` / `OperatorMiddleware`）

「只读」在本系统中的判定标准不以 HTTP 方法为唯一依据。浏览器发起 WebSocket 连接时只能使用
GET 方法，因此 SSH 终端（`GET /api/vms/:id/terminal`）与串口控制台（`GET /api/vms/:id/serial`）
在协议层表现为读请求，实质上却建立了对客户机的**双向写入**通道：前者是完整的 SSH shell，
后者直连虚拟机串口，在多数云镜像上即 root TTY。若仅按方法放行，只读角色便可经由控制台
取得客户机内的任意写权限，与角色语义矛盾。故权限需求明确为：

| 通道 | 协议层方法 | 实质语义 | admin | viewer |
|---|---|---|---|---|
| 读接口（列表 / 详情 / 统计） | GET | 读 | ✓ | ✓ |
| 变更接口（增删改、启停、克隆） | POST/PUT/DELETE | 写 | ✓ | ✗ 403 |
| 图形控制台（VNC） | POST 取 token | 观看（键鼠可禁用） | ✓ 可操作 | ✓ **只读观看** |
| SSH 终端 | GET（WebSocket） | **写**（shell） | ✓ | ✗ 403 |
| 串口控制台 | GET（WebSocket） | **写**（串口 TTY） | ✓ | ✗ 403 |
| 用户 / 审计 / 设置 | 全部 | 敏感 | ✓ | ✗ 403 |

图形控制台的只读性需在客户端实现：VNC（RFB）协议本身不提供只读模式，服务端无法单向裁剪
输入通道，因此由后端在签发 token 时下发 `view_only` 标记，前端据此以 noVNC 的 `view_only`
模式加载，禁用键盘与鼠标事件。

## 4. 非功能需求

- [ ] 性能：接口响应、KVM 操作耗时
- [x] 安全：JWT 鉴权、bcrypt、目录穿越防护、输入校验（细化见 4.1）
- [x] 可靠性：单次请求或单个后台任务的异常不得导致整个服务进程退出（细化见 4.2）
- [x] 正确性与数据安全：功能语义须可被外部工具验证，破坏性操作不得损坏其他实体的数据（细化见 4.3）
- [ ] 易用性：Web 管理界面、六页面覆盖
- [ ] 可维护性：分层结构、统一响应封装
- [ ] 可部署性：单二进制 + 前端静态托管

### 4.1 安全需求（细化）

平台以 root 级能力操作宿主机的虚拟化资源，一旦被越权驱动，影响面不限于平台自身数据。
故安全需求按「攻击者可控的输入 → 该输入最终流向哪个解释器」逐条约束：

| 输入 | 流向的解释器 | 需求 |
|---|---|---|
| 路径参数 `:id` | SQL（GORM 内联条件） | 必须先解析为数值主键再进入查询，禁止以字符串形态构造条件 |
| 存储池路径、卷名与格式、网络名与网关 | libvirt XML 定义 | XML 必须由结构化序列化生成（元字符自动转义），并在接口层限制取值域 |
| 宿主机 `ssh_ip` | 外部进程 argv（`ping`） | 必须限定为 IP 或保守主机名，禁止以连字符开头（会被当作命令选项） |
| Web 终端首帧的 SSH 目标 | 出站网络连接 | 必须限定在平台管理的私有网段内，禁止主机名（防 DNS 解析到公网与 DNS rebinding） |
| JWT 的 `alg` 头 | 签名验签逻辑 | 必须锁定为签发时所用算法，防算法混淆 |
| 密钥与口令 | 配置与日志 | 生产模式禁止使用内置默认密钥；明文口令不得进入日志 |

### 4.2 可靠性需求（细化）

- Web 框架的 panic 恢复机制只覆盖 HTTP 请求处理链，**不覆盖任何自行启动的 goroutine**。
  平台的后台 worker、定时清扫器与 WebSocket 转发协程均在请求链之外，须各自具备恢复能力，
  且恢复后仅向用户暴露中文友好文案，原始 panic 值与调用栈只进服务端日志。
- 并发写同一 WebSocket 连接在所用库中属未定义行为并直接 panic，须由统一封装保证写入串行化。
- 后台任务队列在积压时不得无上限地增加等待协程，须有明确的等待上界与失败反馈。
- 前端构建产物缺失属于开发期常态，不应导致后端进程退出。

### 4.3 正确性与数据安全需求（细化）

安全需求（4.1）防的是外部攻击者，本节约束的是平台自身实现错误造成的数据损坏。这类问题的共同特征是
**不报错、不崩溃**，只在特定操作序列下暴露，因此需求上必须明确「怎样才算做对」而非「调用了什么」。

| 需求 | 判据（可验证） | 反例（若不约束会怎样） |
|---|---|---|
| 功能语义须可被外部工具验证 | 「增量克隆」的判据是产出的 qcow2 文件有 backing file：`qemu-img info` 有 `backing file:` 行、`virsh vol-dumpxml` 有 `<backingStore>` 节点、`qemu-img check` 无错误 | 平台调用了名字与「克隆」相关的 libvirt 接口即宣称实现，实际是全量拷贝、无 backing file，功能名不副实且无人发现 |
| 复制出的实体须重新生成全部唯一标识 | 克隆机的 UUID 与**每块网卡的 MAC** 都与源机不同，且格式合法 | libvirt 拒绝重复 UUID（会立刻暴露）但**不校验 MAC**，MAC 沿用源机不会报错，直到两台同时开机才 ARP 冲突、网络双双不可用 |
| 破坏性操作按「保留优先」设计 | 删除虚拟机只清理本机独占的卷；属于其他实体的共享卷（增量克隆父盘、镜像库登记的基镜像）必须保留 | 误删父盘导致 backing chain 断裂，所有子虚拟机磁盘不可读且不可恢复；误删基镜像留下 `images` 表悬挂记录 |
| 「没做某个操作」也要可观测 | 被保留的卷及其中文原因须回传到任务结果并写入服务端日志 | 用户以为删干净了，实际残留文件；或以为删除失败，实际是刻意保留 |
| 同一语义在多层间只有一种写法 | 状态字面量由常量定义，各层引用同一批取值 | `vms.status` 列默认值写成 `shut_off`（下划线）而映射函数返回 `shut off`（空格），落到默认值的记录在前端无法匹配任何状态 |

> 需求层面的取舍也一并明确：「保留优先」会产生孤儿文件（父盘的全部子卷删完后它已无人引用却仍在池里）。
> 这是可接受的——垃圾文件可事后清理，损坏的在用磁盘不可恢复。孤儿卷清理属增强需求，不是本轮范围。
