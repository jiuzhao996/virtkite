### 4.3 第三批：安全校验与 XML 编解码（P4，15 个文件）

P4 批次把 P0–P2 的安全加固固化为回归测试，并补齐 `service/virt` 的 XML 编解码覆盖。
核心用例选录（全部为表驱动 + 中文场景名，`go test -race` 全绿）：

**`service/virt/spec_test.go`（13 函数，domain XML 是全平台配置流转的枢纽）**

| 用例 | 风险点 |
|---|---|
| 最小域/复杂域逐字段解析 | 纳管、克隆、删除都读同一入口，字段错位会连带污染 |
| 内存单位换算（KiB/MiB/GiB/bytes/无单位/大小写/空白） | 算错直接影响创建向导的内存展示 |
| vcpu `current` 优先、缺失回退 chardata | 热升级头寸存于 chardata，取错会把上限当当前核数 |
| 生成器参数校验（nil/空名/0 核/负内存） | 非法定义喂给 libvirt define |
| **XML 转义专项**：名称/路径/网络名塞入闭合载荷，反解确认值原样、节点数无增加 | P1「字符串拼接改 marshal」的回归锚点 |
| **往返测试** `Parse(Build(spec))` | 抓编解码不对称（如某字段只写不读，克隆会静默丢配置） |
| `NextDiskTarget`（空盘/占位/空洞/跨 bus/26 块续编） | target 冲突会导致热插拔失败 |

往返测试中显式断言了两处「设计使然的不对称」：`RawXML`/`Autostart` 不在 domain XML 中（还原为空），
光驱空 driver 生成时按 `raw` 落盘（反解回来是 `raw` 而非空）。把「已知的不对称」写进测试，
可防止后人误判为 bug 而「修复」。

测试中另发现一处真实缺陷（已记录未修）：`diskSuffixIndex("aa")` 算出 0，与 `"a"` 冲突——

虚拟机现实中几乎不存在，故断言现状 + TODO 注释，不在此轮修复。

**`handler/terminal_test.go`（4 函数 / 67 例）**：`validateSSHTarget` 的双分支（VM 已记录 IP 则精确匹配；

### 5.1 实验环境

| 项 | 值 |
|---|---|
| 磁盘 | NVMe SSD × 2（Great Wall GW3000 1TB + SK hynix 512GB，`lsblk` 报告 ROTA=0） |
| 虚拟化 | libvirt（`qemu:///system`，unix socket 直连） |

### 5.2 实验 1：linked clone 与全量拷贝

同一基准卷、同一存储池，对比两条建卷路径：

- **全量拷贝**：`StorageVolCreateXMLFrom`（等价 `virsh vol-clone`）——修复前「增量克隆」的真实实现路径；
- **linked clone**：`StorageVolCreateXML` + 卷 XML 声明 `<backingStore>`（等价 `qemu-img create -f qcow2 -F qcow2 -b 父盘 子盘`）——修复后路径（见 10.2 F-19）。

| 组 | 测试口径 | 轮次 | 各轮耗时（ms） | 均值 | 产物实际磁盘占用（`du`） | 产物 backing file |
|---|---|---|---|---|---|---|
| 全量拷贝 | `StorageVolCreateXMLFrom`（`virsh vol-clone`） | 3 | 970 / 964 / 965 | ≈966 | 1031MB | **无** |
| linked clone | `StorageVolCreateXML` + `<backingStore>` 卷 XML（`qemu-img create -b`） | 5 | 38 / 33 / 34 / 32 / 35 | ≈34 | ≈1MB | 指向源卷（qcow2） |

linked clone 产物验证（口径固定为三条外部命令，见 10.2 F-19）：

- `qemu-img info`：`backing file:` 指向源卷，且 `backing file format: qcow2`；
- `qemu-img check`：`No errors were found on the image`（镜像结构无错误）。

结论：

1. 本组数据下 linked clone **约 28 倍提速**、产物磁盘开销**千倍级缩减**（1031MB → ≈1MB）。
2. 比单点数字更重要的是两组的性质差异：全量拷贝的耗时随源卷**实际数据量**线性增长（本例源卷实际
   数据 529MB 即耗时约 1 秒，源盘越接近写满耗时等比放大），linked clone 只写元数据，耗时与数据量
   无关——即克隆耗时对用户是一个**可预期的常数**，而全量拷贝不可预期。这一性质差异决定了后者才配
   称「增量克隆」。
3. 方法论呼应（见 10.2 F-19）：「调用了哪个 API」不构成功能语义的证明——全量组正是当年「名不副实」
   的实现路径，其外部可观测结果（`qemu-img info` 无 `backing file` 行）就是反证；本实验同样以外部
   可观测结果（计时、`du`、`qemu-img info`）作为两组的唯一判据，不以代码注释为准。

### 5.3 实验 2：平台自身资源占用

| 项 | 占用 | 采样口径 |
|---|---|---|
| vmops 生产实例 | RSS 35.9MB / 16 线程 | `ps` 采样；宿主机约 30 个域定义 |
| 冷启动新实例 | RSS 24MB | 启动完成后即采样 |
| 平台二进制 | 27MB | 单文件，已内嵌前端产物 |
| MySQL（容器） | 204.8MB | `docker stats` |
| **核心合计（平台 + MySQL）** | **≈240MB** | 上述两项之和 |
| Prometheus（可选） | 31.4MB | 容器 |
| Alertmanager（可选） | 14.2MB | 容器 |
| Grafana（可选） | 221.7MB | 容器 |

对照组（官方文档口径，量级对比）：

- OpenStack 安装指南最低要求：controller 4GB + compute 2GB（all-in-one 部署的实践建议 16GB+）；
- Proxmox VE 官方最低要求：2GB（OS + 管理服务，不含 guest）。

结论：vmops 控制面自身内存占用比上述两家低 **1–2 个数量级**（≈240MB 对 2–4GB 量级），监控栈为可选
组件且单组件不超过 222MB。受限硬件（如 8GB 内存的实验室旧机器）即可承载平台本体与若干小规格 guest，
这正是「轻量级私有云管理平台」定位的资源侧依据。

### 5.4 实验 3：部署耗时

| 项 | 实测 / 口径 |
|---|---|
| 冷启动 | **206ms**（进程启动到 API 可响应，含 MySQL 连接、GORM AutoMigrate、种子数据检查；后端启动日志时间戳） |
| 部署动作 | 拷贝 27MB 单二进制 + 一个可用的 MySQL（compose 一键拉起） |
| 对照 | OpenStack 手工部署的公开实践通常以小时计（组件多、依赖关系复杂；此处为量级对比而非同条件实测） |

结论：单二进制 + 单数据库的部署形态把「平台可用」收敛为一次文件拷贝，冷启动亚秒级；与多组件分布式
控制面的部署复杂度差距在一个数量级以上。

| S-FMT-04 | viewer 发起写操作 | 403 | `{"code":403,"data":null,"message":"需要管理员权限"}` ✓ |
| S-FMT-05（不得变更） | `GET /api/vnc/token/bad`（websockify 回调，外部契约） | 404 `{"error":...}` 保持原样 | `{"error":"token 无效或已过期"}` ✓ |

S-FMT-05 是有意保留的例外：该接口由 websockify 的 JSONTokenApi 插件消费，响应格式由 websockify
规定，改为统一格式会使 noVNC 链路整体失效。

### 6.9 登录限流（确认项，功能行为见 2.18）

2.18 已记录功能行为（同 IP 1 分钟内失败 5 次即锁定、第 6 次返回 429「登录失败次数过多」、成功登录
清零计数、不同 IP 互不影响）。此处从安全视角补充确认三点实现语义（`handler/auth.go` 的
`loginLimiter`，附单元测试）：

- 锁定期间**正确密码同样拒绝**——不向爆破者泄露「密码已经猜中」这一信号；
- 计数为进程内存实现、按来源 IP 维度（1 分钟窗口 / 5 次失败阈值），重启即清零——取舍是不为此引入
  额外存储依赖，锁定粒度以单实例为界；
- 超限响应与其他错误一样走统一中文文案，不回显内部细节。

### 6.13 SSH 主机密钥 TOFU 与 XML 直定义收权（v3.3 安全收口）

6.7 记录的「`HostKeyCallback` 为 `InsecureIgnoreHostKey()`」残余风险已由 v3.3 批次闭环：

| 编号 | 场景 | 预期 | 实际 |
|---|---|---|---|
| S-TOFU-01 | 首次 SSH 连接某 host:port | 连接放行，服务器公钥 SHA256 指纹落库 `host_keys`（等价 openssh 写 known_hosts） | 单测三路径验证：首连放行 + 指纹/算法名落库正确 ✓ |
| S-TOFU-02 | 后续连接指纹一致 | 放行 | ✓（同上） |
| S-TOFU-03 | 服务器主机密钥被替换（指纹不一致） | 拒绝连接，错误可被 `errors.Is(ErrHostKeyMismatch)` 识别，文案为固定中文风险提示 | ✓ |
| S-TOFU-04 | 指纹存储未注入 / 查询失败 | **拒绝连接（fail-closed）**，绝不退化成不校验 | ✓（两条专用用例） |
| S-TOFU-05 | 虚拟机重建后密钥更换 | 管理员删旧指纹（`DELETE /api/ssh-host-keys/:id`，仅 admin）后下连重新 TOFU 记录 | 端点经代码路径审查（删除不存在返回 404「指纹记录不存在」）；重录路径由 S-TOFU-01 语义保证 ✓ |
| S-XMLAUTH-01 | operator 提交 `PUT /api/vms/:id/xml`（原始 XML 直定义） | 403（handler 内 `requireAdminRole` 二次收口——该路由在 `/api/vms` 前缀下，中间件层对 operator 放行，须再收一道） | 单测 `TestUpdateVMXMLRequiresAdmin` 走真实路由注册验证 ✓ |

TOFU 的取舍与论证（为何不用人工核对 known_hosts）：平台自建 VM 由 DHCP 动态分配 IP、重建即换
主机密钥，「人工核对指纹」环节不可操作，故采用自动 TOFU；目标范围仍由 `validateSSHTarget`
白名单收敛到私有网段，指纹比对是叠加的纵深防御层。实现细节见 docs/05 §11.3，
存储模型见 docs/04 §3.16。

### 10.2 问题与修复记录（P2 正确性）

本批与 P0/P1 的性质不同：P0 修的是「会让进程死掉」的稳定性缺陷，P1 修的是「会被外部攻击者利用」的
安全缺陷，P2 修的是**「功能表面可用、实际语义与文档声称不符」的正确性缺陷**。这类缺陷不报错、不崩溃，
只在特定操作序列下造成不可恢复的数据损坏，因此只能靠外部工具复核功能语义才能发现。

| F-19 | **「增量克隆」并未实现，而 README 与多篇文档都把它作为核心特性宣称** | 原 `CloneVolumeFromVol` 用 `StorageVolCreateXMLFrom`（等价 `virsh vol-clone`），函数注释还写着「libvirt 自动写 qcow2 backing file」；实测该 API 是**全量数据拷贝**，产出的子卷没有 backing file。功能退化为整盘复制，但因为拷贝也能正常开机，缺陷长期未被察觉 | 改用 `StorageVolCreateXML` + 卷 XML 内声明 `<backingStore>`（等价 `qemu-img create -f qcow2 -F qcow2 -b`）；新增 `buildVolumeXMLWithBacking` 与 `volBackingXML`，`buildVolumeXML` 退化为薄封装 | T-Clone-01（三条外部命令：`qemu-img info` 有 `backing file:`、`vol-dumpxml` 有 `<backingStore>`、`qemu-img check` 无错误；修复前前两条均不存在） |

| F-22 | Dockerfile 无法构建 | ① `golang:1.21` 不满足 `go.mod` 的 `go 1.25.0`；② `go build -o vmops ./...` 必报 `cannot write multiple packages to non-directory`（仓库有 11 个包）；③ 容器内 `proxy.golang.org` 超时使 `go mod download` 挂死；④ alpine 无 `/usr/share/zoneinfo` 而 DSN 带 `loc=Local`，时间静默退化 UTC 差 8 小时；⑤ `alpine:3.19` 已 EOL；⑥ `web/dist/` 被 gitignore，干净克隆里 `COPY web/dist` 直接失败 | 整文件重写：`golang:1.25-alpine`、`-o vmops .`、`ARG GOPROXY=https://goproxy.cn,direct`、`-tags timetzdata` + `ENV TZ=Asia/Shanghai`、`alpine:3.24`、`web/dist` 改从 builder 阶段拷贝并 `mkdir -p` 兜底 | `docker build --no-cache` 成功，74 秒，产物 51.5MB（见第 7 章） |
| F-23 | `vms.status` 列默认值与状态映射不一致 | `model/vm.go` 的 gorm 默认值写作 `shut_off`（下划线），而 `StateToPlatform` 返回 `shut off`（空格），前端亦按空格版本匹配；一旦某行落到列默认值，其状态在前端无法匹配任何已知状态 | 默认值改 `shut off`；新增 `model.VMStatus*` 与 `virt.Status*` 两套常量，`handler/vm.go` 8 处字面量改引用（virt 刻意不 import model，避免把 GORM 拖进封装层） | 数据库核查确认**无** `shut_off` 存量行（所有写入路径都显式给值）；沙箱验证 GORM `AutoMigrate` 能改已有列默认值，重启即收敛 |
| F-24 | `ImportVMs` 内部错误泄漏（handler 层最后一处） | `fmt.Sprintf("%s: %v", name, err)` 把 GORM 原始错误（表结构、约束名）拼进响应 `errors` 数组 | 完整错误经 `LogError` 进日志，响应只给「域名 + 写入数据库失败」 | 代码路径审查；同时更正一处认知：该 `errors` 数组前端 `VmList.vue` 实际未消费，失败原因暂不呈现给用户（列入 10.3） |

关于 F-19 的方法论意义（论文可展开）：修复前的代码调用了名字看起来完全正确的 libvirt API，注释、

的证明**，必须由该功能的外部可观测结果反证。此后「增量克隆」的验收被固定为三条外部命令
