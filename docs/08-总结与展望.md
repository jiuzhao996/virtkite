## 1. 工作总结

已完成功能回顾：认证与三级角色 RBAC（admin/operator/viewer）、VM 资产授权（vm_grants，借鉴堡垒机 4A：授权决定可见性）、宿主机管理、VM 生命周期、异步任务系统、会话跟踪与控制台三链路、镜像与模板、增量克隆与 cloud-init、硬件热管理（磁盘/网卡/核/内存）、存储池、网络、快照、审计、仪表盘、任务中心/会话管理/系统设置前端，以及创建向导与列表实时化。

核心成果：真实 KVM 建机、耗时操作异步化（202 + 轮询）、控制台会话可观测可收敛、增量克隆节磁盘、操作审计可追溯、单二进制轻量部署。

功能完备之后另做了三轮加固，分别针对**进程稳定性**、**外部安全**与**功能正确性**。前两轮的共同思路是
「把隐性假设显式化」：并发写 WebSocket 假设了库允许多协程写、后台协程假设了框架会兜住 panic、路径参数
假设了 ORM 会参数化、XML 拼接假设了输入不含元字符、`alg` 假设了客户端不会改、密钥校验假设了默认值不
存在——这些假设逐条被证否并修正。其中「viewer 完全只读」这一结论值得单独强调：加固前只读角色可经 SSH
终端与串口控制台取得客户机内的任意写权限（两者协议层是 GET，实质是双向写入通道），角色名不副实；加固
后二者对 viewer 关闭，图形控制台改为客户端禁用键鼠的只读观看，只读语义才真正成立。

第三轮（正确性）的性质不同，也是三轮里最值得写进论文的一段：它修的不是「会崩」或「会被攻击」的问题，
而是**「文档声称已实现、实际并未实现」的问题**。最典型的一例是「增量克隆」——README 与多篇设计文档都
把它列为核心特性，代码里也确实调用了一个名字看起来完全正确的 libvirt API（`StorageVolCreateXMLFrom`，
即 `virsh vol-clone`），注释还写着「libvirt 自动写 qcow2 backing file」；但实测该 API 做的是全量数据
拷贝，产出的子卷根本没有 backing file。因为整盘拷贝出来的虚拟机同样能正常开机，这个缺陷在相当长的时间
里没有暴露。由此得到的方法论结论是：**「调用了哪个 API」不构成功能语义的证明，必须由该功能的外部可观测
结果反证**（此处即 `qemu-img info` 的输出）。修复后把「子盘有 `backing file:` 行 / `vol-dumpxml` 有
`<backingStore>` 节点 / `qemu-img check` 无错误」三条外部命令固定为该功能的验收方式。

同一轮里另有两个「不报错的错误」：克隆机沿用源机 MAC（libvirt 拒绝重复 UUID 但不校验 MAC，因此直到两台
同时开机、同网段 ARP 冲突才会发现），以及删除虚拟机会误删被其他机器依赖的共享卷（真正实现 backing chain
后，误删父盘意味着所有子机磁盘不可恢复）。两者的修复方式也反映了两条设计取向：把配置派生抽成不依赖
libvirt 的纯函数以便单元测试断言；破坏性操作按「保留优先」而非「删干净优先」设计，并把「哪些卷没删、
为什么没删」回传给用户。

工程实践：Go + Vue3 + MySQL + libvirt 全栈；virt 封装层统一 libvirt 出口；任务队列与会话注册表两个后台子系统；
单元测试从 0 补到 142 个顶层测试函数（约 950 个子用例 / 7 个包，`go test -race` 全绿），并以反证实验确认修复有效。

  磁盘与网络 → 确认创建。「导入现有磁盘」方式与「引导顺序」设置面板（含后端 `PUT /vms/:id/boot`）
  因体验与语义问题**整体删除**；cloud-init 配置收敛到云镜像方式的第 1 步内。
- **向导体验增厚**：前置条件检查（网络/安装源/激活池，缺项 alert + 直达链接）、存储池下拉带可用空间与
  超额红字预警、云镜像增量盘标注、网络下拉按 libvirt forward 类型分组、ISO 介质平铺选择全部激活池并按
  文件名自动识别操作系统、cloud-init 双入口收敛。
- **镜像管理页双 tab**：「云镜像 / 模板盘」（登记既有池卷 + 上传 + 模板标记）与「ISO 安装镜像」（只读
  展示，管理在存储池页），带来源存储池标注；存储池新增角色/描述元数据（`pool_meta`）。
- **仪表盘与监控中心融合**：仪表盘概览/监控双 tab（监控 tab 复用监控中心），资源容量/超分卡
  （`GET /api/dashboard/capacity`），监控中心增厚——Grafana 探活兜底（`grafana-status`）、告警历史卡、
  file_sd 目标预览卡、告警规则补至 9 条、看板按宿主机/虚拟机分组重构。
- **磁盘分离可选删卷**：`DELETE /api/vms/:id/devices/disks/:target?delete_volume=`——「仅分离（保留
  存储卷）」为默认，「分离并删除存储卷」为危险项，走四重守卫（镜像库 / backing 父盘 / 他机挂载 /
  cdrom 共享介质），响应含 `volume_deleted` 与 `keep_reason`。
- **设备级快捷操作**：一键添加磁盘（建卷 + 热挂载合一）、幂等补齐标准设备（guest-agent 通道 +
  virtio-rng）；父盘链可视化（`ParseDomainXML` 补解析 `<backingStore>`，详情页可见「子 ← 父」链）。

### 2.8 本轮（三级角色与资产授权批次）已落地成果一览

- **三级角色 RBAC**：admin / operator / viewer 三级——operator = VM 全生命周期 + 三类控制台
  （SSH/串口/图形），`/api/vms` 之外的写操作（宿主机/存储/网络/镜像）一律 403；viewer = 只读 +
  图形控制台 view_only。`TestOperatorMiddleware` 12 用例矩阵走真实路由注册守住边界。
- **资产授权（借鉴堡垒机 JumpServer 4A 轻量版）**：新增 `vm_grants` 授权表（user_id×vm_id 唯一，
  `expires_at` 到期即失效，查询时校验、无需清扫协程，行保留可查授权历史）；**授权决定可见性**——
  非 admin 未授权访问 VM 一律 404 查无此项（未授权与不存在同响应，不泄露存在性）；授权管理在
  VM 详情页「授权管理」面板（admin：`GET/POST /api/vms/:id/grants`、`DELETE .../grants/:gid`）；
  建机/克隆自动授权发起人，删 VM 回收授权。
- **监控中心 viewer 收权**：告警 / 告警历史 / file-sd / grafana-status 四端点经
  `NonViewerMiddleware` 对 viewer 返回 403（告警与 file-sd 携带资产名单，viewer 不得见）。
- **启动安全默认**：`SERVER_MODE` 默认值从 debug 改为 release（安全默认），本地开发由 `start.sh`
  自动 `export SERVER_MODE=debug` 兜底；release 校验升级为 JWT **弱密钥黑名单**（内置默认值与
  compose 示例弱值均拒绝启动，三态实测见 docs/06 §6.12）；`docker-compose.yml` 的
  `JWT_SECRET_KEY` 改 `${JWT_SECRET_KEY:?...}` 强制外部注入。
- **任务系统启动收敛**：启动时清扫数据库遗留的 `pending/running` 任务置 failed
  （「服务重启，任务已中断」），进程重启不再留僵尸任务。
- **测试增厚**：142 个顶层测试函数 / 7 个包全绿（新增授权有效期 `TestVMGrantActive` 与
  operator 中间件矩阵）；授权链路 E2E 实测：未授权列表 total=0 → 授权后只见该机 → 到期自动消失
  → 越权 403。

## 3. 展望

- **授权规则矩阵化**：当前 `vm_grants` 是「用户×VM」平面表（单宿主机场景刻意取舍）；后续对齐
  JumpServer 完整形态做 用户组×节点×动作×协议 的四维授权矩阵与授权申请/审批流。
- **per-VM 创建者强归属**：在 VM 模型上固化 `created_by` 归属，与授权体系联动做「创建即归属、
  归属者天然可见」。
- **数据库 schema 版本化**：引入 golang-migrate，替代「AutoMigrate 一把梭 + 列残留靠人工审查」
  （如 `hosts.libvirt_uri` 砍除后 AutoMigrate 不 drop 列）。
- 受限硬件（16GB）下轻量私有云的可落地性（资源占用对比已实测：控制面核心 ≈240MB，见 docs/06 第 5 章）。
- 混合云统一资源视图。
- 故障演练与任务耗时分布数据（性能与对比实验已完成三组，见 docs/06 第 5 章；故障演练仍待做）。
