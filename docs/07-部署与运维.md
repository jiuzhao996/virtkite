## 1. 部署形态

平台支持两种部署形态（详见 deploy/README.md，为部署配置的唯一事实源）：

- **混合形态（开发/演示推荐，当前使用）**：vmops 应用 + websockify 原生跑在宿主机（控制台链路贴着 libvirt 最稳），
  MySQL + 监控三件套（Prometheus/Alertmanager/Grafana）走 docker 容器。
- **一键全容器形态（发布形态）**：`docker compose up -d` 拉起全部 6 个容器
  （mysql / app / websockify / prometheus / alertmanager / grafana），宿主机只需 Docker + KVM。
  app 容器经挂载 `/var/run/libvirt/libvirt-sock` 直通宿主机 libvirtd（libvirt 本身无法容器化）。

两形态共用 deploy/ 下同一套 yml/json 配置；运行 vmops 的机器本身不必是 KVM 宿主机，但被纳管宿主机需能执行 virsh。

## 2. 环境要求

- Go **1.25+**（`go.mod` 声明 `go 1.25.0`，低版本编译直接报版本不足）/ Node.js 18+ / MySQL 8 / libvirt+qemu-kvm。
- 网页控制台：novnc / websockify（`sudo apt install novnc websockify`）。

## 3. 方式一：docker-compose 一键部署（推荐演示）

- 前端先构建：`cd web && npm run build`（`web/dist/` 被 `.gitignore` 排除，但会随构建上下文进入镜像；未构建时镜像内为空目录，后端降级为「仅 API」而非退出，见 5.2）。
- 再 `docker compose up -d --build`。
- 容器：vmops-mysql / vmops-app / vmops-websockify（:6080，由 `docker/websockify.Dockerfile` 构建，
  debian novnc+websockify 包）/ vmops-prometheus（:9090）/ vmops-alertmanager（:9093）/ vmops-grafana（:3000，admin/admin）。
- 监控镜像版本：grafana **13.2.1**（完整版）/ prometheus **v3.14.0** / alertmanager **v0.34.0**。
  **Grafana 勿用 -slim 镜像**：slim 不含内置数据源插件，Prometheus 数据源会报 `plugin not registered`，
  且后台补装依赖 grafana.com 外网、极慢且不可靠。
- Docker Hub 直连超时的环境：用 `docker.m.daocloud.io` 拉取后 `docker tag` 回官方名。
- **混合形态请勿启动 websockify 容器**（与宿主机 start.sh 起的 websockify 抢 6080）：
  按需 `docker compose up -d mysql prometheus alertmanager grafana`。
- app 容器挂载宿主机 libvirtd socket（`/var/run/libvirt/libvirt-sock`），无 KVM 的机器需注释该挂载（指标为空但服务可启动）。

### 3.1 Dockerfile 关键点（每项都对应一次实测失败）

镜像为多阶段构建（`golang:1.25-alpine` 构建 → `alpine:3.24` 运行）。以下取值均是踩坑后固定下来的，
改动前请先复现对应故障：

| 项 | 取值 | 不这样写会怎样 |
|---|---|---|
| builder 基础镜像 | `golang:1.25-alpine` | `golang:1.21` 不满足 `go.mod` 的 `go 1.25.0`，构建阶段直接报版本不足 |
| 构建命令 | `go build -tags timetzdata -o vmops .` | 写 `-o vmops ./...` 会匹配到仓库的 11 个包，报 `cannot write multiple packages to non-directory` |
| 模块代理 | `ARG GOPROXY=https://goproxy.cn,direct` | 容器内访问 `proxy.golang.org` 实测超时，`go mod download` 挂死（不是失败，是卡住）。海外/内网环境用 `docker build --build-arg GOPROXY=https://proxy.golang.org,direct` 覆盖 |
| 时区 | `-tags timetzdata` + `ENV TZ=Asia/Shanghai` | alpine 无 `/usr/share/zoneinfo`，而 MySQL DSN 带 `loc=Local`：时区加载失败后**静默**退化为 UTC，审计与任务时间整体差 8 小时且无任何报错 |
| 运行镜像 | `alpine:3.24` | `alpine:3.19` 已停止维护，不再收安全更新 |
| 前端产物 | builder 阶段 `RUN mkdir -p /build/web/dist` 兜底 + 运行阶段 `COPY --from=builder /build/web/dist ./web/dist` | `web/dist/` 被 gitignore，干净克隆里目录不存在，直接 `COPY web/dist` 会因源路径缺失而整个构建失败 |
| 目录布局 | 二进制与 `web/dist`、`static` 同置于 `/app` | 须对齐 `main.go` 的 `locateWebRoot` 探测顺序（见 5.2）：`/app/web/dist` 命中第一候选，`/app/static` 是第二候选兜底 |

构建验证：`docker build --no-cache -t vmops:verify .` **成功，耗时 74 秒，产物 51.5MB**。

### 5.1 生产模式的密钥强校验

`SERVER_MODE=release` 启动时，若 `JWT_SECRET_KEY` 为空**或**仍等于内置默认值
`vmops-jwt-secret-key-change-in-production`，进程直接 `log.Fatalf` 拒绝启动，日志为
「release 模式必须设置 JWT_SECRET_KEY 环境变量：当前为空或仍是内置默认值，存在 Token 伪造风险」。

背景：`config` 包为该项兜了硬编码默认值，因此旧校验只判 `== ""` 时条件永不成立，等于没有校验。
而默认值随源码公开，任何人都能据此签发 `role=admin` 的合法 token（该行为已在测试章 5.4 得到印证）。
部署清单里的第一条应是生成随机密钥，例如：

```bash
JWT_SECRET_KEY=$(openssl rand -hex 32)
```

同款策略还有一项：**release 模式下 `CORS_ORIGINS` 为 `*` 时直接拒绝启动**
（日志「release 模式必须设置 CORS_ORIGINS 环境变量…存在跨站调用 API 的风险」）——
通配符等于允许任意站点携带凭据跨站调用全部 API。

### 5.2 前端产物目录探测

后端按四候选依次探测前端产物，第一个存在 `index.html` 的胜出，并把命中目录写进启动日志
（`前端产物目录: <路径>`）：

1. `<可执行文件目录>/web/dist`
2. `<可执行文件目录>/static`
3. `<当前工作目录>/web/dist`
4. `<当前工作目录>/static`

- 追加「当前工作目录」两项的原因：`go run main.go` 时二进制位于 `/tmp/go-build*/`，只看可执行文件
  目录必然找不到产物。旧实现在此情况下 `log.Fatalf` 退出，即 `go run` 方式必然启动失败。
- 全部未命中时**降级为「仅 API」模式**：打印构建指引，`/` 与未匹配路由返回 503 中文提示页，
  进程继续提供 API（「后端 `go run` + 前端 `npm run dev`」是正常开发姿势，不应视为致命错误）。
- 排错提示：改了前端却不生效，先看启动日志命中的是哪一份产物——很可能命中了另一个候选目录。

## 6. 运维与排错

- 常见问题表（数据库连接失败、libvirt 连接失败、权限拒绝、前端白屏、审计 username 为空）。
- 新增两条启动期排错：
  - 页面返回 503 中文提示「未找到前端构建产物」→ 未 build 前端。执行 `cd web && npm run build` 后重启，或直接用 Vite 开发服务器（其 `/api` 已代理到本服务）。此时后端仍在提供 API，不是后端挂了。
  - release 模式启动即退出并提示 JWT 密钥风险 → 见 5.1，设置自定义 `JWT_SECRET_KEY` 后重启。
  - release 模式启动即退出并提示 CORS 风险 → 见 5.1，设置具体 `CORS_ORIGINS` 后重启。
  - 登录返回 429「登录失败次数过多」→ 触发登录失败限流（同 IP 1 分钟内失败 5 次锁定 1 分钟，
    成功登录清零），等 1 分钟再试即可；这是防口令爆破的预期行为，不是故障。
- 网页控制台：需安装 `novnc` / `websockify`（`sudo apt install novnc websockify`）。
- 一键启动：`./start.sh --service`（后端 + noVNC 无人值守）/ `./start.sh --stop` 停止。
- libvirt 权限：运行用户需加入 `libvirt` 组（`sudo usermod -aG libvirt $USER`）。

### 6.1 任务 worker 运维

- 任务管理器单例（`tasks.NewManager`）：固定 4 worker、队列缓冲 128。**入队为有界等待**：`Submit` 先非阻塞尝试入队，队列满则最多等 `enqueueTimeout = 3s`；等满仍入不了即把任务置 `failed`、`error` 写「任务队列繁忙，请稍后重试」并打日志 `[tasks] 入队超时（队列已满）`。handler 仍按 202 + `{task_id}` 返回，前端首次轮询即拿到终态与中文原因。
  - 运维含义：`Submit` 最长阻塞 3 秒，不会为入队起额外协程（旧实现会随提交频率堆积无上限且永不退出的阻塞协程）。若日志频繁出现入队超时，说明并发提交量已超出 4 worker 的处理能力，应下调批量操作的并发度或上调 `workerCount`（需改代码常量）。
- **任务 panic 只失败当前任务，不影响进程**：executor 的 panic 由 `runExecutor` 兜住，`run` 顶层再兜一层（覆盖 DB/JSON 等 executor 之外的路径），任务置 `failed`、`error` 写「任务执行异常，请查看服务日志」。panic 值与完整调用栈**只进服务端日志**（`[tasks] executor panic ...` / `[tasks] worker panic ...`），不入库、不回显前端——排查时按任务 id 到日志里捞堆栈。
- worker 随进程退出即弃，无优雅关闭（`Manager` 无 `quit`/`Close`，生命周期与进程一致）；重启导致残留 `pending/running` 任务由启动收敛标 `failed`（“服务重启，未完成任务已终止，请重新提交”），executor 非幂等、不自动重跑，需人工重新提交。
- 任务记录仅终态（success/failed）可删，可经任务中心页批量清理，避免 `tasks` 表无限增长。
- 任务状态取值仍为 `pending / running / success / failed`。

### 6.2 会话清扫与启动收敛

- VNC 会话：websockify 解析 token 即刷新 `last_seen`；清扫器每 5 分钟将超 60 分钟无解析的 active VNC 会话标 `closed`（`Registry.StartSweeper` → `sweepOnce`，`vncStaleAfter=60min`）。单轮清扫自带 `recover`，一次异常只打日志、不终止定时循环；清扫不再持锁做数据库 IO（锁内取快照 → 锁外查库 → 回锁删除并二次确认），避免阻塞会话开启与关闭。
- SSH/串口会话：WS 关闭即回写 `ended_at`；进程重启导致 WS 丢失时，`main.go sweepStaleRecords` 将残留 active 的 ssh/serial 会话标 `closed`。
- 管理员强制断开：经 `Conn.CloseWithReason("管理员已断开连接")`，先在写锁内发关闭帧再关底层连接，浏览器侧能收到中文原因。
- VNC token TTL：内存 `TokenStore` 默认 5 分钟过期，一次性语义（同 VM 新 token 使旧 token 失效）。
- 排错提示：控制台相关的进程级崩溃在本轮已收敛（WS 写入统一经 `console.Conn` 串行化，三个转发协程各自 `recover`）。若日志出现 `[terminal] 输出转发 panic` / `[serial] 输出转发 panic` / `[console] 会话清扫 panic`，说明兜底生效但存在待修缺陷，按堆栈定位即可，服务不会退出。

### 6.3 VNC 链路检查清单

1. `pgrep -af websockify` 确认中转进程存活（不保活，掉线则控制台全不可用）。
2. token 解析地址 `GET /api/vnc/token/:token` 内网可达（websockify `--token-source` 指向）。
3. 端口冲突：旧 `vmops.pid` 可能陈旧，按 AGENTS.md 流程核对 `:8080` 实际 PID 后重启。

### 6.4 Prometheus + Grafana 监控栈

- 后端内建 exporter：`GET /metrics` 公开（Prometheus 每 15s 抓取；生产环境用防火墙限制来源，仅监控内网可达）。
- compose 一键起栈：prometheus（`deploy/prometheus.yml` + `deploy/alerts.yml` 5 条规则）+ grafana（预置数据源与 `deploy/grafana-dashboard.json` 9 面板看板）。
- app 容器直通宿主机 libvirtd socket（`/var/run/libvirt/libvirt-sock` 挂载），否则容器内采集为空；宿主机直跑后端时改 prometheus.yml targets 为宿主机 IP:8080。
- 告警规则：VM 运行数归零 / Host CPU>85% / 池可用<10% / 任务堆积>10 / 单 VM CPU>90%（阈值按规模调）。
- 看板：运行中 VM 数 / 宿主机 CPU / 任务堆积（stat）+ VM CPU/内存/磁盘 IO/网络 IO / 宿主机 / 存储池使用率（timeseries）。

### 6.5 监控栈运行形态（已全部容器化）

- 监控三件套**已从原生二进制（`~/monitor/`，已删除）全部迁移为 compose 容器**，勿再回退原生运行。
- 混合形态下 app 原生直跑，Prometheus 容器经 `host.docker.internal:8080`
  （compose `extra_hosts: host-gateway`）抓取；抓取目标若改回 `app:8080` 即为一键全容器形态。
- **Prometheus 2.x→3.x 迁移注意**：`--alertmanager.url` 参数在 2.x 起已移除（启动直接报
  unknown long flag），告警对接改在 prometheus.yml 的 `alerting:` 段配置。
- 产品「监控中心」页嵌 Grafana 的前提是容器 env 开启匿名只读 + `GF_SECURITY_ALLOW_EMBEDDING`
  （默认拒绝 iframe）；**勿用 -slim 镜像**（见第 3 节）。
- 注意：`/metrics` 已从审计中间件排除，否则 15s 一次抓取会淹没审计表。审计白名单当前为 `/static`、`/assets`（Vite 产物 js/css）、`/favicon.ico`、`/api/health`、`/metrics`，并额外跳过 SPA 路由回退（非 `/api` 路径且响应 `Content-Type` 为 `text/html`/`text/plain`）——否则用户每刷新一次页面都会多出一条审计。
- 注意：`/metrics` 公开无鉴权（Prometheus 抓取需要），生产环境须用防火墙限制来源，仅监控内网可达。

### 6.6 告警通知（Alertmanager）

- compose 内 `alertmanager`（:9093），prometheus 经 prometheus.yml 的 `alerting:` 段对接；规则见 `deploy/alerts.yml`。
- 默认 webhook 为占位地址（告警仅在 Alertmanager UI 可见 firing 状态）；生产替换为钉钉/飞书/企业微信机器人 webhook（`deploy/alertmanager.yml` 注释有示例）。

### 6.7 存储卷与增量克隆运维

- **克隆出来的虚拟机磁盘依赖源盘**：平台的克隆是增量克隆（子盘 qcow2 的 `backingStore` 指向源盘），子盘只存写入差异。因此**父盘不可删除、不可移动、不可改写**，否则 backing chain 断裂，所有子虚拟机磁盘立刻不可读且无法恢复。绕开平台直接 `virsh vol-delete` 或 `rm` 池内文件属高危操作。
- 排查一台虚拟机的磁盘依赖关系：`qemu-img info <盘>` 看 `backing file:` 指向谁；`virsh vol-dumpxml <卷> --pool <池>` 看 `<backingStore>`；`qemu-img check <盘>` 确认镜像结构完好。
- **平台删除虚拟机时会刻意保留部分卷**，三种情况：① 卷不在该存储池路径下（如挂载的宿主机 ISO）；② 卷是镜像库登记的共享基镜像（「基于云镜像创建」是直接引用不拷贝）；③ 卷仍被其他子卷当作 backing file（增量克隆父盘）。
  - 观察方式有两处：任务详情的 `kept_volumes` 字段（形如 `web-base.qcow2（是增量克隆父盘，仍被 2 个子卷依赖（web-c1.qcow2、web-c2.qcow2））`），以及服务端日志 `[tasks] 保留卷（未删）vm=.. vol=.. 原因=..`。任务进度文案也会变成「磁盘清理完成（保留 N 个共享卷）」。
  - 这是**预期行为，不是删除失败**。任务仍为 `success`，虚拟机定义与数据库记录都已删除。
- **孤儿卷可用「清理孤儿卷」一键处理（发布闭环新增）**：存储池页每个池的操作列提供「清理孤儿卷」
  按钮（admin），先经 volume-refs 接口列出零引用卷候选，确认后提交 `cleanup_volumes` 后台任务。
  任务判定与删卷守卫同一套数据反向使用：不被虚拟机挂载、未登记镜像库、也非任何子卷 backing 父盘的卷才删除；
  任一命中引用则保留并记录原因。任务结果含 `pool/deleted/kept` 明细（见 task-contract.md）。
  设计取舍不变：宁可漏删占空间，不可错删在用磁盘——清理入口复用了守卫的全部引用判定。
- 删卷失败不再静默：若日志出现 `[tasks] 删除卷失败 vm=.. pool=.. vol=.. err=..`，多为权限或卷被占用，按 err 定位；此时文件可能残留，需按上一条流程人工确认后清理。

## 7. 备份与升级

- mysqldump 备份、qcow2 磁盘备份。
- **qcow2 备份注意 backing chain**：增量克隆的子盘单独拷走是**不可用**的（它只含差异数据，缺了父盘无法读）。要么连父盘一起备份，要么先 `qemu-img convert -O qcow2 <子盘> <独立盘>` 把 chain 压平成完整镜像再备份。
