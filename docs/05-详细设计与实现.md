## 1. 项目结构

目录树：`main.go / config / database / handler / middleware / model / service/virt / service/tasks / service/console / service/vnc / web / static / docs`。

分层说明：handler 直连 GORM；虚拟化操作下沉至 `service/virt` 封装层（go-libvirt 直连 `qemu:///system`）；耗时操作委托 `service/tasks` 后台执行；控制台连接由 `service/console` 注册表跟踪。所有 libvirt 调用走 `service/virt`，错误用 `%w` 包装并注明 virsh 等价命令。

## 2. 认证与授权模块（含 RBAC 只读角色）

- 登录流程：bcrypt 校验 + JWT 签发（`handler/auth.go`，`middleware.GenerateToken`）。
- JWT 中间件：`AuthMiddleware`（`middleware/jwt.go`），支持 `Authorization` 头与 WS `?token=` 查询参数；校验用户存在与 `is_active`。
- Token 解析：`ParseToken` 以 `jwt.WithValidMethods([]string{"HS256"})` 锁定签名算法。若不锁定，攻击者可改写 header 的 `alg` 让库走不同的验签路径（算法混淆攻击）；本平台只签发 HS256，故显式限定为单一算法。
- 中间件错误响应：统一经包内 `abortJSON` 输出 `{code, message, data}`（原先返回 `{"error": "..."}`，与全站契约不一致）。此处**不能**复用 `handler.Fail`——`handler` 包已依赖 `middleware`（`HashPassword`、`GenerateToken`），反向引用会构成导入环，故在 `middleware` 包内单独提供同格式助手。
- 角色中间件：`AdminMiddleware`（仅 `admin`）与 `OperatorMiddleware`（RBAC 第一阶段：只读 viewer）。
  - 关键函数：`middleware/jwt.go` 的 `OperatorMiddleware()`、`isVNCTokenPath()`、`isGuestWriteChannel()`。
  - 规则：admin 放行全部；viewer 放行 GET 与 `POST /api/vms/:id/vnc-token`（图形控制台观看）；**GET 中的 `/terminal` 与 `/serial` 例外拒绝**；其余 POST/PUT/DELETE 一律 403。
  - 类型断言带 `ok`：上下文中的 `role` 类型不符时按无权限处理，不能 panic 掉整条请求链。
  - 路由装配（`main.go`）：`/users`、`/audit`、`/settings` 用 `AdminMiddleware`；`/hosts`、`/vms`、`/storage`、`/networks`、`/images`、`/dashboard`、`/tasks`、`/sessions` 用 `OperatorMiddleware`。
- **为什么不能只按 HTTP 方法判定读写**：浏览器发起 WebSocket 连接时只能使用 GET，因此 SSH 终端与串口控制台在协议层是 GET，实质上却是对客户机的双向写入通道——`/terminal` 建立完整 SSH shell，`/serial` 直连虚拟机串口（多数云镜像上即 root TTY）。二者若按 GET 放行，只读角色便可绕过 RBAC 取得客户机内的任意写权限。`isGuestWriteChannel` 按 `c.FullPath()` 后缀识别这两条路径并对 viewer 返回 403，文案为「只读角色不能使用 SSH 终端与串口控制台，请使用图形控制台查看」。
- **图形控制台的只读实现**：VNC（RFB）协议本身没有只读模式，服务端无法单向裁剪输入通道，键鼠必须在客户端关闭。故 `VNCHandler.RequestToken` 在响应中增加 `view_only` 布尔字段（`role != "admin"` 即为 `true`），前端据此追加 noVNC 的 `&view_only=1` 参数并在顶栏显示「只读观看（键鼠已禁用）」标签。
- 角色×资源×读写矩阵：

| 资源组 | GET（读） | POST/PUT/DELETE（写） |
|---|---|---|
| `/hosts`、`/vms`、`/storage`、`/networks`、`/images`、`/dashboard`、`/tasks`、`/sessions` | admin ✓ / viewer ✓ | admin ✓ / viewer ✗（403） |
| `POST /api/vms/:id/vnc-token` | —（viewer ✓，图形观看，`view_only=true`） | viewer ✓（仅此例外） |
| `GET /api/vms/:id/terminal`、`GET /api/vms/:id/serial` | admin ✓ / **viewer ✗（403）** | — |
| `/users`、`/audit`、`/settings` | admin ✓ / viewer ✗ | admin ✓ / viewer ✗ |
| 前端路由 | `vms/new`、`settings`、`audit` 标 `requiresAdmin`，viewer 直输 URL 重定向 dashboard（`web/src/router/index.js`） | — |

- 前端边界（`ConsolePage.vue`）：viewer 不渲染 SSH / 串口的侧栏入口与选择卡（`v-if="isAdmin"`），选择页追加一条黄色说明条，`select()` 内另有兜底提示；「运行中自动尝试串口」的智能默认仅对 admin 生效。
- 修改密码：`PUT /api/users/me/password`（所有角色，需校验旧密码，新密码≥6 位且与旧不同，bcrypt 落库；`handler/user.go ChangeMyPassword`）。前端右上角用户名旁入口，改完强制重新登录验证。

## 3. 宿主机管理模块

- CRUD 接口实现；删除前检查关联 VM。
- 连通性测试（ping 取延迟），连通成功回写 `hosts.status=reachable`（失败置 `unreachable`），列表不再 unknown。
- `ssh_ip` 入库校验（`validateSSHIP`）：优先按 IP 解析，非 IP 时退回保守主机名白名单（`^[a-zA-Z0-9]([a-zA-Z0-9.-]*[a-zA-Z0-9])?$`，长度 ≤253），创建与更新两处入口都校验。动机是该值会作为 argv 直接传给 `exec.Command("ping", ..., host.SSHIP)`：以连字符开头的串（如 `-f`）会被 ping 当成选项解析（flood ping），必须拦在写库入口而非调用处。
- 实时状态采集（`handler/host.go GetHostStats`）：hostname/uname 取系统信息，内存读 `/proc/meminfo`（与 dashboard 同源，不依赖 free 文本解析），运行时长读 `/proc/uptime` 转中文（X 天 X 小时 X 分钟）。
- 关键代码要点：`handler/host.go`（`validateSSHIP/readHostMeminfo/formatBytes/readHostUptimeSec/formatUptimeCN`）。

## 4. 虚拟机生命周期模块（核心）

- 列表/详情（go-libvirt 状态同步：ListAllDomains + DomainGetState）。
- 创建：生成 UUID/MAC → DB 写入 → **存储池建卷（StorageVolCreateXML，qcow2）** → DomainDefineXML → 失败回滚。当前创建/删除/克隆/优雅关机已转异步任务（见 6.5），同步语义保留在 executor 内。
- 启停/重启/删除（DomainCreate / Shutdown+Destroy / Reboot / Undefine+存储卷删除）。
- 建盘走 libvirt 存储池/卷 API（对应 virsh vol-create-as），支持多存储池选择（默认 vmops）。
- 停止策略：优雅关机 + 轮询（15s）超时强制断电（已搬入 `execStopVM` 后台执行，根治 axios 超时）。
- 删除策略：运行中先 Destroy 再 Undefine，再删存储卷；删除前先取完整磁盘清单再删定义，且**每个卷在删除前须通过三重守卫**（池外文件 / 镜像库登记的共享基镜像 / 仍被子卷当作 backing file 的增量克隆父盘），命中即保留并回传中文原因（见 6.7.3）。
- domain XML 模板、名称校验、随机 MAC/UUID。
- 存量 VM 导入/纳管：扫描 libvirt 全部域（ListDomainsWithDetail，解析 XML 取 vCPU/内存/MAC/磁盘路径），与 DB UUID 比对筛出未纳管域，勾选导入只写 DB、不改 libvirt；磁盘归属按存储池路径前缀推断。
- 关键代码要点：`handler/vm.go`、`service/virt/domain.go`、`service/virt/storage.go`、`service/virt/import.go`、`service/tasks/vm_tasks.go`。

## 5. 镜像管理模块

- 上传（流式写入 + 安全文件名 + 目录穿越防护），增加 form 字段 `pool`（默认 `img`），上传为池卷 + DB 记录。
- 列表/详情（`is_template` 筛选：`GET /api/images?is_template=true`）、模板标记（`PUT /api/images/:id/template` 改写 `Image.IsTemplate`，创建向导云镜像选项即取模板）、删除（软删除 + 清理文件）。
- 基于镜像创建 VM（`POST /api/images/:id/clone`）已转异步 `clone_image_vm` 任务，底层为增量克隆（见 6.7）。
- 需注意「基于云镜像创建」（`POST /api/vms` 带 `disks[].source_image_id`）与上者不同：前者是**直接引用镜像文件、不拷贝**（`execCreateVM` 的 `source_image_id` 分支只把 `img.Path` 填进磁盘 source），因此镜像文件同时被镜像库与该 VM 共用，删 VM 时必须由守卫拦住（见 6.7.3）。
- 关键代码要点：`handler/image.go`。

## 6.1 存储池管理模块

- 池列表（状态/容量/分配/路径）、池详情（卷列表）。
- 新建目录型存储池（StoragePoolDefineXML + Create + autostart）、删除（destroy + undefine）。
- 卷创建（StorageVolCreateXML）/ 删除。
- 建盘走存储卷 API（VM 创建时在所选池建卷）。
- 入参校验（`handler/storage.go`）：
  - `validPoolPath`：目录池的 `path` 决定该池所有卷的落盘位置，要求绝对路径 + 字符白名单 `^/[a-zA-Z0-9_./-]+$` + 规范写法（`filepath.Clean(p) == p`，借此拒绝 `..`、`//` 与结尾斜杠）+ 不得为根目录本身。违反返回 400「存储池路径必须是规范的绝对路径（不含 ..、结尾斜杠），且不能是根目录」。
  - `validVolFormat`：卷格式白名单仅 `qcow2` / `raw`（与前端下拉一致），空值保持原行为（virt 层默认 qcow2）。违反返回 400「卷格式只支持 qcow2 或 raw」。
  - `validVolName`：卷/池名允许字母数字下划线连字符和点（卷名含扩展名）。
- XML 生成（`service/virt/storage.go`）：`buildVolumeXML`（`volumeXML`）与 `buildDirPoolXML`（`poolXML`）经 `encoding/xml` 序列化，固定取值用命名常量（`volUnitGiB`/`volUnitByte`/`volFormatQcow2`/`poolTypeDir`）。与接口层白名单构成纵深防御：接口层限制取值域，序列化层保证元字符无害。增量克隆另走 `buildVolumeXMLWithBacking`（多一个 `<backingStore>` 子节点，`buildVolumeXML` 即其 `backingPath=""` 的薄封装，见 6.7）。
- backing 依赖枚举（`ListBackingRefs(poolName) (map[string][]string, error)`）：遍历池内所有卷的 `vol-dumpxml`，解析 `<backingStore><path>`，返回「父卷路径 → 依赖它的子卷名列表」。查询前若池 active 则先 `StoragePoolRefresh`（保证直接落盘的文件也在卷列表里）。这是删卷父盘守卫的数据来源（见 6.7.3）。
- 关键代码要点：`service/virt/storage.go`、`handler/storage.go`。

## 6.2 网络管理模块

- 网络列表（网桥/转发/网关）、详情（XML）。
- 网络启停 / 删除（运行中先 destroy 再 undefine）。
- 创建 NAT 网络（模板）/ 从 XML 定义；网络编辑（停→undefine→define→启，对应 `UpdateNetwork`）。
- 入参校验（`handler/network.go`）：网络名限字母数字下划线连字符；`gateway` 非空时须为规范写法的合法 IPv4（`validIPv4` 额外要求 `ip.String() == 输入`，借此排除 IPv6 与 `::ffff:1.2.3.4` 之类映射写法），违反返回 400「网关必须是合法的 IPv4 地址」；留空仍走 virt 层默认网关 `192.168.100.1`。
- XML 生成（`service/virt/network.go`）：`NetworkXMLFromParams` 改由 `networkXML`/`netForwardXML`/`netBridgeXML`/`netIPXML`/`netDhcpXML` 结构体 `xml.Marshal` 生成，NAT 模板固定取值用命名常量（`natForwardMode`/`natPortStart`/`natPortEnd`/`natNetmask`/`natDefaultGW`/`bridgeSTP`/`bridgeDelay`）。函数签名仍返回 `string`：结构体只含字符串与整数字段，`Marshal` 不会失败，兜底返回空串由 `DefineNetwork` 报「定义网络失败」，绝不产出半截 XML。
- 说明：`POST /api/networks/xml` 与 `PUT /api/networks/:name` 仍接受调用方原始 XML 直接定义（仅 admin 可达，viewer 被 403 拦住），尚未做结构校验。
- 关键代码要点：`service/virt/network.go`、`handler/network.go`。

## 6.3 网页控制台模块（noVNC + Web 终端 + 串口）

- 后端：VM VNC 端口解析（DomainGetXMLDesc graphics port，对应 `virsh dumpxml`）+ token 生成（`VNCHandler.RequestToken`，`POST /api/vms/:id/vnc-token`），响应含 `view_only`（`role != "admin"` 即 `true`）。
- websockify：JSONTokenApi 动态解析 token → host:port（`VNCHandler.ResolveToken`，`GET /api/vnc/token/:token`，解析即经 `TouchByToken` 刷新会话存活）。该接口的 `{"host","port"}` / 404 `{"error"}` 是 websockify 规定的**外部契约**，不走全站统一响应，亦不得改动。
- Web 终端：WebSocket→SSH 桥（x/crypto/ssh），首个消息携带连接参数，xterm.js 前端（`handler/terminal.go` 的 `Connect`，`GET /api/vms/:id/terminal`）。**仅 admin 可用**。
- 串口 Console：libvirt `DomainOpenConsoleBidirectional`（`service/virt/console.go`），禁止直接打开 `/dev/pts/*`；`GET /api/vms/:id/serial`。**仅 admin 可用**。
- **SSH 目标白名单（`validateSSHTarget`）**：首帧 `auth` 的 `host`/`port`/`user`/`password` 全部来自浏览器，原实现零校验，配合 RBAC 对 GET 的放行，任何登录用户都能驱动服务器向任意地址发起 SSH 连接——平台等于免费的跳板机、内网端口扫描器与口令爆破器。现按约束由强到弱收敛：① 端口须在 1-65535；② 平台已记录该 VM 的 IP（`vms.ip` 非空）时目标必须与之精确一致；③ 未记录 IP（无 guest agent 时的常态）时只接受 RFC1918 私有网段的 IP 字面量，并排除环回（否则可 SSH 进宿主机自身）、未指定、链路本地（含云元数据地址 169.254.169.254）与组播，且不接受主机名（避免 DNS 解析到公网与 DNS rebinding 绕过）。拒绝原因经 WS 错误帧回中文，拨号前后写服务端日志（含 vm/target/user/来源 IP，不记口令）。`HostKeyCallback` 显式为 `ssh.InsecureIgnoreHostKey()`：目标是平台自建的短生命周期 VM，IP 由 DHCP 动态分配、重建即换主机密钥，维护 known_hosts 不具可操作性，中间人风险由目标白名单收敛。
- **WS 写入串行化（`console.Conn`）**：SSH 桥与串口桥的所有写入经 `console.NewConn(rawConn)` 包装（详见 6.10）。
- 前端：VM 列表「控制台」→ 站内选择页（图形控制台 noVNC 内嵌 / Web 终端 SSH / 串口）；**viewer 只渲染图形控制台入口**，选择页追加只读说明条，VNC 连上后顶栏显示「只读观看（键鼠已禁用）」。
- 会话收敛：三链路建会话记录，SSH/串口可强制断开，VNC 靠过期清扫收敛（详见 6.6）。
- 关键代码要点：`service/vnc/token.go`（`TokenStore/Generate/Lookup`）、`handler/vnc.go`、`handler/terminal.go`（`Connect/validateSSHTarget`）、`handler/serial.go`（`ConnectSerial/vmNameByID`）、`service/console/conn.go`、`web/src/views/ConsolePage.vue`。
- 控制台体验优化（`ConsolePage.vue`）：VNC 未运行时页内一键开机并轮询至 running 自动连接（闭环，不跳走）；SSH 连接参数记忆（localStorage 按 VM 存 host/port/user，密码永不落盘，连通成功才记）；VNC iframe 加载遮罩（15s 兜底）+ 新窗口打开。

## 6.5 异步任务子系统

设计思路：同步 `StopVM` 轮询 15s 会撞上 axios 超时，大盘创建/克隆同样慢。参考 JumpServer/PVE 的 task 队列语义，将五个耗时操作后台化：handler 只做基础参数校验后 `Submit` 入库并返回 `202 + {task_id}`，固定 worker 池执行并回写进度，前端 `pollTask` 轮询至终态。

关键接口与函数（均与代码逐字一致）：

| 层次 | 函数/接口 | 说明 |
|---|---|---|
| 模型 | `model.Task`（表 `tasks`） | `type/title/status/progress/payload/result/error/user_id/username/vm_id/vm_name` |
| 队列 | `tasks.NewManager(db)`（`service/tasks/manager.go`） | 内部 `virt.New()`，起 4 个 worker goroutine（`workerCount=4`，`queueBufferSize=128`）；`Manager` 生命周期与进程一致，不提供单独关闭入口 |
| 队列 | `Manager.Register(taskType, fn)` | 启动时注册 executor |
| 队列 | `Manager.Submit(taskType, title, payload, userID, username, vmName, vmID)` | 序列化 payload、置 `pending` 入库后交 `enqueue` |
| 队列 | `Manager.enqueue(task)` | **有界入队**：先非阻塞尝试；队列满则用单个 `time.NewTimer(enqueueTimeout=3s)` 等待，超时置 `failed` + `Error="任务队列繁忙，请稍后重试"` 并同步回写返回给 handler 的 task |
| 队列 | `Manager.Get(id)` / `Manager.List(limit, status)` | 单查 / 按 id 倒序（默认 50、上限 200） |
| 容错 | `runExecutor(fn, ctx)` / `run(id)` 顶层 `defer` / `markFailed(id, msg)` | 三处 recover：executor panic、executor 之外的裸奔点（DB/JSON）、落库自身；panic 值与 `debug.Stack()` 只进日志，`Task.Error` 只存中文文案「任务执行异常，请查看服务日志」 |
| 执行 | `ExecContext`（`DB/Virt/Task/Payload/Report`）、`Executor`、`ProgressFunc` | executor 禁止引用 gin/handler，错误用中文 `%w` 包装 |
| 执行 | `RegisterVMTasks(m)`（`service/tasks/vm_tasks.go`） | 注册 `create_vm / delete_vm / clone_vm / clone_image_vm / stop_vm` |
| 执行 | `execCreateVM` | 搬运自 `CreateVM`：校验名称→查宿主→默认值→UUID/MAC→逐盘落地（Report 10/30/50/70）→seed→`BuildDomainXML`→写 DB→`DefineDomain`；成功回填 `Result={"vm_id"}`；失败清理已建卷与 seed |
| 执行 | `execDeleteVM` | 搬运自 `DeleteVM`：取磁盘清单→`UndefineDomain`→逐卷清理（每卷先过 `shouldKeepVol` 三重守卫）+seed→软删除；被保留的卷进 `Result.kept_volumes`；对应 `virsh undefine + vol-delete` |
| 执行 | `execCloneVM` | 搬运自 `CloneVM`：`GetDomainSpec`→覆盖→`CloneVMFromSpec`（内部重生成 UUID 与全部网卡 MAC）→回读新域 UUID/MAC 同步 DB→写 DB；对应 `qemu-img create -b + virsh define` |
| 执行 | `execCloneImageVM` | 搬运自镜像 `CloneVM`：`LookupVolByPath`→`CloneVolumeFromVol`→seed→define→DB；云镜像增量克隆 |
| 执行 | `execStopVM` | 搬运自 `StopVM`：`ShutdownDomain`→15s 轮询（每秒 Report）→超时 `DestroyDomain`→DB 置 `shut off`；对应 `virsh shutdown / destroy` |
| REST | `POST /api/vms`、`DELETE /api/vms/:id`、`POST /api/vms/:id/clone`、`POST /api/images/:id/clone`、`POST /api/vms/:id/stop` | 改异步，202 返回 `{task_id}` |
| REST | `TaskHandler.ListTasks/GetTask/DeleteTask`（`handler/task.go`） | `GET /api/tasks?status=&limit=` 返回 `{total, items}`；`GET /api/tasks/:id`；`DELETE /api/tasks/:id` 仅终态可删 |
| 前端 | `web/src/utils/task.js`（`pollTask`）、`TaskList.vue` | `pollTask(taskId, {interval=2000, timeout=300000})` 轮询至 success resolve / failed reject；任务中心智能轮询（有进行中才刷）+ 清理已完成 |

virsh 等价：创建 `vol-create-as + define`；删除 `undefine + vol-delete`；克隆 `vol-create（含 backingStore）+ define`；停止 `shutdown（超时 destroy）`。未指定存储池时统一取包内常量 `defaultStoragePool = "vmops"`（与 `model.VM.StoragePool` 的 gorm 默认值一致）。

**入队策略的取舍**：队列满时有三种可选做法——丢任务、无上限地起协程等待、由调用方有界等待。
原实现取第二种（`go func(){ m.queue <- id }()`），协程数量随提交频率增长且永不退出，属隐性资源泄漏。
现取第三种：等待发生在 handler 自己的请求协程上（该协程本就存在，且由服务器连接数天然限流），
协程数量零增长，并能把背压如实传回客户端；代价是队列满时 `Submit` 最多阻塞 3 秒
（`enqueueTimeout`）。超时后任务落库置 `failed`，同时回写返回给 handler 的 task 结构体，
避免前端拿到 `pending` 却永远等不到执行。handler 仍按 202 + `{task_id}` 返回，前端首次轮询即
取得终态与中文原因。

**panic 兜底的必要性**：Web 框架的 Recovery 中间件只包裹 HTTP 请求处理链，worker 是
`NewManager` 自行启动的 goroutine，其内部一次未处理的 panic 会直接终止整个进程——连带所有
在途任务与全部控制台会话。故按「executor → worker → 落库」三层各自 recover，且严格区分
可见性：panic 值与调用栈只进服务端日志，写入 `Task.Error` 的一律是中文友好文案（该字段会回显前端）。
同理 `friendlyError` 会丢弃原始错误链（无中文时降级为「操作失败」），因此 `run` 必须先把完整
错误打进日志再落库，否则任务失败后无从排查。状态机取值仍为 `pending/running/success/failed`，未变。

## 6.7 增量克隆（linked clone）与删除保护

设计目标：PVE 式增量克隆——子卷只保存写入差异，基础数据仍读父盘，因此建盘瞬时完成、初始几乎不占
空间。VM 克隆与镜像建机共用同一原语。本节同时记录一次**「文档声称的功能其实并未实现」**的发现与
修复，这是本轮工作中最值得写入论文的一段。

### 6.7.1 一次实现层面的更正：`vol-clone` 并不产生 backing file

原实现的 `CloneVolumeFromVol` 调用 `StorageVolCreateXMLFrom`（等价 `virsh vol-clone`），函数注释
写着「libvirt 自动写 qcow2 backing file」，README 与本文档也据此把「增量克隆、子卷带 backing file、
保护基镜像」列为核心特性之一。

实测结论与上述描述相反：`StorageVolCreateXMLFrom` 做的是**全量数据拷贝**，产出的子卷**没有**
backing file。取证方式是两条外部命令——`virsh vol-clone` 出来的卷，`qemu-img info` 的输出中不存在
`backing file` 行，`virsh vol-dumpxml` 的输出中也不存在 `<backingStore>` 节点。也就是说，修复前的
「PVE 式增量克隆」「子卷带 backing file，保护基镜像」这些表述**全部不成立**：功能实际退化为「等价
容量的整盘复制」，只是因为拷贝也能正常开机、克隆结果表面可用，缺陷长期未被察觉。

修复方式是改用另一条 libvirt 路径：`StorageVolCreateXML` + 在卷 XML 内显式声明 backing 节点。

```xml
<volume>
  <name>web-clone-diskb.qcow2</name>
  <capacity unit="B">与父卷同虚拟容量</capacity>
  <target><format type="qcow2"/></target>
  <backingStore>
    <path>/var/lib/libvirt/images/web-base.qcow2</path>
    <format type="qcow2"/>
  </backingStore>
</volume>
```

该 XML 等价于 `qemu-img create -f qcow2 -F qcow2 -b <父盘> <子盘>`。序列化入口为
`service/virt/storage.go` 新增的 `buildVolumeXMLWithBacking(name, format, unit, capacity, backingPath)`
与结构体 `volBackingXML`；原 `buildVolumeXML` 退化为 `backingPath=""` 的薄封装，`volumeXML.BackingStore`
为指针加 `omitempty`，因此非克隆场景不会多出空节点，既有调用方无需改动。

修复后的验收仍以外部工具为准（三条命令全部通过）：

| 判据 | 命令 | 修复前 | 修复后 |
|---|---|---|---|
| 子卷有后备文件 | `qemu-img info <子盘>` | 无 `backing file` 行 | 有 `backing file:` 行，指向父盘 |
| libvirt 侧可见 | `virsh vol-dumpxml <子卷> --pool <池>` | 无 `<backingStore>` | 有 `<backingStore>` 节点 |
| 镜像结构完好 | `qemu-img check <子盘>` | —— | `No errors were found on the image` |

方法论上的收获：**平台层面「调用了哪个 API」不能证明功能语义成立，必须由该功能的外部可观测结果反
证。**「增量克隆」的唯一判据不是代码里写了什么，而是产出的 qcow2 文件里到底有没有 backing file。
本项目此后把这三条命令固定为该功能的验收方式（见 docs/06 §8）。

### 6.7.2 克隆机身份唯一性：UUID 与每块网卡的 MAC

`CloneVMFromSpec` 原以 `spec := *source` 派生克隆配置。Go 的结构体赋值是浅拷贝，切片字段只复制切片
头（指针 + 长度 + 容量），因此原实现对 `Disks` 做了显式深拷贝、却**漏了 `Interfaces`**：克隆机的网卡
配置与源机共享同一底层数组，MAC 也就原样沿用了源机。

这个缺陷的隐蔽性在于**没有任何报错**：libvirt 会拒绝 UUID 重复的域定义（所以 UUID 漏改会立刻暴露），
但对 MAC 不做唯一性校验——XML 里显式给了就照用。后果直到两台机器同时开机才出现：源机与克隆机在同一
网段持有相同 MAC，ARP 表错乱，两台的网络双双不可用。`service/tasks/vm_tasks.go` 的 `execCloneVM` 里
还有一句与之呼应的错误注释「首个网卡 MAC 从 libvirt 查询（克隆后重新生成）」，同样已更正——libvirt
不会自动改 MAC，重新生成是平台自己的责任，该处只是把结果回读同步进数据库。

修复后的实现把「派生克隆配置」抽为**不依赖 libvirt 连接的纯函数**，目的正是让它可被单元测试断言：

| 函数（`service/virt/clone.go`） | 职责 |
|---|---|
| `randomMACAddr() (string, error)` | 生成 `52:54:00:xx:xx:xx` 随机 MAC。前缀取 KVM/QEMU 保留段，避免撞上物理网卡厂商 OUI；与 `service/tasks` 的 `randomMAC` 保持同一前缀 |
| `systemDiskIndex(source) int` | 定位首个 `device=='disk'` 的磁盘下标（**跳过 cdrom**，光驱不能作 linked clone 父盘），无则返回 -1 |
| `buildCloneSpec(source, newName, diskIdx, newDiskPath, srcDiskPath) (*DomainSpec, error)` | 纯函数：深拷贝 `Disks` 与 `Interfaces`、改名、重新生成 UUID、**逐块网卡重新生成 MAC**、清空 `RawXML`（克隆后 XML 由 `BuildDomainXML` 重建，dumpxml 原文不再适用） |

实测：源机 `52:54:00:7a:ad:94` → 克隆机 `52:54:00:6d:f2:b1`，数据库记录与 libvirt 侧一致。相关单元
测试 8 例见 docs/06 §4.2，其中「两块网卡的 MAC 都必须与源机不同、彼此不同、且不污染源 spec」是核心
用例。

### 6.7.3 删除保护：三重守卫与 `kept_volumes`

真正实现 backing chain 之后，删除虚拟机的破坏力随之上升：父盘一旦被删，chain 断裂，所有子虚拟机的
磁盘**立刻不可读且无法恢复**。而 `execDeleteVM` 原先只按「是否位于该存储池路径下」判断卷是否属于本
虚拟机，会误删两类共享文件：

| 误删对象 | 为什么会被误判 | 后果 |
|---|---|---|
| 增量克隆父盘 | 父盘与子盘同池同目录，路径前缀判定无法区分 | backing chain 断裂，全部子机磁盘不可读、不可恢复 |
| 镜像库登记的共享基镜像 | 「基于云镜像创建」是**直接引用不拷贝**（`execCreateVM` 的 `source_image_id` 分支），镜像与 VM 同池时按路径判定即被当成该 VM 的盘 | 镜像文件被删而 `images` 表记录仍在，留下悬挂记录，其他引用它的 VM 一并损坏 |

现由 `shouldKeepVol(src, volName) string` 统一判定，返回非空字符串即为「保留原因」，任一守卫命中即
跳过该卷：

| 序 | 守卫 | 判据 | 保留原因（逐字，会回传前端） |
|---|---|---|---|
| 1 | 池外文件 | `src` 不以 `<池路径>/` 开头 | `不在存储池 <池名> 路径下` |
| 2 | 共享基镜像 | `src` 命中 `images` 表登记的 `path` 集合 | `是镜像库登记的共享基镜像` |
| 3 | 增量克隆父盘 | `ListBackingRefs(pool)[src]` 非空 | `是增量克隆父盘，仍被 N 个子卷依赖（子卷名列表）` |

- 守卫二与守卫三的数据源分别是一次数据库查询与一次 `ListBackingRefs`，两者失败均**只打日志并降级**
  （跳过该守卫），不阻断删除流程——守卫的作用是减少破坏面，不应把删除变成必失败操作。
- 命中守卫时写服务端日志 `[tasks] 保留卷（未删）vm=.. vol=.. 原因=..`，并把 `"<卷名>（<原因>）"`
  追加进任务结果的 `kept_volumes` 数组（前端任务详情可见）。进度文案随之分叉为「磁盘清理完成
  （保留 N 个共享卷）」。
- 同批把 `DeleteVolume` 的错误从 `_ =` 丢弃改为打日志，避免删卷失败无声无息。

**已知取舍（如实记录）**：父盘守卫会导致「先删父机、再删子机」的操作顺序下，父盘文件残留在池里成为
**孤儿文件**（此时已没有任何域引用它）。这是刻意选择的取舍——一个垃圾文件可以事后清理，一块损坏的
在用磁盘不可恢复。孤儿卷清理入口列入后续工作（docs/08 §2.3）。

### 6.7.4 关键函数一览

| 函数 | 说明（外部等价命令） |
|---|---|
| `CloneVolumeFromVol(poolName, srcVolName, newVolName)` | 查池→查父卷→取父卷虚拟容量与绝对路径→`buildVolumeXMLWithBacking` 组 XML→`StorageVolCreateXML` 建增量子卷→返回子卷路径；等价 `qemu-img create -f qcow2 -F qcow2 -b <父盘> <子盘>` |

## 6.8 cloud-init seed

设计思路：创建 VM 时可选注入主机名、用户口令、SSH 公钥与静态网络。纯 Go 生成 iso9660 seed ISO（卷标 `cidata`，cloud-init 约定），落到独立 seed 目录（`SEED_DIR`，默认 `/home/jiuzhao/vmops/data/seed`，web 可写、qemu 可读，不依赖存储池目录权限），以只读 cdrom 挂载，引导顺序提至光驱优先。

## 6.10 WebSocket 写入串行化与后台协程容错

设计思路：本平台在 HTTP 请求链之外还有三类常驻或短生命周期的执行流，它们的异常不受 Web 框架
Recovery 中间件保护，一次未处理的 panic 会直接终止进程。其中最容易被忽视的是 WebSocket 的
并发写：所用库（gorilla/websocket）允许「一个读协程 + 一个写协程」并发，但**明确禁止多个协程
同时写**，违反即 panic（`concurrent write to websocket connection`）。

本平台控制台桥实际存在的写入方：

| 桥 | 写入方 | 数量 |
|---|---|---|
| SSH 桥（`handler/terminal.go`） | stdout 转发协程、stderr 转发协程、主读循环的错误帧 | 3 |
| 串口桥（`handler/serial.go`） | 客户机输出转发协程、错误帧 | 2 |
| 会话注册表（`registry.go Disconnect`） | 管理员强制断开时的 `CloseMessage` | 1 |

因此新增 `service/console/conn.go` 的 `Conn` 类型统一承担串行化：

| 成员 | 说明 |
|---|---|
| `NewConn(ws *websocket.Conn) *Conn` | 包装原始连接 |
| `WriteMessage(t int, data []byte)` / `WriteJSON(v any)` | 持写锁串行化写入；连接已关闭返回 `ErrConnClosed` |
| `ReadMessage()` | 直接转发；读侧由单一协程独占，不加锁 |
| `Close()` / `CloseWithReason(reason string)` | 幂等；`CloseWithReason` 先在写锁内尽力发送带中文原因的关闭帧再关底层连接 |
| `ErrConnClosed` | 哨兵错误，桥接协程据此退出转发循环 |

后台协程容错清单（全仓库原先 `recover()` 出现 0 次）：

| 协程 | 位置 | recover 后行为 |
|---|---|---|
| 任务 worker（4 个） | `tasks.runExecutor` / `tasks.run` / `tasks.markFailed` | 任务置 `failed` + 中文文案，worker 继续取下一个 |
| VNC 会话清扫器 | `console.Registry.sweepOnce` | 打日志，定时循环不中断 |
| SSH 输出转发 | `handler/terminal.go pipeOut` | 打日志退出该路转发 |
| 串口打开 | `handler/serial.go` | 打日志并向 `errCh` 投递 `ErrConnClosed`，避免主流程永久等待 |
| 串口输出转发 | `handler/serial.go` | 打日志退出该路转发 |

另修复读循环的控制流缺陷：`handler/terminal.go` 的输入分发原为 `switch` 内裸 `break`，
只跳出 `switch` 而非外层 `for`，stdin 写失败时循环不会退出；现改为带 `readLoop` 标签的 `break`。

## 6.11 安全加固

### 6.11.1 路径参数主键统一解析（防 SQL 注入）

新增 `handler/param.go`：

| 函数 | 说明 |
|---|---|
| `parseID(raw string) (uint, bool)` | 纯函数，不写 HTTP 响应；供 WebSocket 等需自定义错误通道的场景使用 |
| `paramID(c *gin.Context, name string) (uint, bool)` | 失败时已写好 400「ID 参数非法」并 `Abort`，调用方直接 `return` |

原理：GORM 的 `BuildCondition` 对「非纯数字字符串且未附带占位参数」的内联条件，会把该字符串
当作原始 SQL 片段直接拼进 `WHERE`。因此 `db.First(&vm, c.Param("id"))` 存在注入面，
而 `db.First(&vm, id)`（`id` 为 `uint`）走参数化。由于只读角色可访问全部读接口，
最低权限账号即可经由查询接口构造布尔盲注读取任意表（含 `users.password_hash`）。

改造范围共 39 处调用点：37 处普通处理器改用 `paramID`（`vm.go` 26、`host.go` 4、`image.go` 4、
`audit.go` 1、`user.go` 1、`vnc.go` 1），2 处 WebSocket 处理器改用 `parseID`
（`terminal.go`、`serial.go`；WS 已升级无法再写 JSON 响应，错误经 WS 帧
`{"type":"error","msg":"虚拟机 ID 非法"}` 回送）。串口处的 `vmNameByID` 形参类型随之由 `string` 改为 `uint`。

对外行为变化：`/api/vms/abc` 这类非法 ID 以前落到查询后返回 404「虚拟机不存在」，
现提前返回 400「ID 参数非法」；合法数字 ID 的状态码全部不变。

### 6.11.2 libvirt XML 生成改结构化序列化（防 XML 注入）

`service/virt/` 原有 5 处以 `fmt.Sprintf` 拼接 libvirt XML，外部可控字段中的 `"` 与 `>`
可闭合当前标签并注入额外节点（如把存储池的目标路径改写到任意目录）。现全部改为
`encoding/xml` 结构体 marshal，元字符由标准库自动转义：

| 函数 | 文件 | 序列化入口 |
|---|---|---|
| `CreateVolume` | `storage.go` | `buildVolumeXML`（`volumeXML`，unit=G） |
| `CreateVolumeCustom` | `storage.go` | `buildVolumeXML`（自定义 format） |
| `CreateDirPool` | `storage.go` | `buildDirPoolXML`（`poolXML`） |
| `CloneVolumeFromVol` | `clone.go` | `buildVolumeXMLWithBacking`（unit=B，与父卷等容量，含 `<backingStore>`） |
| `NetworkXMLFromParams` | `network.go` | `networkXML` + 5 个子结构体 |

该改造同时落实 AGENTS.md 的「XML 用标准库 encoding/xml」与「flag/固定取值用命名常量」两条标准。

### 6.11.3 JWT 算法锁定与生产密钥强校验

- `ParseToken` 增加 `jwt.WithValidMethods([]string{jwt.SigningMethodHS256.Alg()})`。不加此项时，
  攻击者可改写 header 的 `alg` 让库走不同的验签路径（算法混淆攻击）。
- 启动校验原判 `config.GlobalConfig.JWTSecretKey == ""`，而 config 包为该项兜了硬编码默认值
  `vmops-jwt-secret-key-change-in-production`，条件永不成立——该校验是**死代码**。现改为
  「空 **或** 等于内置默认值」即 `log.Fatalf` 拒绝启动，因为默认值随源码公开，任何人都能据此
  伪造管理员 token。

### 6.11.4 敏感信息与内存边界

- 种子账号的明文口令不再写入启动日志（改为只打用户名与角色，并提示默认口令见 README、
  首次登录后立即修改）；`initSeedData` 的 `Count`/`HashPassword`/`Create` 失败均打日志中止，
  不再写入空哈希造成账号静默不可登录。
- `middleware/audit.go` 删除把整个请求体 `io.ReadAll` 进内存却从未使用的死代码
  （多 GB 镜像上传会直接把进程内存打满）；`main.go` 显式设置 `r.MaxMultipartMemory = 32 << 20`，
  超阈值部分落磁盘临时文件。
- 审计白名单增加 `/assets`（Vite 产物 js/css，开一次页面即一批请求）与 `/favicon.ico`，
  并跳过 SPA 路由回退（非 `/api` 路径且响应 `Content-Type` 为 `text/html`/`text/plain` 时不写审计）。
- `AuditMiddleware` 与 `AdminMiddleware` 的上下文类型断言全部带 `ok`，类型不符时降级为匿名请求
  或按无权限处理，不再 panic 掉整条请求链。
- 内部错误泄漏的**最后一处**（`handler/vm.go` 的 `ImportVMs`）已收口：原先把 `fmt.Sprintf("%s: %v", name, err)`
  拼进响应的 `errors` 数组，会把 GORM/SQL 原文（表结构、约束名）带到前端；现改为完整错误经 `LogError`
  进服务端日志，响应只给「域名 + 写入数据库失败」。附带更正一处认知：该 `errors` 数组前端
  `VmList.vue` 实际并未消费（只读 `imported`/`skipped`/`failed` 三个计数），因此单台导入失败的具体
  原因目前不会呈现给用户——列为待改进项（见 6.11.5）。

### 6.11.5 残余风险（如实记录）

`POST /api/networks/xml`、`PUT /api/networks/:name`、`PUT /api/vms/:id/xml` 仍接受调用方原始 XML

## 6.12 工程一致性：状态字面量收口为常量

平台状态只有四个合法取值（`running` / `shut off` / `paused` / `error`），由 `virt.StateToPlatform`
从 libvirt 域状态枚举映射而来，并直接落进 `vms.status`、再由前端做颜色与文案映射。也就是说，同一批
字面量散落在三层（virt 封装层、业务层、前端），任何一处笔误都会造成状态显示错乱，且不会有编译错误。

本轮发现的实际不一致：`model/vm.go` 的 gorm 默认值写作 `shut_off`（**下划线**），而
`StateToPlatform` 返回的是 `shut off`（**空格**），前端亦按空格版本匹配。也就是说，一旦某条记录落到
列默认值，其状态在前端将无法匹配任何已知状态。修复与核查如下：

- 默认值改为 `shut off`，与映射函数及前端一致。gorm tag 内不能引用常量，故该字面量须与常量手工同步，
  代码注释已注明。
- 新增两套常量：`model.VMStatusRunning/VMStatusShutOff/VMStatusPaused/VMStatusError`（业务层）与
  `virt.StatusRunning/StatusShutOff/StatusPaused/StatusError`（封装层）；`StateToPlatform` 的
  `return` 与 `handler/vm.go` 的 8 处字面量改为引用常量。
- **刻意不让 virt 层 import model**：`model` 依赖 GORM，若 virt 反向引用会把 ORM 拖进最底层的 libvirt
  封装层并倒置分层依赖。因此两处各自定义、注释交叉引用，改一处必须同步另一处——这是「分层洁净」与
  「单一定义点」之间的取舍，选择了前者并用注释约束后者。
- 存量数据核查：数据库中**不存在** `shut_off` 的历史行（所有写入路径都显式给出状态值，从未落到列默认
  值）；另在沙箱中验证 GORM `AutoMigrate` 能够修改已有列的默认值，故后端下次重启即收敛，无需手工 DDL。
- 未完成部分如实记录：`service/tasks/vm_tasks.go` 仍有 5 处 `"shut off"` 字面量未替换（行为正确，属
  一致性隐患）。
