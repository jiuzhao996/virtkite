## 1. 项目结构

目录树：`main.go / config / database / handler / middleware / model / service/virt / service/tasks / service/console / service/vnc / web / static / docs`。

分层说明：handler 直连 GORM；虚拟化操作下沉至 `service/virt` 封装层（go-libvirt 直连 `qemu:///system`）；耗时操作委托 `service/tasks` 后台执行；控制台连接由 `service/console` 注册表跟踪。所有 libvirt 调用走 `service/virt`，错误用 `%w` 包装并注明 virsh 等价命令。

大文件按职责拆分（行为不变，便于定位与单测）：`handler/vm.go` 拆为 `vm / vm_devices / vm_import / vm_xml / vm_snapshot` 五文件；`service/tasks` 的 VM 任务拆为 `vm_tasks / vm_create / vm_delete / vm_clone` 四文件；`service/virt/spec.go` 拆为 `spec / spec_parse / spec_build` 三文件。

## 2. 认证与授权模块（含 RBAC 只读角色）

- 登录流程：bcrypt 校验 + JWT 签发（`handler/auth.go`，`middleware.GenerateToken`）。
- JWT 中间件：`AuthMiddleware`（`middleware/jwt.go`），支持 `Authorization` 头与 WS `?token=` 查询参数；校验用户存在与 `is_active`。
- Token 解析：`ParseToken` 以 `jwt.WithValidMethods([]string{"HS256"})` 锁定签名算法。若不锁定，攻击者可改写 header 的 `alg` 让库走不同的验签路径（算法混淆攻击）；本平台只签发 HS256，故显式限定为单一算法。
- 中间件错误响应：统一经包内 `abortJSON` 输出 `{code, message, data}`（原先返回 `{"error": "..."}`，与全站契约不一致）。此处**不能**复用 `handler.Fail`——`handler` 包已依赖 `middleware`（`HashPassword`、`GenerateToken`），反向引用会构成导入环，故在 `middleware` 包内单独提供同格式助手。
- 角色中间件（RBAC 三级角色 `admin / operator / viewer`）：`AdminMiddleware`（仅 `admin`）、`OperatorMiddleware`（三级权限主闸）与 `NonViewerMiddleware`（监控可见级别闸）。
  - 关键函数：`middleware/jwt.go` 的 `OperatorMiddleware()`、`NonViewerMiddleware()`、`isVNCTokenPath()`、`isGuestWriteChannel()`。
  - `OperatorMiddleware` 规则：**admin** 放行全部；**operator**（小组成员/学生）读全放，写仅限 `/api/vms` 前缀（虚拟机全生命周期，含 vnc-token；SSH 终端与串口是其职责内的操作通道，正常放行），其余模块（宿主机/存储/网络/镜像）的写操作一律 403「仅可操作虚拟机…」；**viewer**（检查者/教师）只读——放行 GET 与 `POST /api/vms/:id/vnc-token`（图形控制台观看），**GET 中的 `/terminal` 与 `/serial` 例外拒绝**，其余 POST/PUT/DELETE 一律 403。
  - `NonViewerMiddleware`：监控中心四端点（`/api/monitor/alerts`、`/api/monitor/alerts/history`、`/api/monitor/file-sd`、`/api/monitor/grafana-status`）仅 operator/admin 可达，viewer 一律 403——实时告警 labels 与 file-sd 会枚举全部 running VM 的名称与 IP，属资产敏感数据，不向只读角色暴露。
  - 类型断言带 `ok`：上下文中的 `role` 类型不符时按无权限处理，不能 panic 掉整条请求链。
  - 路由装配（`main.go`）：`/users`、`/audit`、`/settings` 用 `AdminMiddleware`；`/hosts`、`/vms`、`/storage`、`/networks`、`/images`、`/dashboard`、`/tasks`、`/sessions` 用 `OperatorMiddleware`；`/monitor` 用 `NonViewerMiddleware`。
- **为什么不能只按 HTTP 方法判定读写**：浏览器发起 WebSocket 连接时只能使用 GET，因此 SSH 终端与串口控制台在协议层是 GET，实质上却是对客户机的双向写入通道——`/terminal` 建立完整 SSH shell，`/serial` 直连虚拟机串口（多数云镜像上即 root TTY）。二者若按 GET 放行，只读角色便可绕过 RBAC 取得客户机内的任意写权限。`isGuestWriteChannel` 按 `c.FullPath()` 后缀识别这两条路径并对 viewer 返回 403，文案为「只读角色不能使用 SSH 终端与串口控制台，请使用图形控制台查看」。
- **图形控制台的只读实现**：VNC（RFB）协议本身没有只读模式，服务端无法单向裁剪输入通道，键鼠必须在客户端关闭。故 `VNCHandler.RequestToken` 在响应中增加 `view_only` 布尔字段（**仅 viewer 为 `true`**，operator 可操作控制台），前端据此追加 noVNC 的 `&view_only=1` 参数并在顶栏显示「只读观看（键鼠已禁用）」标签。
- **VM 资产授权（授权决定可见性）**：非 admin 用户对 VM 的可见/可操作范围另受 `vm_grants` 授权约束（未授权一律 404「查无此项」，admin 不受约束），详见 6.18。
- 角色×资源×读写矩阵：

| 资源组 | GET（读） | POST/PUT/DELETE（写） |
|---|---|---|
| `/vms`（VM 全生命周期） | admin ✓ / operator ✓ / viewer ✓ | admin ✓ / operator ✓ / viewer ✗（403） |
| `/hosts`、`/storage`、`/networks`、`/images`、`/dashboard`、`/tasks`、`/sessions` | admin ✓ / operator ✓ / viewer ✓ | admin ✓ / operator ✗（403） / viewer ✗（403） |
| `POST /api/vms/:id/vnc-token` | — | admin ✓ / operator ✓（`view_only=false`）/ viewer ✓（图形观看，`view_only=true`） |
| `GET /api/vms/:id/terminal`、`GET /api/vms/:id/serial` | admin ✓ / operator ✓ / **viewer ✗（403）** | — |
| `/monitor`（监控中心四端点） | admin ✓ / operator ✓ / **viewer ✗（403）** | — |
| `/users`、`/audit`、`/settings` | admin ✓ / operator ✗ / viewer ✗ | admin ✓ / operator ✗ / viewer ✗ |
| 前端路由 | `vms/new`、`settings`、`audit` 标 `requiresAdmin`，viewer 直输 URL 重定向 dashboard（`web/src/router/index.js`） | — |

- 前端边界（`ConsolePage.vue`）：viewer 不渲染 SSH / 串口的侧栏入口与选择卡（`v-if="isAdmin"`），选择页追加一条黄色说明条，`select()` 内另有兜底提示；「运行中自动尝试串口」的智能默认仅对 admin 生效。
- 修改密码：`PUT /api/users/me/password`（所有角色，需校验旧密码，新密码经动态密码策略校验（可配置最小长度，默认 8 位且≥8 时需含字母与数字，settings.password_min_length）且与旧不同，bcrypt 落库；`handler/user.go ChangeMyPassword`）。前端右上角用户名旁入口，改完强制重新登录验证。

## 3. 宿主机管理模块

- CRUD 接口实现；删除前检查关联 VM。
- 连通性测试（ping 取延迟），连通成功回写 `hosts.status=reachable`（失败置 `unreachable`），列表不再 unknown。
- `ssh_ip` 入库校验（`validateSSHIP`）：优先按 IP 解析，非 IP 时退回保守主机名白名单（`^[a-zA-Z0-9]([a-zA-Z0-9.-]*[a-zA-Z0-9])?$`，长度 ≤253），创建与更新两处入口都校验。动机是该值会作为 argv 直接传给 `exec.Command("ping", ..., host.SSHIP)`：以连字符开头的串（如 `-f`）会被 ping 当成选项解析（flood ping），必须拦在写库入口而非调用处。
- 实时状态采集（`handler/host.go GetHostStats`）：hostname/uname 取系统信息，内存读 `/proc/meminfo`（与 dashboard 同源，不依赖 free 文本解析），运行时长读 `/proc/uptime` 转中文（X 天 X 小时 X 分钟）。
- 关键代码要点：`handler/host.go`（`validateSSHIP/readHostMeminfo/formatBytes/readHostUptimeSec/formatUptimeCN`）。

## 4. 虚拟机生命周期模块（核心）

- 列表/详情（go-libvirt 状态同步：ListAllDomains + DomainGetState）。
- 创建：生成 UUID/MAC → DB 写入 → **存储池建卷（StorageVolCreateXML，qcow2）** → DomainDefineXML → 失败回滚。当前创建/删除/克隆/优雅关机已转异步任务（见 6.5），同步语义保留在 executor 内。
- 启停/重启/删除（DomainCreate / Shutdown+Destroy / Reboot / Undefine+存储卷删除）。
- 建盘走 libvirt 存储池/卷 API（对应 virsh vol-create-as），支持多存储池选择（默认 vmops）。
- 停止策略：优雅关机 + 轮询（15s）超时强制断电（已搬入 `execStopVM` 后台执行，根治 axios 超时）。
- 删除策略：运行中先 Destroy 再 Undefine，再删存储卷；删除前先取完整磁盘清单再删定义，且**每个卷在删除前须通过三重守卫**（池外文件 / 镜像库登记的共享基镜像 / 仍被子卷当作 backing file 的增量克隆父盘），命中即保留并回传中文原因（见 6.7.3）。
- domain XML 模板、名称校验、随机 MAC/UUID。
- 存量 VM 导入/纳管：扫描 libvirt 全部域（ListDomainsWithDetail，解析 XML 取 vCPU/内存/MAC/磁盘路径），与 DB UUID 比对筛出未纳管域，勾选导入只写 DB、不改 libvirt；磁盘归属按存储池路径前缀推断。
- IP 自动回填（`handler/vm_ip_sync.go`）：VM 列表/详情请求时惰性触发（全局 30s 节流、失败静默），**双通道**——先按 MAC 匹配 libvirt DHCP 租约（`virt.ListDHCPLeases`，对应 `virsh net-dhcp-leases`，多网络归并 + 过期过滤）；租约未命中且域已装 guest-agent 时改走 `virt.ListGuestIPs`（对应 `virsh domifaddr --source agent`，静态 IP 不进租约，QGA 是唯一自动途径）。
- 资产授权过滤：列表只返回「admin 或持有效 `vm_grants` 授权」的 VM，单 VM 接口（`findVM`）对非 admin 校验授权，未授权 404（见 6.18）。
- 关键代码要点：`handler/vm.go`、`handler/vm_ip_sync.go`、`service/virt/domain.go`、`service/virt/storage.go`、`service/virt/import.go`、`service/tasks/vm_tasks.go`。

## 5. 镜像管理模块

- 上传（流式写入 + 安全文件名 + 目录穿越防护），增加 form 字段 `pool`（默认 `img`），上传为池卷 + DB 记录。
- 既有池卷登记（`POST /api/images/register`）：把已存在于存储池的卷登记为云镜像（同路径已登记返回 409，软删记录可恢复），供「云镜像」方式直接引用。
- 列表/详情（`is_template` 筛选：`GET /api/images?is_template=true`）、模板标记（`PUT /api/images/:id/template` 改写 `Image.IsTemplate`，创建向导云镜像选项即取模板）、删除（软删除 + 清理文件）。前端镜像页为双 tab：「云镜像 / 模板盘」（登记+上传+模板标记）与「ISO 安装镜像」（只读展示，管理在存储池页）。
- 基于镜像创建 VM（`POST /api/images/:id/clone`）已转异步 `clone_image_vm` 任务，底层为增量克隆（见 6.7）。
- 需注意「基于云镜像创建」（`POST /api/vms` 带 `disks[].source_image_id`）与上者不同：前者是**直接引用镜像文件、不拷贝**（`execCreateVM` 的 `source_image_id` 分支只把 `img.Path` 填进磁盘 source），因此镜像文件同时被镜像库与该 VM 共用，删 VM 时必须由守卫拦住（见 6.7.3）。
- 关键代码要点：`handler/image.go`。

## 6.1 存储池管理模块

- 池列表（状态/容量/分配/路径）、池详情（卷列表）。
- 新建目录型存储池（StoragePoolDefineXML + Create + autostart）、删除（destroy + undefine）。
- 卷创建（StorageVolCreateXML）/ 删除。
- 建盘走存储卷 API（VM 创建时在所选池建卷）。
- 入参校验（`handler/storage.go`）：
  - `validPoolPath`：目录池的 `path` 决定该池所有卷的落盘位置，要求绝对路径 + 字符白名单 `^/[a-zA-Z0-9_./-]+$` + 规范写法（`filepath.Clean(p) == p`，借此拒绝 `..`、`//` 与结尾斜杠）+ 不得为根目录本身。违反返回 400「存储池路径必须是规范的绝对路径（不含 ..、结尾斜杠），且不能是根目录」。
  - `validVolFormat`：卷格式白名单仅 `qcow2` / `raw`（与前端下拉一致），空值保持原行为（virt 层默认 qcow2）。违反返回 400「卷格式只支持 qcow2 或 raw」。
  - `validVolName`：卷/池名允许字母数字下划线连字符和点（卷名含扩展名）。
- XML 生成（`service/virt/storage.go`）：`buildVolumeXML`（`volumeXML`）与 `buildDirPoolXML`（`poolXML`）经 `encoding/xml` 序列化，固定取值用命名常量（`volUnitGiB`/`volUnitByte`/`volFormatQcow2`/`poolTypeDir`）。与接口层白名单构成纵深防御：接口层限制取值域，序列化层保证元字符无害。增量克隆另走 `buildVolumeXMLWithBacking`（多一个 `<backingStore>` 子节点，`buildVolumeXML` 即其 `backingPath=""` 的薄封装，见 6.7）。
- backing 依赖枚举（`ListBackingRefs(poolName) (map[string][]string, error)`）：遍历池内所有卷的 `vol-dumpxml`，解析 `<backingStore><path>`，返回「父卷路径 → 依赖它的子卷名列表」。查询前若池 active 则先 `StoragePoolRefresh`（保证直接落盘的文件也在卷列表里）。这是删卷父盘守卫的数据来源（见 6.7.3）。
- 池角色与描述（`model.PoolMeta`，`PUT /api/storage/pools/:name/meta`）：libvirt 池 XML 没有 description/role 语义，平台侧用 `pool_meta` 表补充；`Role` 为空时按名称/路径自动推断（`handler.inferPoolRole`，base→模板基盘等）。
- 删卷守卫与引用预览：`DELETE .../volumes/:vol` 删除前计算该卷引用（`virt.ListAllDomainDiskSources` 域磁盘挂载 + `images.path` 精确匹配 + `ListBackingRefs` 子卷依赖），任一命中返回 **409** 与中文原因；`GET .../volume-refs` 池级一次算全，前端卷管理弹窗显示「在用」徽标、删卷确认带引用详情。与 `shouldKeepVol` 同一立场：宁可删不掉，不可损坏在用磁盘。
- 关键代码要点：`service/virt/storage.go`、`handler/storage.go`。

## 6.2 网络管理模块

- 网络列表（网桥/转发/网关）、详情（XML）。
- 网络启停 / 删除（运行中先 destroy 再 undefine）；自启动开关（`PUT /api/networks/:name/autostart`，virt 层 `SetNetworkAutostart`，前端卡片 el-switch 直切，对应 `virsh net-autostart on|off`）。
- 创建 NAT 网络（模板）/ 从 XML 定义；网络编辑（停→undefine→define→启，对应 `UpdateNetwork`）。
- 入参校验（`handler/network.go`）：网络名限字母数字下划线连字符；`gateway` 非空时须为规范写法的合法 IPv4（`validIPv4` 额外要求 `ip.String() == 输入`，借此排除 IPv6 与 `::ffff:1.2.3.4` 之类映射写法），违反返回 400「网关必须是合法的 IPv4 地址」；留空仍走 virt 层默认网关 `192.168.100.1`。
- XML 生成（`service/virt/network.go`）：`NetworkXMLFromParams` 改由 `networkXML`/`netForwardXML`/`netBridgeXML`/`netIPXML`/`netDhcpXML` 结构体 `xml.Marshal` 生成，NAT 模板固定取值用命名常量（`natForwardMode`/`natPortStart`/`natPortEnd`/`natNetmask`/`natDefaultGW`/`bridgeSTP`/`bridgeDelay`）。函数签名仍返回 `string`：结构体只含字符串与整数字段，`Marshal` 不会失败，兜底返回空串由 `DefineNetwork` 报「定义网络失败」，绝不产出半截 XML。
- 说明：`POST /api/networks/xml` 与 `PUT /api/networks/:name` 仍接受调用方原始 XML 直接定义（仅 admin 可达，viewer 被 403 拦住），尚未做结构校验。
- 关键代码要点：`service/virt/network.go`、`handler/network.go`。

## 6.3 网页控制台模块（noVNC + Web 终端 + 串口）

- 后端：VM VNC 端口解析（DomainGetXMLDesc graphics port，对应 `virsh dumpxml`）+ token 生成（`VNCHandler.RequestToken`，`POST /api/vms/:id/vnc-token`），响应含 `view_only`（仅 viewer 为 `true`）。
- websockify：JSONTokenApi 动态解析 token → host:port（`VNCHandler.ResolveToken`，`GET /api/vnc/token/:token`，解析即经 `TouchByToken` 刷新会话存活）。该接口的 `{"host","port"}` / 404 `{"error"}` 是 websockify 规定的**外部契约**，不走全站统一响应，亦不得改动。
- Web 终端：WebSocket→SSH 桥（x/crypto/ssh），首个消息携带连接参数，xterm.js 前端（`handler/terminal.go` 的 `Connect`，`GET /api/vms/:id/terminal`）。仅 admin / operator 可用（operator 的职责内操作通道，见 6.18 的授权约束）。
- 串口 Console：libvirt `DomainOpenConsoleBidirectional`（`service/virt/console.go`），禁止直接打开 `/dev/pts/*`；`GET /api/vms/:id/serial`。仅 admin / operator 可用。
- **SSH 目标白名单（`validateSSHTarget`）**：首帧 `auth` 的 `host`/`port`/`user`/`password` 全部来自浏览器，原实现零校验，配合 RBAC 对 GET 的放行，任何登录用户都能驱动服务器向任意地址发起 SSH 连接——平台等于免费的跳板机、内网端口扫描器与口令爆破器。现按约束由强到弱收敛：① 端口须在 1-65535；② 平台已记录该 VM 的 IP（`vms.ip` 非空）时目标必须与之精确一致；③ 未记录 IP（无 guest agent 时的常态）时只接受私有网段的 IP 字面量（IPv4 为 RFC1918 三段，IPv6 为 ULA `fd00::/8`，经 `net.IP.IsPrivate` 统一判定），并排除环回（否则可 SSH 进宿主机自身）、未指定、链路本地（含云元数据地址 169.254.169.254）与组播，且不接受主机名（避免 DNS 解析到公网与 DNS rebinding 绕过）。拒绝原因经 WS 错误帧回中文，拨号前后写服务端日志（含 vm/target/user/来源 IP，不记口令）。`HostKeyCallback` 原显式为 `ssh.InsecureIgnoreHostKey()`（中间人风险由目标白名单收敛）；v3.3 起两处 SSH 拨号全部改走 TOFU 主机密钥校验（首连记录 SHA256 指纹、指纹变化拒绝，见 11.3 与 docs/06 §6.13），该残余风险闭环。
- **WS 写入串行化（`console.Conn`）**：SSH 桥与串口桥的所有写入经 `console.NewConn(rawConn)` 包装（详见 6.10）。
- 前端：VM 列表「控制台」→ 站内选择页（图形控制台 noVNC 内嵌 / Web 终端 SSH / 串口）；**viewer 只渲染图形控制台入口**，选择页追加只读说明条，VNC 连上后顶栏显示「只读观看（键鼠已禁用）」。
- 会话收敛：三链路建会话记录，SSH/串口可强制断开，VNC 靠过期清扫收敛（详见 6.6）。
- 关键代码要点：`service/vnc/token.go`（`TokenStore/Generate/Lookup`）、`handler/vnc.go`、`handler/terminal.go`（`Connect/validateSSHTarget`）、`handler/serial.go`（`ConnectSerial/vmNameByID`）、`service/console/conn.go`、`web/src/views/ConsolePage.vue`。
- 控制台体验优化（`ConsolePage.vue`）：VNC 未运行时页内一键开机并轮询至 running 自动连接（闭环，不跳走）；SSH 连接参数记忆（localStorage 按 VM 存 host/port/user，密码永不落盘，连通成功才记）；VNC iframe 加载遮罩（15s 兜底）+ 新窗口打开。

## 6.5 异步任务子系统

设计思路：同步 `StopVM` 轮询 15s 会撞上 axios 超时，大盘创建/克隆同样慢。参考 JumpServer/PVE 的 task 队列语义，将六个耗时操作后台化（创建/删除/克隆/镜像建机/优雅关机/孤儿卷清理）：handler 只做基础参数校验后 `Submit` 入库并返回 `202 + {task_id}`，固定 worker 池执行并回写进度，前端 `pollTask` 轮询至终态。

关键接口与函数（均与代码逐字一致）：

| 层次 | 函数/接口 | 说明 |
|---|---|---|
| 模型 | `model.Task`（表 `tasks`） | `type/title/status/progress/payload/result/error/user_id/username/vm_id/vm_name` |
| 队列 | `tasks.NewManager(db)`（`service/tasks/manager.go`） | 内部 `virt.New()`，起 4 个 worker goroutine（`workerCount=4`，`queueBufferSize=128`）；`Manager` 生命周期与进程一致，不提供单独关闭入口 |
| 队列 | `Manager.Register(taskType, fn)` | 启动时注册 executor |
| 队列 | `Manager.Submit(taskType, title, payload, userID, username, vmName, vmID)` | 序列化 payload、置 `pending` 入库后交 `enqueue` |
| 队列 | `Manager.enqueue(task)` | **有界入队**：先非阻塞尝试；队列满则用单个 `time.NewTimer(enqueueTimeout=3s)` 等待，超时置 `failed` + `Error="任务队列繁忙，请稍后重试"` 并同步回写返回给 handler 的 task |

| 容错 | `runExecutor(fn, ctx)` / `run(id)` 顶层 `defer` / `markFailed(id, msg)` | 三处 recover：executor panic、executor 之外的裸奔点（DB/JSON）、落库自身；panic 值与 `debug.Stack()` 只进日志，`Task.Error` 只存中文文案「任务执行异常，请查看服务日志」 |

| 执行 | `execCloneImageVM` | 搬运自镜像 `CloneVM`：`LookupVolByPath`→`CloneVolumeFromVol`→seed→define→DB；云镜像增量克隆 |

virsh 等价：创建 `vol-create-as + define`；删除 `undefine + vol-delete`；克隆 `vol-create（含 backingStore）+ define`；停止 `shutdown（超时 destroy）`。未指定存储池时统一取包内常量 `defaultStoragePool = "vmops"`（与 `model.VM.StoragePool` 的 gorm 默认值一致）。

**入队策略的取舍**：队列满时有三种可选做法——丢任务、无上限地起协程等待、由调用方有界等待。
原实现取第二种（`go func(){ m.queue <- id }()`），协程数量随提交频率增长且永不退出，属隐性资源泄漏。
现取第三种：等待发生在 handler 自己的请求协程上（该协程本就存在，且由服务器连接数天然限流），
协程数量零增长，并能把背压如实传回客户端；代价是队列满时 `Submit` 最多阻塞 3 秒
（`enqueueTimeout`）。超时后任务落库置 `failed`，同时回写返回给 handler 的 task 结构体，
避免前端拿到 `pending` 却永远等不到执行。handler 仍按 202 + `{task_id}` 返回，前端首次轮询即
取得终态与中文原因。

**启动清扫（`sweepOrphanRunning`）**：任务队列只在内存中（channel），进程重启后数据库遗留的
`running`/`pending` 行永远不会被执行，不处理就是僵尸任务。`NewManager` 启动时把这些行统一置
`failed`，错误文案为「服务重启，任务已中断」（`main.go` 的 `sweepStaleRecords` 在启动流程更早处也做
同样收敛，并连带把 SSH/串口的 active 会话标 `closed`，两处文案不同属历史演进）。另外 manager 写入任务终态失败时会留下服务端日志，
不再静默丢弃——终态写不进去时，前端轮询只能靠任务列表页的状态修正兜底，日志是排查的唯一线索。

**panic 兜底的必要性**：Web 框架的 Recovery 中间件只包裹 HTTP 请求处理链，worker 是
`NewManager` 自行启动的 goroutine，其内部一次未处理的 panic 会直接终止整个进程——连带所有
在途任务与全部控制台会话。故按「executor → worker → 落库」三层各自 recover，且严格区分
可见性：panic 值与调用栈只进服务端日志，写入 `Task.Error` 的一律是中文友好文案（该字段会回显前端）。
同理 `friendlyError` 会丢弃原始错误链（无中文时降级为「操作失败」），因此 `run` 必须先把完整
错误打进日志再落库，否则任务失败后无从排查。状态机取值仍为 `pending/running/success/failed`，未变。

## 6.7 增量克隆（linked clone）与删除保护

设计目标：PVE 式增量克隆——子卷只保存写入差异，基础数据仍读父盘，因此建盘瞬时完成、初始几乎不占
空间。VM 克隆与镜像建机共用同一原语。本节同时记录一次**「文档声称的功能其实并未实现」**的发现与
修复，这是本轮工作中最值得写入论文的一段。

### 6.7.1 一次实现层面的更正：`vol-clone` 并不产生 backing file

原实现的 `CloneVolumeFromVol` 调用 `StorageVolCreateXMLFrom`（等价 `virsh vol-clone`），函数注释
写着「libvirt 自动写 qcow2 backing file」，README 与本文档也据此把「增量克隆、子卷带 backing file、
保护基镜像」列为核心特性之一。

实测结论与上述描述相反：`StorageVolCreateXMLFrom` 做的是**全量数据拷贝**，产出的子卷**没有**
backing file。取证方式是两条外部命令——`virsh vol-clone` 出来的卷，`qemu-img info` 的输出中不存在
`backing file` 行，`virsh vol-dumpxml` 的输出中也不存在 `<backingStore>` 节点。也就是说，修复前的
「PVE 式增量克隆」「子卷带 backing file，保护基镜像」这些表述**全部不成立**：功能实际退化为「等价
容量的整盘复制」，只是因为拷贝也能正常开机、克隆结果表面可用，缺陷长期未被察觉。

修复方式是改用另一条 libvirt 路径：`StorageVolCreateXML` + 在卷 XML 内显式声明 backing 节点。

```xml
<volume>
  <name>web-clone-diskb.qcow2</name>
  <capacity unit="B">与父卷同虚拟容量</capacity>
  <target><format type="qcow2"/></target>
  <backingStore>
    <path>/var/lib/libvirt/images/web-base.qcow2</path>
    <format type="qcow2"/>
  </backingStore>
</volume>
```

该 XML 等价于 `qemu-img create -f qcow2 -F qcow2 -b <父盘> <子盘>`。序列化入口为
`service/virt/storage.go` 新增的 `buildVolumeXMLWithBacking(name, format, unit, capacity, backingPath)`
与结构体 `volBackingXML`；原 `buildVolumeXML` 退化为 `backingPath=""` 的薄封装，`volumeXML.BackingStore`
为指针加 `omitempty`，因此非克隆场景不会多出空节点，既有调用方无需改动。

修复后的验收仍以外部工具为准（三条命令全部通过）：

| 判据 | 命令 | 修复前 | 修复后 |
|---|---|---|---|
| 子卷有后备文件 | `qemu-img info <子盘>` | 无 `backing file` 行 | 有 `backing file:` 行，指向父盘 |
| libvirt 侧可见 | `virsh vol-dumpxml <子卷> --pool <池>` | 无 `<backingStore>` | 有 `<backingStore>` 节点 |
| 镜像结构完好 | `qemu-img check <子盘>` | —— | `No errors were found on the image` |

方法论上的收获：**平台层面「调用了哪个 API」不能证明功能语义成立，必须由该功能的外部可观测结果反
证。**「增量克隆」的唯一判据不是代码里写了什么，而是产出的 qcow2 文件里到底有没有 backing file。
本项目此后把这三条命令固定为该功能的验收方式（见 docs/06 §8）。

### 6.7.2 克隆机身份唯一性：UUID 与每块网卡的 MAC

`CloneVMFromSpec` 原以 `spec := *source` 派生克隆配置。Go 的结构体赋值是浅拷贝，切片字段只复制切片
头（指针 + 长度 + 容量），因此原实现对 `Disks` 做了显式深拷贝、却**漏了 `Interfaces`**：克隆机的网卡
配置与源机共享同一底层数组，MAC 也就原样沿用了源机。

这个缺陷的隐蔽性在于**没有任何报错**：libvirt 会拒绝 UUID 重复的域定义（所以 UUID 漏改会立刻暴露），
但对 MAC 不做唯一性校验——XML 里显式给了就照用。后果直到两台机器同时开机才出现：源机与克隆机在同一
网段持有相同 MAC，ARP 表错乱，两台的网络双双不可用。`service/tasks/vm_tasks.go` 的 `execCloneVM` 里
还有一句与之呼应的错误注释「首个网卡 MAC 从 libvirt 查询（克隆后重新生成）」，同样已更正——libvirt
不会自动改 MAC，重新生成是平台自己的责任，该处只是把结果回读同步进数据库。

修复后的实现把「派生克隆配置」抽为**不依赖 libvirt 连接的纯函数**，目的正是让它可被单元测试断言：

| 函数（`service/virt/clone.go`） | 职责 |
|---|---|
| `randomMACAddr() (string, error)` | 生成 `52:54:00:xx:xx:xx` 随机 MAC。前缀取 KVM/QEMU 保留段，避免撞上物理网卡厂商 OUI；与 `service/tasks` 的 `randomMAC` 保持同一前缀 |
| `systemDiskIndex(source) int` | 定位首个 `device=='disk'` 的磁盘下标（**跳过 cdrom**，光驱不能作 linked clone 父盘），无则返回 -1 |
| `buildCloneSpec(source, newName, diskIdx, newDiskPath, srcDiskPath) (*DomainSpec, error)` | 纯函数：深拷贝 `Disks` 与 `Interfaces`、改名、重新生成 UUID、**逐块网卡重新生成 MAC**、清空 `RawXML`（克隆后 XML 由 `BuildDomainXML` 重建，dumpxml 原文不再适用） |

实测：源机 `52:54:00:7a:ad:94` → 克隆机 `52:54:00:6d:f2:b1`，数据库记录与 libvirt 侧一致。相关单元
测试 8 例见 docs/06 §4.2，其中「两块网卡的 MAC 都必须与源机不同、彼此不同、且不污染源 spec」是核心
用例。

### 6.7.3 删除保护：三重守卫与 `kept_volumes`

真正实现 backing chain 之后，删除虚拟机的破坏力随之上升：父盘一旦被删，chain 断裂，所有子虚拟机的
磁盘**立刻不可读且无法恢复**。而 `execDeleteVM` 原先只按「是否位于该存储池路径下」判断卷是否属于本
虚拟机，会误删两类共享文件：

| 误删对象 | 为什么会被误判 | 后果 |
|---|---|---|
| 增量克隆父盘 | 父盘与子盘同池同目录，路径前缀判定无法区分 | backing chain 断裂，全部子机磁盘不可读、不可恢复 |
| 镜像库登记的共享基镜像 | 「基于云镜像创建」是**直接引用不拷贝**（`execCreateVM` 的 `source_image_id` 分支），镜像与 VM 同池时按路径判定即被当成该 VM 的盘 | 镜像文件被删而 `images` 表记录仍在，留下悬挂记录，其他引用它的 VM 一并损坏 |

现由 `shouldKeepVol(src, volName) string` 统一判定，返回非空字符串即为「保留原因」，任一守卫命中即
跳过该卷：

| 序 | 守卫 | 判据 | 保留原因（逐字，会回传前端） |
|---|---|---|---|
| 1 | 池外文件 | `src` 不以 `<池路径>/` 开头 | `不在存储池 <池名> 路径下` |
| 2 | 共享基镜像 | `src` 命中 `images` 表登记的 `path` 集合 | `是镜像库登记的共享基镜像` |
| 3 | 增量克隆父盘 | `ListBackingRefs(pool)[src]` 非空 | `是增量克隆父盘，仍被 N 个子卷依赖（子卷名列表）` |

- 守卫二与守卫三的数据源分别是一次数据库查询与一次 `ListBackingRefs`，两者失败均**只打日志并降级**
  （跳过该守卫），不阻断删除流程——守卫的作用是减少破坏面，不应把删除变成必失败操作。
- 命中守卫时写服务端日志 `[tasks] 保留卷（未删）vm=.. vol=.. 原因=..`，并把 `"<卷名>（<原因>）"`
  追加进任务结果的 `kept_volumes` 数组（前端任务详情可见）。进度文案随之分叉为「磁盘清理完成
  （保留 N 个共享卷）」。
- 同批把 `DeleteVolume` 的错误从 `_ =` 丢弃改为打日志，避免删卷失败无声无息。

**已知取舍（如实记录）**：父盘守卫会导致「先删父机、再删子机」的操作顺序下，父盘文件残留在池里成为
**孤儿文件**（此时已没有任何域引用它）。这是刻意选择的取舍——一个垃圾文件可以事后清理，一块损坏的
在用磁盘不可恢复。孤儿卷的清理入口已闭环（见 6.15，复用同一套引用判定反向使用：零引用才删）。

## 6.8 cloud-init seed

设计思路：创建 VM 时可选注入主机名、用户口令、SSH 公钥与静态网络。纯 Go 生成 iso9660 seed ISO（卷标 `cidata`，cloud-init 约定），落到独立 seed 目录（`SEED_DIR`，默认 `/home/jiuzhao/vmops/data/seed`，web 可写、qemu 可读，不依赖存储池目录权限），以只读 cdrom 挂载，引导顺序提至光驱优先。

## 6.10 WebSocket 写入串行化与后台协程容错

设计思路：本平台在 HTTP 请求链之外还有三类常驻或短生命周期的执行流，它们的异常不受 Web 框架
Recovery 中间件保护，一次未处理的 panic 会直接终止进程。其中最容易被忽视的是 WebSocket 的
并发写：所用库（gorilla/websocket）允许「一个读协程 + 一个写协程」并发，但**明确禁止多个协程
同时写**，违反即 panic（`concurrent write to websocket connection`）。

本平台控制台桥实际存在的写入方：

| 桥 | 写入方 | 数量 |
|---|---|---|
| SSH 桥（`handler/terminal.go`） | stdout 转发协程、stderr 转发协程、主读循环的错误帧 | 3 |
| 串口桥（`handler/serial.go`） | 客户机输出转发协程、错误帧 | 2 |
| 会话注册表（`registry.go Disconnect`） | 管理员强制断开时的 `CloseMessage` | 1 |

因此新增 `service/console/conn.go` 的 `Conn` 类型统一承担串行化：

| 成员 | 说明 |
|---|---|
| `NewConn(ws *websocket.Conn) *Conn` | 包装原始连接 |
| `WriteMessage(t int, data []byte)` / `WriteJSON(v any)` | 持写锁串行化写入；连接已关闭返回 `ErrConnClosed` |
| `ReadMessage()` | 直接转发；读侧由单一协程独占，不加锁 |
| `Close()` / `CloseWithReason(reason string)` | 幂等；`CloseWithReason` 先在写锁内尽力发送带中文原因的关闭帧再关底层连接 |
| `ErrConnClosed` | 哨兵错误，桥接协程据此退出转发循环 |

后台协程容错清单（全仓库原先 `recover()` 出现 0 次）：

| 协程 | 位置 | recover 后行为 |
|---|---|---|
| 任务 worker（4 个） | `tasks.runExecutor` / `tasks.run` / `tasks.markFailed` | 任务置 `failed` + 中文文案，worker 继续取下一个 |
| VNC 会话清扫器 | `console.Registry.sweepOnce` | 打日志，定时循环不中断 |
| SSH 输出转发 | `handler/terminal.go pipeOut` | 打日志退出该路转发 |
| 串口打开 | `handler/serial.go` | 打日志并向 `errCh` 投递 `ErrConnClosed`，避免主流程永久等待 |
| 串口输出转发 | `handler/serial.go` | 打日志退出该路转发 |

另修复读循环的控制流缺陷：`handler/terminal.go` 的输入分发原为 `switch` 内裸 `break`，
只跳出 `switch` 而非外层 `for`，stdin 写失败时循环不会退出；现改为带 `readLoop` 标签的 `break`。

## 6.11 安全加固

### 6.11.1 路径参数主键统一解析（防 SQL 注入）

新增 `handler/param.go`：

| 函数 | 说明 |
|---|---|
| `parseID(raw string) (uint, bool)` | 纯函数，不写 HTTP 响应；供 WebSocket 等需自定义错误通道的场景使用 |
| `paramID(c *gin.Context, name string) (uint, bool)` | 失败时已写好 400「ID 参数非法」并 `Abort`，调用方直接 `return` |

原理：GORM 的 `BuildCondition` 对「非纯数字字符串且未附带占位参数」的内联条件，会把该字符串
当作原始 SQL 片段直接拼进 `WHERE`。因此 `db.First(&vm, c.Param("id"))` 存在注入面，
而 `db.First(&vm, id)`（`id` 为 `uint`）走参数化。由于只读角色可访问全部读接口，
最低权限账号即可经由查询接口构造布尔盲注读取任意表（含 `users.password_hash`）。

改造范围共 39 处调用点：37 处普通处理器改用 `paramID`（`vm.go` 26、`host.go` 4、`image.go` 4、
`audit.go` 1、`user.go` 1、`vnc.go` 1），2 处 WebSocket 处理器改用 `parseID`
（`terminal.go`、`serial.go`；WS 已升级无法再写 JSON 响应，错误经 WS 帧
`{"type":"error","msg":"虚拟机 ID 非法"}` 回送）。串口处的 `vmNameByID` 形参类型随之由 `string` 改为 `uint`。

对外行为变化：`/api/vms/abc` 这类非法 ID 以前落到查询后返回 404「虚拟机不存在」，
现提前返回 400「ID 参数非法」；合法数字 ID 的状态码全部不变。

### 6.11.2 libvirt XML 生成改结构化序列化（防 XML 注入）

`service/virt/` 原有 5 处以 `fmt.Sprintf` 拼接 libvirt XML，外部可控字段中的 `"` 与 `>`
可闭合当前标签并注入额外节点（如把存储池的目标路径改写到任意目录）。现全部改为
`encoding/xml` 结构体 marshal，元字符由标准库自动转义：

| 函数 | 文件 | 序列化入口 |
|---|---|---|
| `CreateVolume` | `storage.go` | `buildVolumeXML`（`volumeXML`，unit=G） |
| `CreateVolumeCustom` | `storage.go` | `buildVolumeXML`（自定义 format） |
| `CreateDirPool` | `storage.go` | `buildDirPoolXML`（`poolXML`） |
| `CloneVolumeFromVol` | `clone.go` | `buildVolumeXMLWithBacking`（unit=B，与父卷等容量，含 `<backingStore>`） |
| `NetworkXMLFromParams` | `network.go` | `networkXML` + 5 个子结构体 |

该改造同时落实 AGENTS.md 的「XML 用标准库 encoding/xml」与「flag/固定取值用命名常量」两条标准。

### 6.11.3 JWT 算法锁定与生产密钥强校验

- `ParseToken` 增加 `jwt.WithValidMethods([]string{jwt.SigningMethodHS256.Alg()})`。不加此项时，
  攻击者可改写 header 的 `alg` 让库走不同的验签路径（算法混淆攻击）。
- 启动校验原判 `config.GlobalConfig.JWTSecretKey == ""`，而 config 包为该项兜了硬编码默认值
  `vmops-jwt-secret-key-change-in-production`，条件永不成立——该校验是**死代码**。现改为
  **弱密钥黑名单**（内置默认值 + `change-me-please-use-a-strong-random-secret`，命中即拒绝），
  release 模式下命中黑名单即 `log.Fatalf` 拒绝启动——默认值随源码公开，任何人都能据此伪造管理员
  token。debug 模式（本地开发由 `start.sh` 显式 `export SERVER_MODE=debug`）放行以便开箱即用。
- `SERVER_MODE` 默认值从 debug 改为 **release**（安全默认）：裸部署不再落入「默认 JWT 密钥 +
  CORS `*`」的可伪造态。release 模式下还拒绝 `CORS_ORIGINS=*`（等于允许任意站点携带凭据跨域调用
  全部 API），必须显式配置具体来源。

### 6.11.4 敏感信息与内存边界

- 种子账号的明文口令不再写入启动日志（改为只打用户名与角色，并提示默认口令见 README、

## 6.12 工程一致性：状态字面量收口为常量

平台状态只有四个合法取值（`running` / `shut off` / `paused` / `error`），由 `virt.StateToPlatform`
从 libvirt 域状态枚举映射而来，并直接落进 `vms.status`、再由前端做颜色与文案映射。也就是说，同一批
字面量散落在三层（virt 封装层、业务层、前端），任何一处笔误都会造成状态显示错乱，且不会有编译错误。

本轮发现的实际不一致：`model/vm.go` 的 gorm 默认值写作 `shut_off`（**下划线**），而
`StateToPlatform` 返回的是 `shut off`（**空格**），前端亦按空格版本匹配。也就是说，一旦某条记录落到
列默认值，其状态在前端将无法匹配任何已知状态。修复与核查如下：

- 默认值改为 `shut off`，与映射函数及前端一致。gorm tag 内不能引用常量，故该字面量须与常量手工同步，
  代码注释已注明。
- 新增两套常量：`model.VMStatusRunning/VMStatusShutOff/VMStatusPaused/VMStatusError`（业务层）与
  `virt.StatusRunning/StatusShutOff/StatusPaused/StatusError`（封装层）；`StateToPlatform` 的
  `return` 与 `handler/vm.go` 的 8 处字面量改为引用常量。
- **刻意不让 virt 层 import model**：`model` 依赖 GORM，若 virt 反向引用会把 ORM 拖进最底层的 libvirt
  封装层并倒置分层依赖。因此两处各自定义、注释交叉引用，改一处必须同步另一处——这是「分层洁净」与
  「单一定义点」之间的取舍，选择了前者并用注释约束后者。
- 存量数据核查：数据库中**不存在** `shut_off` 的历史行（所有写入路径都显式给出状态值，从未落到列默认
  值）；另在沙箱中验证 GORM `AutoMigrate` 能够修改已有列的默认值，故后端下次重启即收敛，无需手工 DDL。
- 收口进度：`handler/vm.go` 8 处先行替换；`service/tasks`（vm_tasks/vm_create/vm_clone）与
  `handler/dashboard.go`、`service/metrics` 的字面量已在批 B 全部换为常量引用，本节开篇描述的
  「字面量散落三层」现状即告消除（gorm tag 内的字面量除外，见上）。

## 6.13 监控中心模块（告警代理 + Grafana 双看板 + 告警历史 + 服务发现预览）

设计思路：监控栈（Prometheus/Grafana/Alertmanager）以 Docker 容器常驻，产品内提供统一入口而非让运维分散在三个独立控制台。

- **告警代理**：`GET /api/monitor/alerts` 由后端转发 Alertmanager 的 `/api/v2/alerts`
  （`http.Client{Timeout:5s}`，地址取 `ALERTMANAGER_URL`），规避跨域并隐藏监控组件地址；
  AM 不可达返回 502，前端页内提示如何启动监控栈。
- **告警历史（webhook 网关）**：`POST /api/monitor/webhook`（公开路由，env `ALERT_WEBHOOK_TOKEN`
  可选鉴权；非 401/400 恒回 200 防 AM 重试轰炸）接收 AM 推送，按 fingerprint 去重 upsert 入
  `alerts` 表；`GET /api/monitor/alerts/history` 分页追溯（status/fingerprint 过滤），前端
  「告警历史」卡片展示——实时列表查不到的告警（平台重启/AM 环形截断）这里仍有记录。
- **服务发现预览**：`GET /api/monitor/file-sd` 返回 `{enabled, items}`——file_sd 将下发的

## 6.14 历史性能曲线（Prometheus 当历史库）

设计权衡：曲线历史的三种候选——MySQL 采样表（需自建清理任务、重复造时序轮子）、浏览器 localStorage
（跨设备失效、数据错位）、**Prometheus query_range 回放（采用）**：指标本来就在每 15s 入库，历史查询零新增存储，
保留期由 Prometheus 管理。

- 后端 `handler/history.go` 三个接口，均经 `PROMETHEUS_URL` 调 `query_range`（step=15s 与抓取周期一致）：
  `GET /api/dashboard/host-history`（宿主机大盘）、`GET /api/dashboard/vm-history`（**批量**返回全部 VM 序列，
  列表页一次请求预填所有迷你图）、`GET /api/vms/:id/stats-history`（详情页大图）。
- 前端策略：进页面先拉历史**预填** 60 点环形序列，之后 3s/5s 轮询在尾部无缝追加——
  「刷新即失、进页等 5s」的体验问题根治；Prometheus 不可达时静默降级为原攒点行为。
- **实现坑（论文测试素材）**：内存占比表达式 `100*used/total` 在 VM 关机瞬间产生 0/0=NaN，
  Go 的 `encoding/json` 不支持序列化 NaN，导致 `c.JSON` 渲染失败、响应体为空（HTTP 200 + Content-Length:0）。
  解析点位时必须以 `math.IsNaN/IsInf` 跳过非有限值。
- 关键文件：`handler/history.go`（含 `escapePromLabel` 的 PromQL 字面量转义）、`handler/history_test.go`。

## 6.15 孤儿卷清理（cleanup_volumes 任务）

删虚拟机的三重守卫会刻意保留共享卷；按「先删父机、再删子机」顺序操作后，最终守卫放行的父盘可能成为
零引用孤儿。孤儿卷清理任务复用守卫的同一套引用判定**反向使用**：

- 孤儿定义：不被任何虚拟机磁盘挂载（`ListAllDomainDiskSources`）、未登记镜像库（`images.path`）、
  也不是任何子卷的 backing 父盘（`ListBackingRefs`）——三者皆空才删，任一命中保留并记录原因。
- 链路：`POST /api/storage/pools/:name/orphan-cleanup`（202）→ `cleanup_volumes` 任务 →
  Result `{pool, deleted[], kept[{name,reason}]}`；前端存储池页「清理孤儿卷」按钮先经 volume-refs
  列出候选再二次确认。
- 设计立场不变：宁可漏删占空间，不可错删在用磁盘。
- 关键文件：`service/tasks/vm_tasks.go`（`execCleanupVolumes`）、`handler/storage.go`（`CleanupOrphans`）。

## 6.18 VM 资产授权（授权决定可见性，借鉴堡垒机 4A）

设计思路：堡垒机（JumpServer）的 4A 模型把「分配」当作一等实体——用户能看到什么由授权规则决定，
而不是靠界面藏入口。本平台取其「授权决定可见性」思想做轻量版：`vm_grants` 单表（字段与索引见
docs/04 §3.11），一行 = 「把某台 VM 授给某个用户」，用户可见/可操作的 VM = 有效授权的并集。

- **404 语义**：非 admin 访问任何 VM（列表/详情/规格/克隆源/快照/三控制台/历史曲线）都要求存在
  未过期授权，未授权一律 404「查无此项」而非 403——不向无权用户暴露资产的存在性；admin 不受约束。
  过期授权在查询判定时即时视为不存在（软回收，行保留可查授权历史，无需清扫协程）。
- **生命周期自动化**：建机/克隆任务成功后自动给发起人授一条长期授权（`execCreateVM` /
  `execCloneVM` / `execCloneImageVM`，学生开机即拥有自己机器的完整操作权）；删 VM 时回收该 VM
  的全部授权（`execDeleteVM`），不留悬挂行。
- **API（admin 专用）**：`GET /api/vms/:id/grants`、`POST /api/vms/:id/grants`
  （body `{user_id, expires_at?}`；(user_id, vm_id) 已存在则更新有效期，过去时间 400）、
  `DELETE /api/vms/:id/grants/:gid`。授权管理路由挂在 `/api/vms` 前缀下，OperatorMiddleware
  会对 operator 放行该前缀写操作，故 handler 内以 `requireAdminRole` 二次收口为仅 admin。
- **与 JumpServer 的刻意取舍**：不做 用户组×资产节点树×账号×动作/协议 的多维矩阵、不做命令过滤
  ACL、账号托管代填、自定义 RBAC 权限点引擎与多级审批流——单宿主机场景一张平面表足够，
  多级模型的重是它的场景，不是它的好。
- 关键文件：`model/vm_grant.go`、`handler/vm_grant.go`（含 `grantedVMIDs`/`requireAdminRole`）、
  `handler/vm.go`（`findVM` 内授权过滤）、`service/tasks/{vm_create,vm_clone,vm_delete}.go`（授权生命周期）。

## 6.19 SSH 跳板入口（jumpd，借鉴堡垒机 4A）

- **定位**：把 Web 端已建成的三套体系（RBAC、`vm_grants` 资产授权、`vmssh` 安全链）在「原生终端」入口复用一遍——任意终端工具 `ssh <用户名>@<宿主机> -p 2222` 即可连资产，不绑定浏览器。JumpServer 的 SSH 入口（koko）即同型能力。
- **结构**（`service/jumpd` 五单元，全部 TDD）：
  - `limiter.go`：per-IP 登录失败限流（1 分钟 5 次锁定，先查锁再验密；时间判定抽可注入时钟，窗口推进测试不靠 sleep——优于 handler 版 loginLimiter）；
  - `menu.go`：菜单纯函数（授权过滤/9 台分页/渲染/按键状态机 `1-9`/`j`/`q`），映射只携带 VM ID——连接前授权/状态/IP 由 server 现查重验（时间窗防绕过）；
  - `auth.go`：users 表 bcrypt 校验（`middleware.CheckPassword` 同链路）+ 禁用账号拦截 + viewer 会话层拒绝（SSH 密码失败无法携带自定义文案，故认证放行、会话内提示后断开——Gitea/koko 惯例）；
  - `hostkey.go`：跳板自身 ed25519 密钥持久化 `data/jumpd_host_key`（0600），损坏 fail-closed 拒绝启动（known_hosts 稳定性的根，绝不静默重生成）；
  - `server.go`：SSH 服务端装配（`AddHostKey` + PasswordCallback）、**单读者桥接模型**（keyStream 是用户 channel 的唯一读者，桥接期 forwardKeys 消费键流、结束后未消费字节归还菜单——杜绝双读者抢字节）、PTY 参数原样回放（window-change 转发）、会话落库经 `dbx` 收口。
- **安全要点**：连接目标唯一来源是 DB 行（不存在从键盘输入解析 IP 的路径，比 Web 终端更进一步）；明文口令仅内存流转不进日志；goroutine 全覆盖 recover；jump 会话纳入重启清扫（`sweepStaleRecords` type IN 加 "jump"）。
- **命令黑名单**：`forwardKeys` 行缓冲拦截——默认逐字节透传（vim/htop 全屏交互不受影响），行结束（\r）时对「该行输入」归一化匹配黑名单（小写+连续空白折叠，抗 `RM  -RF` 变体）；命中则整行不送达 + 向目标 tty 发 Ctrl-U（0x15）清残留行（防下条命令的回车误执行）+ 红字提示 + `audit_logs` 落行（Action=jumpd.cmd_blocked，审计中心直接可见）。黑名单为 settings 键 `jumpd_cmd_blacklist`，设置页可配，空值回退内置默认（护栏 fail-safe）。
- **跳板传输面天然关闭**：channel 类型白名单只收 session——direct-tcpip（端口转发）、subsystem（sftp）、exec（scp/rsync）一律 Reject。即「连上后只能敲键盘」，传不了文件、开不了隧道，这是授权动作粒度的最严档默认。
- **部署**：`JUMPD_ENABLED=1` 开启（默认关），`JUMPD_PORT` 默认 2222；公网暴露须叠加防火墙白名单（服务内限流只是兜底）。
- **测试**：19 个顶层测试函数（限流窗口/菜单状态机/认证链/hostkey fail-closed/重验四路拒绝/会话幂等/panic 兜底）+ 7 项真实 SSH 客户端冒烟（含爆破锁定后正确密码也拒）。

## 11. v3 扩展模块实现要点（容器 / 应用商店 / 凭据 / 计划任务 / 文件管理 / AI 等）

v3 起平台从「纯 KVM 管理」扩展为「KVM + 容器」双运行时的轻量私有云控制面。本章按模块记录实现
机制与设计取舍；容器与商店两线在对标 1Panel 后强化（设计模式参考 1Panel，GPLv3，仅借鉴交互与
分层思路、不引入其代码与 UI 组件）。v3 新增的服务包：`service/dockerx`（容器代理）、
`service/appstore`（声明式 compose 应用包）、`service/apps`（VM 内脚本安装目录）、
`service/vmssh`（SSH 一次性命令执行 + TOFU 主机密钥）、`service/secretbox`（凭据加解密）、
`service/cron`（cron 解析与调度）；对应模型见 docs/04 §3.12–3.16。

### 11.1 容器管理（dockerx 代理 + 容器终端）

- **`service/dockerx` 走 docker CLI 而非 Engine API**：`exec.CommandContext("docker", ...)` + `--format '{{json .}}'` 结构化输出逐行反序列化（单行脏数据跳过不毁整表）。取舍：零第三方依赖、天然继承用户 `docker` 组权限与镜像加速配置；统一 30s 超时（logs 60s）防假死命令拖住 handler；全部数组参数禁止 shell 拼接，凡外部传入的容器/镜像 ID 先过 `safeDockerID`（字母数字 `-_.` 白名单，≤128 字符）才允许拼进 argv。能力面：容器列表/启停重启删/日志/inspect/单容器与全量 stats、镜像列表/拉取/删除、`image|container prune`（解析输出中的回收空间）、网络与卷的增删查、`compose ls` 与项目级启停。路由组 `/api/docker` 挂 `NonViewerMiddleware`（容器清单暴露内网端口映射，viewer 403）。
- **容器终端（`handler/container_terminal.go`）走 Docker Engine API（`/var/run/docker.sock`）而非 `docker exec -it`**：实测 CLI 对非 TTY 的 stdin 直接拒绝（"the input device is not a TTY"，该检查在 CLI 内部，`-t` 与本进程侧管道天然互斥），CLI 方案根本无法工作；Engine API 的 `/exec`（Tty=true）+ attach 劫持流没有这道检查，且 `/exec/{id}/resize` 原生支持运行中调窗。桥接纪律与 SSH 终端桥严格对齐：WS 升级后一律经 `console.Conn` 包装（输出转发/pong/管理员强断多路写，裸 `*websocket.Conn` 并发写会 panic 带走进程）、自起协程逐个 `defer recover`、错误帧固定中文文案。API 版本与 dockerd 协商一次（`/_ping` 响应头，失败回退 1.44——docker 29 起强制最低 1.44，写死更旧版本被 400 拒绝，实测踩中）。生命周期：exec 进程由 dockerd 托管、本地无子进程可泄漏；WS 断开先发 EOF 促使空闲 shell 自退再关劫持流。参考 1Panel（GPLv3）容器终端的 exec(Tty)+attach 设计模式。
- **容器创建（v3.4，`POST /api/docker/containers`）**：表单字段（名称/镜像/端口映射/挂载卷/环境变量/重启策略/启动命令）映射 `docker run -d` 参数。`BuildRunArgs` 与 `ValidateContainerOpts` 拆成包级纯函数可单测（端口两/三段式 + 1-65535 + tcp/udp 白名单、volume 目标端必须绝对路径、env 按第一个 `=` 切分且键禁空白、restart 四值白名单、镜像名复用 `safeImageRef` 与 Pull 同口径）；handler 与 dockerx 双层校验（与 CreateNetwork 同防线）。镜像本地缺失时 docker 先自动拉取（耗时不可控，超时与 Pull 同为 10 分钟），`CombinedOutput` 会把拉取噪音混在 64 位容器 ID 前——`extractContainerID` 从最后一行向前找第一个 12-64 位 hex 形态的行截取 12 位短 ID（E2E 实测：alpine 自动拉取场景返回正确短 ID）。
- 关键文件：`service/dockerx/{dockerx,json,container_create}.go`、`handler/docker.go`、`handler/docker_compose.go`、`handler/container_terminal.go`。

### 11.2 应用商店 v2（声明式 compose 应用包）

- **包协议**：每个应用 = 磁盘目录 `conf/appstore/<key>/<version>/` 三件套——应用级 `data.yml` 元数据（名称/分类/描述/标签）+ 版本级 `data.yml` 表单定义（`formFields`：envKey/label/type(text·number·password·select)/default/required/rule）+ `docker-compose.yml`（`${VAR}` 占位）。内置 20 个应用包（nginx/mysql/redis/postgresql/minio/gitea/jenkins/n8n/code-server 等）。
- **安装流水线**（`service/appstore` `Install`）：读包校验 key/版本 → `ValidateFields` 参数校验（`paramPort` 规则 = 端口 1-65535）+ 补默认值 → 拷贝包到 `data/apps/<key>/`（重装覆盖 yml、**保留 `data/` 运行数据**）→ 写 `.env`（每表单项一行 `KEY=VALUE`）→ `docker compose -p <key> --env-file .env up -d`（10 分钟超时）。**变量替换完全交给 compose 原生 `--env-file` 插值，平台零模板渲染**；校验在拷贝之前，参数不合法不留半装目录；compose 失败时安装目录保留供排查。项目名固定 `-p <key>`，卸载/状态查询用同一项目名对上。`ComposeError` 随错误携带 stderr 尾部摘要（镜像拉不动/端口被占的原因几乎都在 compose 输出里，属必须透出的运维信息）。
- **两个刻意决策**：①不用 go:embed——运维可直接在磁盘增改应用包，无需重编译（部署形态为单机同目录）；②yaml 解析用约百行的行式读取器（`parseSimpleYAML`）而非引入 yaml 库——data.yml 结构受控，覆盖不到的完整 YAML 语法一律不支持并在包内禁用。key/版本目录名经正则白名单校验（key 会拼进文件路径，拒绝路径穿越成分），`.env` 键名白名单防换行/等号伪造变量行。安装入口对 Docker 不可用返回明确状态（前端禁用安装）；目录浏览挂 `NonViewerMiddleware`。
- **与 v1 脚本商店（`service/apps`）的关系**：v1 面向**虚拟机内**（内置 Detect/Install 脚本经 SSH 执行，`app_install` 任务；脚本 `set -e` + `DEBIAN_FRONTEND=noninteractive` + 幂等，目录接口不泄露脚本正文、详情接口供安装前审查）；v2 面向**宿主机**容器。两套并存，前者管「给 VM 装软件」，后者管「在宿主机起一套 compose 应用」。
- 关键文件：`service/appstore/{appstore,compose}.go`、`handler/appstore.go`、`service/apps/apps.go`、`service/tasks/app_tasks.go`、`conf/appstore/*`。

### 11.3 SSH 凭据托管与 TOFU 主机密钥校验

- **凭据托管**（`service/secretbox` + `handler/vm_credentials.go`，模型见 docs/04 §3.14）：主密钥复用 `JWT_SECRET_KEY`（运行时注入、不落库），每条凭据随机 32 字节盐，`SHA-256(主密钥‖盐)` 派生 AES-256 密钥后 GCM 加密（随机 nonce 前置，整体 base64）。威胁模型明确：防「数据库泄露后凭据直接可读」，不防进程与库同时失守；解密只发生在服务端（`ResolveFor`，供文件管理/商店安装的 `use_saved` 通道取用），前端只拿掩码；`PasswordEnc`/`Salt` 的 json tag 为 `-`。解密失败（盐/密文损坏或主密钥已轮换）一律 fail-closed，绝不降级成空口令。
- **TOFU 主机密钥**（`service/vmssh/hostkey.go`，存储见 docs/04 §3.16）：Web 终端与文件管理两处 SSH 拨号原先各有一个 `ssh.InsecureIgnoreHostKey()`——主机密钥完全不校验，中间人只要能劫持路由（ARP 欺骗/DHCP 抢占）即可在 SSH 认证发生前替换对端。现统一走 `TOFUHostKeyCallback()`：首连记录公钥 SHA256 指纹（等价 openssh 写 known_hosts），复连逐一比对，不一致即拒绝（哨兵错误 `ErrHostKeyMismatch`，文案直接引导「管理员删除旧指纹后重录」——平台自建 VM 重建即换密钥，人工核对 known_hosts 不可操作，故取自动 TOFU；目标范围仍由调用方 `validateSSHTarget` 白名单收敛，本层是纵深防御）。回调 **fail-closed**：指纹存储未注入或查询失败一律拒绝连接，绝不退化成不校验；并发首连撞 `(host,port)` 唯一索引时第二个连接报错拒绝，属可接受的保守行为。admin 管理端点 `GET|DELETE /api/ssh-host-keys`（挂 AdminMiddleware）。
- **`service/vmssh` 面向一次性命令执行**：与终端桥的常驻会话不同，文件管理每次调用新建连接、执行完即关；VM 内路径参数必须经 `ShellQuote` 单引号包裹后才能拼进远程命令（防命令注入，单测覆盖 `$( )`、反引号、分号、管道、换行等注入载荷）。
- 关键文件：`service/secretbox/secretbox.go`、`service/vmssh/{vmssh,hostkey}.go`、`handler/vm_credentials.go`、`handler/ssh_host_keys.go`、`handler/terminal.go`（HostKeyCallback 换 TOFU）。

### 11.4 计划任务（调度 + 执行记录 + cron 预览）

- **cron 解析自研不引库**（`service/cron`）：只需「分 时 日 月 周」五字段子集（无秒/年/时区/@daily 别名），纯函数约百行覆盖（`*`、`*/n` 步进、逗号列表、闭区间±步进），错误消息固定中文可直接回显。匹配语义为五字段全 AND（与 robfig 标准版在 dom/dow 同时受限时的 OR 行为不同，本项目场景不存在该用法）。`Next` 逐分钟探测取下一次执行时刻，设 366 天前瞻上限防「永不匹配的表达式」（如 2 月 31 日）死循环；`NextRuns` 供 `GET /api/crons/preview?expr=` 返回未来 5 次执行时刻预览（前端建任务时即时可见）。
- **调度器**：`Scheduler.loop` 对齐分钟边界整分 tick（`time.Sleep` 到下一分钟），循环体带 recover 防 panic 杀掉调度协程。动作白名单 `vm_snapshot`（对指定 VM 打 `cron-` 前缀快照）与 `db_backup`（mysqldump 落盘，10 分钟超时防容器假死拖住调度协程）；每任务按 `keep` 保留最近 N 份产物，清理只针对 `cron-` 前缀（手工快照不受影响）。每次执行在 `cron_runs` 插行跟踪（running → success/failed + 摘要 ≤2000 字符）；失败可选推 webhook 通知（`CRON_NOTIFY_URL`，飞书/钉钉机器人格式，5s 超时，异步推送不占调度锁）。
- **CRUD**（`handler/crons.go`，admin）：创建/编辑经 `ParseCron` 校验表达式、`vm_snapshot` 动作校验目标 VM 存在；启停开关、立即运行（手动触发同走执行记录）、按任务分页查执行历史。模型与索引见 docs/04 §3.12/3.13。
- 关键文件：`service/cron/cron.go`、`handler/crons.go`、`model/scheduled_task.go`、`model/cron_run.go`。

### 11.5 VM 文件管理（SSH 在线 + guestmount 离线双通道）

- **在线通道**（`handler/vm_files.go`）：对开机 VM 经 SSH 执行列目录/下载/上传/删除/建目录。信任模型与 Web 终端一致——拨号参数由请求体携带、仅内存透传；目标先过 `validateSSHTarget` 白名单（防平台沦为跳板机）；路径参数经 `ShellQuote` 后拼接（防命令注入）；`use_saved=true` 时经凭据托管 `ResolveFor` 后端自行取凭据（口令不出服务端）。**上传限 16MB**：SSH exec 通道会把内容整体载入内存，必须设上限防大文件 OOM，更大文件引导走离线通道。
- **离线通道**（`handler/vm_files_offline.go`）：对关机 VM 用 `guestmount` 把系统盘只读挂到 `/tmp/vmops-mounts` 再走普通文件 API，不依赖 VM 内 SSH 服务（在线管开机机、离线管关机机）。权限与安全现实：libvirt 卷属 root，guestmount 经 `sudo -n` 调用（宿主机免密 sudo，`-n` 禁止交互挂死）；磁盘被运行中 VM 持有时会因写锁失败，故**运行中的 VM 一律拒绝挂载**；挂载固定 `--ro` 只读——宁可浏览受限，不可损坏磁盘（与删卷守卫同一立场）。挂载表在内存（进程重启即失，重新挂载即可），`OfflineCapability` 端点供前端预判该 VM 走哪条通道。
- 关键文件：`handler/vm_files.go`、`handler/vm_files_offline.go`、`service/vmssh`、`handler/vm_files_test.go`（`ls --full-time` 输出解析器单测）。

### 11.6 AI 运维助手（平台上下文注入 + SSE 流式）

- **形态**：OpenAI 兼容 `/chat/completions` 的服务端代理（`POST /api/ai/chat`）。三项配置（`ai_base_url`/`ai_api_key`/`ai_model`）存 `system_settings`（经设置页写入），**API Key 只存服务端永不下发**（状态接口只回掩码）。流式响应逐段经 SSE 转发给浏览器。
- **平台上下文注入**：`with_context=true` 时把「平台环境摘要」拼进 system prompt——VM 总数与运行数、运行中 VM 清单（名称/核/内存，至多 20 台）、Docker 容器总数与运行数、镜像库条数、firing 告警数——使助手「看得懂这台服务器」，能回答「几台虚拟机在跑」这类问题而不需要任何工具调用通道。
- **安全边界**：AI 只读问答，不具备任何平台写操作能力（不提供 function calling 通道）；未配置 Key 返回 400 + 配置引导；viewer 403（消耗 API 配额且平台上下文属资产信息，路由组挂 `NonViewerMiddleware`）。
- 关键文件：`handler/ai.go`、`web/src/views/AiChat.vue`（markdown 渲染 + 停止生成）。

### 11.7 回收站（软删 VM 可视化）

删除 VM 已是「软删 DB + 域 undefine + 卷按守卫保留」，回收站把软删记录可视化：列表（`GET /api/vms-recycle`）经 `Unscoped()` 绕过 GORM 软删过滤取 `deleted_at` 非空的行，并逐台探测 libvirt 域是否还在（`domain_exists`）；恢复（`POST /:id/restore`）只还原数据库记录、不重建 libvirt 域——恢复前先做**同名活记录防撞**（软删期间用同名重建过机器则 409 拒绝，防 libvirt 按名寻址打到别机），域若还在则顺带同步实时状态，不在则如实回「记录已恢复，但虚拟机定义已不存在，可在创建向导用同名卷重新定义」；彻底清除（`DELETE /:id/purge`）物理删行。全部端点仅 admin（方法内 `requireAdminRole` 二次收口，与 vm_grant 同款双保险）。关键文件：`handler/vm_recycle.go`、`web/src/views/RecycleBin.vue`。

### 11.8 VM 导出/导入（tar.gz 全量包）

导出（`GET /api/vms/:id/export`，VM 必须关机）：把 `GetDomainSpec` 的域 XML 原文与系统盘卷文件流式打成 tar.gz 直接写响应体——gzip/tar 两级 writer 管道到 HTTP、64KB 缓冲分块拷贝，**全程不落临时盘、不整载内存**，20GB 级磁盘不放大进程内存。导入（`POST /api/vms/import-file`，admin）：multipart 上传（超 32MB 部分自动落服务器临时文件），逐 tar 条目流式解包到池内临时目录；卷恢复优先 rename（同文件系统）回退 io.Copy（跨文件系统）；域 XML 里的旧磁盘路径替换为新池路径后 define，最后写 vms 表记录；**任一步失败按已产生的副作用逆序清理**（undefine + 删卷），不留半台机器。包格式 `<域名>.xml` + `<盘名>.qcow2`；导入包请求体上限 20GB、包内 XML 上限 4MB、tar 条目扫描上限 64（防恶意超长包）。已知限制：数据盘/cdrom 不在包内（导出的是「可引导的系统盘 + 定义」）。关键文件：`handler/vm_export.go`。

### 11.9 云镜像市场（获取渠道，与镜像库理顺）

内置官方云镜像清单（Ubuntu 22.04/24.04、Rocky 9 等，URL 均经 HEAD 实测 200），`GET /api/images/market` 返回清单（每项标注官方来源、体积参考与默认下载目标池）；`POST /api/images/market/download`（admin）校验后提交 `image_download` 异步任务（202 + task_id），executor 流式落盘到目标池并登记 `images` 表。定位口径：**市场 = 获取渠道，镜像库 = 资产仓库**——下载完成即成为普通云镜像，后续走「基于云镜像创建」的增量克隆链路；市场并入镜像管理页双 tab 展示，下载中的任务经任务系统跟踪、页面刷新后按 running 任务恢复下载态（防重复发起）。清单项 `os_name` 与 `virt.OSList` 对齐（下载完成建机时可自动选中 OS）。关键文件：`handler/image_market.go`、`service/tasks/image_download.go`、`web/src/views/ImageList.vue`（市场 tab）。

### 11.10 Loki 日志栈（可观测性：指标 + 日志）

Loki/Promtail 以 docker compose 形态部署（`deploy/docker-compose.loki.yml`，promtail 挂 `/var/log` 与 docker.sock 按容器标签发现），平台侧不做栈管理、只做**查询代理**：`GET /api/monitor/loki/query` 把 LogQL 转发给 Loki `query_range`（`since` 换算 start/end，step 按跨度自动取点；默认 1h、上限 168h 与 Loki 保留期对齐——更早日志已被 compactor 删除；`limit` 钳制 1~5000；响应体积上限 16MB 防异常上游拖垮后端），原始 JSON 放进统一信封 `data` 返回；`GET /api/monitor/loki/query` 之外另有 labels 端点。代理动机与告警代理相同：规避跨域并隐藏 Loki 地址端口；Loki 未部署返回 502 + 部署指引，不影响平台其余功能（日志栈是可选增量）。前端在监控中心以「日志」面板消费（LogQL 输入 + 结果表格）。关键文件：`handler/loki.go`、`deploy/README-loki.md`。

### 11.11 公告板（登录页与仪表盘）

公告面向全员（含未登录的登录页访客）：`GET /api/announcement` 公开读取，返回 `{content, updated_at}`——内容读 `service/setting` 进程内缓存（匿名高频访问不打 DB），`updated_at` 查 `system_settings` 行的更新时间，查库失败降级为不下发该字段并留日志（**公开端点恒 200**，不因辅助字段失败影响公告展示）。写入口收敛在 `PUT /api/settings`（admin），内容与长度（≤2000 字符）由 `service/setting.Validate` 把关，存储复用 `system_settings` KV 表（`announcement` 键），不另建表。前端登录页与仪表盘展示。关键文件：`handler/announcement.go`、`service/setting`。

### 11.12 配套小模块（工具箱 / cloud-init 模板 / 安全入口与密码策略）

- **工具箱**（admin）：宿主机快捷运维四件——进程列表、磁盘占用（`du` 平台数据目录）、docker prune、过期任务记录清理。外部命令一律数组参数 + 30s 超时，方法内 `requireAdminRole` 二次收口。关键文件：`handler/toolbox.go`。
- **cloud-init 模板**：把创建向导的 cloud-init 参数（主机名/用户/口令/SSH 公钥/网络模式）存为可复用预设（`cloud_init_templates` 表，docs/04 §3.15），CRUD 挂 operator 档，建机时套用即回填表单。关键文件：`handler/cloud_init_templates.go`。
- **安全入口与密码策略**：`security_entrance` 非空时登录路由挂 `EntranceMiddleware`（请求须携带 `X-Entrance` 头或 `?entrance=` 参数，口令白名单限 URL/HTTP 头安全字符），扫描器打 `/login` 只得 404；`password_min_length` 控制改密/建用户的密码最小长度（≥8 时额外要求含字母与数字）。关键文件：`middleware/entrance.go`、`service/setting`。

### 11.13 告警出站通知（v3.4，飞书/钉钉 webhook）

- **`service/notify` 叶子包**：`SendText(url, text)` 向飞书/钉钉自定义机器人推送文本消息，**按 URL 域名自动分派报文格式（飞书/钉钉）**——host 含 `oapi.dingtalk.com` 发钉钉 `{"msgtype":"text","text":{"content":...}}`（HTTP 200 且 body `errcode=0` 才算成功，解析不出 errcode 当成功），其余发飞书 `{"msg_type":"text","content":{"text":...}}`（按状态码判定成败）（5s 超时、`%w`+中文包装、网络错误文案脱敏只含 scheme://host 不泄漏机器人 token），零业务依赖无导入环；`service/cron` 的计划任务失败通知 `notifyFailure` 重构复用同一实现（行为不变：URL 空跳过、失败只打日志，推送异步化不占调度锁）。
- **触发与去重语义**：settings 白名单新键 `alert_notify_url`（进 `All()` 快照供设置页回显——GET /api/settings 本就 admin-only，不回显会导致刷新后无法核对是否已配置）；告警 webhook 入库时经 `alertTransitionedToFiring` 判定——**仅「新建即 firing」或「resolved 转回 firing」才推送**，Alertmanager `repeat_interval` 重复推送同 fingerprint 不重复通知、resolved 一律不推（防刷屏）。推送在 `goroutine + defer recover` 中 best-effort 执行，失败只进日志、绝不影响 webhook 的 200 响应（AM 重试轰炸防线，AGENTS 在案约定）。
- E2E 实测：本地 mock 接收器收到 `{"msg_type":"text",...}[鸢航 VirtKite] 告警触发: <alertname> <summary>`，同 fingerprint 重复推送正确去重（仅 1 次到达）。关键文件：`service/notify/notify.go`、`handler/alert_webhook.go`、`service/setting`。
