## 1. vmdashboard 研究要点

- **架构**：`pages/{domain,host,network,storage,config}/` 按资源分区，list/detail 两级；每个请求新建 libvirt 连接。
- **认证**：PHP Session + bcrypt（`password_verify`），**无角色区分**（比本平台弱）。
- **libvirt 封装**：1398 行 facade 类，全部走 PHP libvirt 扩展（`libvirt_connect` 等），非 virsh。
- **VNC 链路**（核心借鉴）：
  1. VM 详情页生成随机 token（100 位），写入 `tokens.php` 映射文件；
  2. `index.php` 启动 websockify：`websockify --target-config tokens.php 6080`；
  3. 前端 `vnc.php` iframe 嵌入 `vnc_lite.html?token=xxx`；
  4. token 仅对「当前查看的运行中 VM」有效。
  - **Go 版改进**：用 websockify 的 `JSONTokenApi` 代替写文件，Go 侧 `GET /token/{id}` 动态返回 `{host,port}`。
- **存储池**：列表（状态/容量/分配/路径）、卷创建/克隆/删除、注册新池（路径限定 `/var /mnt /media` 前缀）。
- **网络**：列表（网关/IP段/转发/DHCP）、启停/删除、XML dumpxml/编辑、NAT+DHCP/macvtap/从 XML 创建。
- **Domain**：创建向导（OS 平台自动选 virtio/rtl8139 网卡模型）、XML 编辑、磁盘增删、光驱挂载、网卡增删、快照、VNC 预览。
- **事件审计**：`vmdashboard_events` 表记录 谁/何时/对哪台 VM/做了什么（与本平台 audit_logs 呼应）。

## 2. KvmDash 研究要点

- **架构**：Symfony 7 + API Platform，前后端分离（React 19 + Vite + MUI）。
- **认证**：**无状态 JWT（RSA 签名）+ json_login** —— 登录端点公开，其余 `/api` 全部要求 `Bearer`。与本平台 JWT 思路一致。
- **API 风格**：「资源 + 动作动词」REST：`/api/virt/domains`、`/api/virt/domain/{name}/start|stop|reboot|delete`、子资源 `/snapshots`。统一 DTO 响应。
- **创建 VM**：混合方案 —— `qemu-img create` 建盘 + `virt-install --graphics spice` 定义并启动，失败回滚删盘（本平台已实现等价逻辑：qemu-img + virsh define + DB 回滚）。
- **删除 VM 带存储清理**：遍历存储池 + XML 提取 disk path + `undefine_flags(NVRAM|MANAGED_SAVE|SNAPSHOTS_METADATA)` —— 删除彻底性的关键。
- **快照**：级联删除（先删子再删父）。
- **控制台**：SPICE + spice-html5（本平台可选 noVNC，两者同构：XML 取 port → websockify → 前端）。
- **监控**：`libvirt_domain_memory_stats` 算真实内存（RSS/USABLE 等 tag）—— 仪表盘指标参考。
- **前端**：VM 状态 5 秒轮询、指标 2 秒轮询、token 存 localStorage、401 统一登出 —— Go 版初期轮询足够，不必上 WebSocket。

## 3. Cockpit Machines 研究要点

- 技术栈：libvirt-dbus 枚举/操作 VM + **virt-install / virt-xml**（virt-manager 家族 CLI）创建/修改定义。
- 结论：Rocky 自带管理页的 VM 模块底层与 virt-manager 同源，走 libvirt 线，与我们殊途同归。
- 借鉴：UI 简洁、任务导向、创建向导（业界标准形态）。

## 4. 对本平台的启示

### 4.3 JumpServer 实站调研（Docker jms_all:v4.10.19 实测）

> 部署方式：`docker run -p 18080:80 -p 2222:2222 -e DOMAINS=localhost:18080 jumpserver/jms_all:v4.10.19`；前端入口为 `/lina/`（别进 `/core/auth/login/` 的 Django 后台登录）。

- **首次登录强制改密码**：出厂 admin 密码为 `ChangeMe`，首次登录后端置 `is_first_login=true`，强制跳转改密（`users/serializers/profile.py`）。**用户侧机制值得借鉴**：默认弱密码 + 首登强制改密，避免出厂密码裸奔。实现要点：用户表加 `is_first_login`，登录成功若为 true 则前端强制进入改密页、改完清标志。
- **连接方式选择器**（Luna `ui/components/ConnectForm/connectMethodPicker.vue`）：按协议（SSH/RDP/VNC）分组 Tab，`builtin`（内置 Web 终端）/ `native`（本地客户端）/ `remote_app` 三类，默认选中、可切换。与我们控制台"侧边栏 + 自动尝试串口"同哲学。
- **登录链路错误必须透出**（教训）：v4 存在密码策略异常二次抛错（`PasswordTooSimple` → `str(e)` 再崩）导致登录接口 500、前端"点登录无反应"。**反面教材**：认证失败必须返回明确中文错误，前端兜底提示，禁止静默 500。
- **CSRF/DOMAINS 配置**：非标准端口/IP 访问需配 `DOMAINS`（CSRF_TRUSTED_ORIGINS），否则登录被 CSRF 拦截。我们平台用 JWT + `Authorization` 头，天然规避此问题。

### 4.4 资产授权规则（4A 产品逻辑）与本平台轻量落地

JumpServer 是符合 **4A 规范**的堡垒机（认证 Authentication / 授权 Authorization / 账号 Account /
审计 Audit），其核心产品逻辑是**资产授权规则**：用户（组）× 资产/节点 × 账号 × 动作/协议 × 有效期
组成授权矩阵，**用户可见的资产 = 命中规则的并集，未授权资产查无此项**——不是界面灰化，而是从数据
层面就不存在。这套「授权决定可见性」是本平台 `vm_grants` 表的直接思想来源。

| 维度 | JumpServer | 本平台（轻量版） |
|---|---|---|
| 授权模型 | 用户/组 × 节点树 × 账号 × 动作/协议 × 有效期 多维矩阵 | 单表 `vm_grants`：一行 = 「把某台 VM 授给某用户」（`(user_id, vm_id)` 唯一 + `expires_at` 可空 = 长期） |
| 可见性 | 未授权资产查无此项 | 同语义：非 admin 未授权一律 404，不暴露资产存在性；admin 不受约束 |
| 到期 | 调度回收 | 查询判定时即时失效（软回收，行保留可查授权历史，无需清扫协程） |
| 角色对照 | 系统管理员 / 审计员 / 普通用户 | admin / viewer（教师） / operator（学生） |

**明确不搬的部分**（对该场景过重，属其场景而非其好）：命令过滤 ACL、多级资产节点树、账号托管与
代填、自定义 RBAC 权限点引擎、多级审批流。本平台的完整落地方案见 docs/05 §6.18。

### 4.2 需规避缺陷

- vmdashboard：SQL 字符串拼接（注入）、状态变更走 GET（CSRF）、无 RBAC、websockify 重复拉起。
- KvmDash：RBAC 形同虚设（未做 per-route 角色校验）、`execute` 白名单命令接口意义不明。
- 本平台现状已规避大部分：GORM 参数化、POST 动作、JWT + AdminMiddleware、单进程托管。

### 5.2 被多个项目独立印证的硬差距

同一结论被两个以上**互不相关**的项目指出，才算真差距（不是「人家 UI 好看」）：

| 差距 | 谁在指 | 本平台现状 |
|---|---|---|
| **任务日志是纯文本** | Coolify + Semaphore + XXL-JOB | `tasks.result` 是 2s 节流的纯字符串，前端只能整块显示 |
| **没有失败重试** | XXL-JOB + Harvester | 任务失败即失败，无重投机制 |
| **没有回滚** | Coolify | 栈/应用只有向前升级 |
| **密钥明文可能进日志** | Coolify + Semaphore | 管住了「口令不落库」，但日志脱敏未系统化 |

### 5.3 改造清单（三梯队）

**🥇 第一梯队：真差距 + 可复用现有基建**

1. **任务日志结构化 + WebSocket 增量推送**
   - Coolify：日志是**结构化 JSON 数组**，每条 `{command, output, type: stdout|stderr, timestamp, hidden, order}`，`hidden=true` 的调试行默认折叠；渲染时 command 加粗、stderr 标红。
   - Semaphore：**双通道** —— 写库批量 flush（500 条或 500ms），实时走 WebSocket 推增量；前端首屏拉全量后 WS 追平。
   - 落地：`service/tasks` 的输出升级为结构化条目；实时推送**复用已有的 `service/console/conn.go`**（单写者锁现成）。前端任务详情可做「命令加粗 / stderr 标红 / 时间戳开关 / 自动滚底 / 搜索」。
2. **漂移基线 + 一键收敛**（Containerlab）
   - 做法：**每次 deploy 成功把「当时的目标」写成基线**；下次拿基线与当前配置 diff，得 `none/restart/recreate` + 变更理由。漂移不是「猜」，是「和上次的目标比」。deploy 即 reconcile（增量收敛，非重建）。
   - 落地：`saveSnapshot` 语义明确为「已落地基线」（只在落地成功时覆盖）；漂移判定改三方对比（**JSON 计划=期望 / 基线=上次期望 / DB+libvirt=实际**），能区分「用户改了画布没落地」与「现实被外部改了」——两者处理方式完全不同。
   - **反向修正**：Containerlab 以 YAML 为唯一制品是因为**它没有画布**；本平台的真相是 X6 画布（坐标/边类型/SSH 参数），YAML 有损（现有 `ExportYAML` 只是注释拼接、不可回读）。**结论：不换格式，只引入「基线」这一独立制品。**
3. **失败重试与告警走独立扫描器**（XXL-JOB + Harvester）
   - XXL-JOB：10s 扫描线程统一处理，**CAS 锁防重复告警**，`failRetryCount>0` 即重投。
   - Harvester：`IsRetryAble` / `IsRetryLater` 区分「可重试」与「该延后重试」。
   - 落地：扫描器 + 行级 CAS，**与执行路径解耦**；**只有幂等安全的任务类型进白名单**（镜像下载可以，建 VM 绝对不行）。
4. **Survey Vars：变量定义类型化 + 防注入**（Semaphore）
   - 结构：`{Name, Title, Required, Type: str|int|enum|text|select|secret, Target, Values[], DefaultValue}` + 强校验。
   - 安全：survey 答案写 YAML 时**字符串一律打 `!unsafe`** 防 Jinja 求值；密钥走独立加密通道；**命令行只传 `@file`**，不再明文拼 `--extra-vars`。

**🥈 第二梯队**

5. **回滚**（Coolify）—— 回滚**不是重建**，而是「保留产物 + 复用旧版本重跑」：列出可用镜像 tag，点一下以 `rollback:true` 重新入队。→ 栈升级前把旧 compose 快照进 history 表。
6. **密钥脱敏入日志**（Coolify）—— `logRedactionValues` 把密钥明文从日志替换成 `REDACTED`。
7. **审计前后快照 + diff**（NetBox）—— `ObjectChange` 存 `prechange_data`/`postchange_data` 两个 JSON，`diff()` 只列变化字段。⚠️ NetBox 靠 Django 信号自动快照，本平台是 Gin 中间件**拿不到对象上下文**，必须在 service 层显式快照，勿硬套。
8. **应用商店表单数据驱动**（1Panel）—— 后端 `formFields{type,label,envKey,required,default,rule,values}` → 前端按 type 分派控件。**契约可学，代码 GPL 必须重写。**
9. **IPAM 可用区间动态算**（NetBox）—— 「哪些 IP 空闲」是**区间差集现算**不落记录；已用/空闲交错渲染；「下一个可用 IP」预填建机表单。
10. **容器内文件浏览 + 容器→来源反查**（1Panel）—— 行下拉含 file-browser；「关联」列反查所属应用。

**🥉 第三梯队：手感（低风险）**

| 项 | 来源 | 要点 |
|---|---|---|
| 任务列表列收敛 + 操作按选中数自动启停 | XXL-JOB | 长字段截断 + tooltip；行操作未选中即灰 |
| 侧栏「运行中任务」角标弹层 | Coolify | 聚合双池 running，点击跳详情 |
| compose 编辑器即时校验 | Dockge | CodeMirror6 + 仅聚焦时校验、首个错误延迟 3s 防噪 |
| 栈级锁 | Dockge | 终端名唯一性即天然锁：同栈串行、异栈并行 |
| 请求层统一 loading/错误 + 逃生口 | 1Panel | 类封装 + 全局 loading 码 + `skipErrorMessage` |
| 设置页逐控件即时生效 | 1Panel | 改完即存 + toast + 回读 |
| 栈状态机含「草稿态」 | Dockge | 把「文件在但未部署」单列一态 |

### 5.4 明确不学（过度设计）

判断标准：**它的复杂度是「多节点分布式」的前提产物，还是通用工程经验？** 前者一律不学。

- **Harvester**：CRD + controller 循环 + KubeVirt 最终一致性模型、`spec/status` 分离、PVC/DataVolume/StorageClass 存储栈、NAD/CNI 网络抽象、finalizer/ownerReferences —— 前提是**多节点 + 声明式 API**；本平台单机 libvirt，引入只会多出「改完不立刻生效、要等 reconcile」的心智负担。**其结论：本平台「API 直改 libvirt + 写 DB + 任务队列」在单机规模下更直接，无需转向。**
- **NetBox**：VRF / Aggregate / 物理布线追踪（Front/RearPort）/ 全套自定义字段类型系统；**接口拆分**（IP 挂接口而非主机）对单网卡 VM 也是过度设计，等真要多网卡再拆。
- **Coolify**：Project→Environment→Resource 三级模型（那是「一套代码多环境」）；Horizon 多服务器部署树。
- **1Panel**：core/agent 双进程多节点架构、i18n 全量 `$t()`、多主题、企业版分支。
- **Semaphore**：三层权限（全局 + 项目 + 模板级）。
- **Containerlab**：kinds 注册表、veth/netns 语义。
- **XXL-JOB**：轮询从游标扫到文件尾（大日志拖垮执行器，本平台的节流攒批更稳）、默认 10 行分页、单层子任务。

**一条反向发现**：Dockge **自己不做漂移检测**（状态只来自 `docker compose ls`，改草稿不会把运行中的栈标脏）。也就是说本平台的 `checkDrift` 在这一项上**是领先的**——答案得自研，抄不到。

### 5.5 从 Harvester 额外得到的三条通用工程习惯

1. **Conditions 数组代替单一状态字符串** —— `Condition{Type, Status, Reason, Message, LastTransitionTime}`。本平台 VM 只存 `running/shut off/paused/error`，用户看到「错误」时不知道卡在哪；加 `conditions` 就能回答「**为什么没起来 / 卡在哪一步**」。
2. **错误分类驱动重试** —— 区分「可重试」与「该延后重试」，退避重入（与 §5.3 第 3 条同源）。
3. **类型化错误** —— `AdmitError{code, reason, field, causes}` 带构造器，前端能拿到稳定 code 而非只认中文文案。
