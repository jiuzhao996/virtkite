### 1.3 qcow2 增量镜像与 backing chain

qcow2（QEMU Copy-On-Write v2）除稀疏分配、快照、压缩加密等能力外，还支持**后备文件（backing file）**：
一个 qcow2 镜像可以声明另一个镜像为其基础，自身只保存相对基础镜像的写入差异，读取未修改的数据块时
穿透到后备文件。多层叠加即形成 **backing chain**。这是「增量克隆 / linked clone」的底层机制，也是
PVE 等平台批量派生虚拟机的常规做法。

| 概念 | 说明 |
|---|---|
| 全量克隆（full clone） | 复制整个磁盘数据，两盘完全独立；耗时与磁盘容量成正比，占用翻倍 |
| 增量克隆（linked clone） | 只建一个声明了 backing file 的新 qcow2；建盘瞬时完成，初始占用仅元数据量级 |
| 代价 | 子盘存续期间**父盘不可删除、不可移动、不可改写**；父盘一旦损坏，chain 上全部子盘不可读 |

创建方式与验证命令（本平台把后两条固定为验收标准，见 docs/05 §6.7.1）：

```bash
# 建增量子盘：-b 指定后备文件，-F 显式声明后备文件格式（不声明会有告警且依赖探测）
qemu-img create -f qcow2 -F qcow2 -b /pool/base.qcow2 /pool/child.qcow2

qemu-img info  /pool/child.qcow2   # 输出应含 "backing file: /pool/base.qcow2"
qemu-img check /pool/child.qcow2   # 输出应为 "No errors were found on the image"
```

在 libvirt 侧，等价能力由**存储卷 XML 的 `<backingStore>` 节点**表达，经 `StorageVolCreateXML` 建卷：

```xml
<volume>
  <name>child.qcow2</name>
  <capacity unit="B">与父卷同虚拟容量</capacity>
  <target><format type="qcow2"/></target>
  <backingStore>
    <path>/pool/base.qcow2</path>
    <format type="qcow2"/>
  </backingStore>
</volume>
```

> **易混淆点（本项目曾在此踩坑）**：libvirt 另有一个 `StorageVolCreateXMLFrom` 接口（对应
> `virsh vol-clone`），名字与「克隆」直接相关，容易被当作 linked clone 的实现方式。但它执行的是
> **全量数据拷贝**，产出的子卷**不含** backing file——`qemu-img info` 无 `backing file` 行、
> `virsh vol-dumpxml` 无 `<backingStore>` 节点。二者的区别不体现在调用是否成功、克隆机能否开机上，
> 只体现在产出文件的结构上，因此必须用外部命令核验（详见 docs/05 §6.7.1 与 docs/06 §9.2 F-19）。

| 接口 | 等价命令 | 实际行为 | 子卷有 backing file |
|---|---|---|---|
| `StorageVolCreateXMLFrom(pool, xml, srcVol, 0)` | `virsh vol-clone` | 全量数据拷贝 | ❌ |
| `StorageVolCreateXML(pool, xml, 0)`，xml 含 `<backingStore>` | `qemu-img create -b` | 只写元数据 | ✅ |

备份时同样需要注意 chain：单独拷走子盘是不可用的，需连父盘一起备份，或先
`qemu-img convert -O qcow2 <子盘> <独立盘>` 压平成完整镜像（见 docs/07 §7）。

### 1.4 libvirt 接入方式：go-libvirt 直连 RPC

本平台采用 **digitalocean/go-libvirt（纯 Go）** 直接对接 libvirt RPC 协议，通过本地 unix socket（`/var/run/libvirt/libvirt-sock`）连接 `qemu:///system`。选型对比（论文素材）：

| 对比项 | go-libvirt 直连 RPC（本平台） | virsh / qemu-img 命令封装 | libvirt-go（CGO 绑定） |
|---|---|---|---|
| 实现方式 | 纯 Go 直接调 libvirt RPC（unix socket） | `exec.Command` 调系统命令 | 调用 libvirt C API 的 Go 绑定 |
| 依赖 | 无 CGO、无需 C 头文件 | 无需额外依赖 | 需 libvirt-dev 头文件 + cgo |
| 代码量 | 中等，类型化 API | 小、可读性强 | 多、样板代码多 |
| 技术深度 | 直接体现 libvirt API 调用 | 隔命令行一层 | 最底层 |
| 跨平台分发 | 单二进制，无 cgo | 单二进制 | 需匹配 libvirt 版本 |

> 结论：`virsh` 本质是 libvirt 官方命令行客户端，内部也是调 libvirt API；但为了论文「直接调用 libvirt RPC API」的技术叙事与类型化编程体验，本平台选用 go-libvirt 纯 Go 直连。建盘通过 libvirt **存储池/存储卷 API**（`StorageVolCreateXML`），域管理通过 `DomainDefineXML` / `DomainCreate` 等，不再依赖 qemu-img 与 virsh 命令。

典型调用（`service/virt` 封装层）：
```go
// 连接 libvirt RPC（unix socket）
u, _ := url.Parse(string(libvirt.QEMUSystem))
l, _ := libvirt.ConnectToURI(u)

// 存储池建卷（对应 virsh vol-create-as，qcow2 格式）
pool, _ := l.StoragePoolLookupByName("vmops")
l.StorageVolCreateXML(pool, volXML, 0)

// 域生命周期（对应 virsh define / start / shutdown / undefine）
l.DomainDefineXML(domainXML)
l.DomainCreate(dom)
l.DomainShutdown(dom)
l.DomainGetState(dom, 0)
```

## 4. 数据与安全

- [ ] MySQL 8（存储引擎、字符集 utf8mb4）
- [x] JWT 认证（无状态鉴权、token 过期控制、验签算法锁定为 HS256 以防算法混淆）

- [x] 结构化序列化替代字符串拼接：libvirt 定义以 XML 为输入，改用 `encoding/xml` 结构体 marshal 后元字符自动转义，从生成方式上消除注入面
- [x] WebSocket 并发写约束：gorilla/websocket 允许「一读 + 一写」并发但禁止多协程同时写，需应用侧串行化

### 5.6 虚拟化控制台方案选型（论文素材）

> 需求：管理平台须提供进入 VM 系统的通道，覆盖两类场景——① 文本/服务器版（CLI）；② 图形化桌面（GUI）。三条主流路线对比如下。

| 方案 | 原理 | 传输粒度 | 浏览器体验 | 文本(CLI)场景 | 图形桌面场景 | 来宾/部署依赖 | 成熟度 |
|---|---|---|---|---|---|---|---|
| **VNC + noVNC**（本平台已实现） | RFB 帧缓冲协议，QEMU 直接暴露 VNC，noVNC/websockify 将协议封装为 WebSocket | **像素/整屏位图差异** | 通用、兼容好 | 可用但浪费带宽、延迟受网络敏感 | 可用，弱网下卡顿/模糊 | 无（QEMU 内置 VNC） | 极高 |
| **SPICE + spice-html5**（KvmDash 采用） | QEMU SPICE 通道，2D 指令级编码 | 绘图指令 | 实现成熟度一般、坑多 | 同样偏重 | **图形质量更优**（虚拟桌面协议，编码优于 VNC） | QEMU SPICE + HTML5 客户端 | 中 |
| **Web SSH 终端**（xterm.js+WebSocket→SSH，堡垒机形态） | SSH 字符流，前端 xterm.js 渲染 | **字符级** | 极佳：延迟≈0、字体/配色/复制粘贴/系统信息栏均可控 | **最优解** | 不适用（无桌面） | VM 需 sshd + 可路由 IP + 平台保管凭据 | 高（JumpServer/Cockpit 均此思路） |

> **结论与分工（本平台的设计取向）**
> - noVNC 之所以被选为第一落地点：QEMU 内置 VNC **零来宾依赖**、noVNC 是**成熟成品即插即用**（调用即可），一次打通图形+文本双场景，是最低成本的兜底方案。其短板是 RFB 像素流本质——文本服务器也在传整屏位图，浏览器上做纯键盘操作体验一般；**图形桌面弱网时卡顿感明显**。
> - **免 IP 的带外终端**：对服务器版/CLI，平台 console（VNC）本身即是免 IP 终端——VM 一启动即可进入，**无需 guest 配置 IP/sshd/网络栈**，可看引导日志、修网络、进 GRUB/单用户，等价 VMware/VirtualBox 的「控制台」（OOB）。因此**「进入命令行操作」这一需求已由 console 覆盖**。
> - **落地形态**：控制台入口做成站内「选择页」，三种连接并行——**图形控制台（noVNC）**直接内嵌；**Web 终端（SSH）**用 xterm.js + Go `x/crypto/ssh` 做 WebSocket↔SSH 桥（参考 JumpServer 形态）；**串口 Console** 走 libvirt `DomainOpenConsoleBidirectional`（免 IP，等价 `virsh console`）。SSH 连接参数由用户在页面手动填写（host 默认取 `vms.ip`），暂不做凭据库与 IP 自动发现（`vms.ip` 可为空），属轻量落地；凭据持久化/堡垒化留作后续增强。
> - **拨号参数来自浏览器带来的安全约束**：SSH 桥的 host/port 完全由客户端提交，若不校验，平台即可被当作跳板机与内网扫描器。因此服务端对目标做白名单收敛——已记录 IP 的虚拟机必须精确匹配，未记录 IP 时只接受 RFC1918 私有网段的 IP 字面量（排除环回、链路本地、组播，且不接受主机名以防 DNS 解析到公网与 DNS rebinding）。这也是「不做凭据库」这一轻量取向的必要配套（见 docs/05 §6.3）。
> - **按角色分工**：SSH 终端与串口是对客户机的双向写入通道（串口在多数云镜像上直接是 root TTY），故仅管理员可用；只读角色只保留图形控制台，并由后端下发 `view_only` 标记、前端以 noVNC 只读模式加载（RFB 协议本身无只读模式，键鼠必须在客户端禁用）。

> - 更优路线仍是**按场景分工**而非单画布硬塞：CLI 终端 → console 免 IP 直连已够；图形桌面 → console（VNC）兜底；对图形质量要求极高的场景再考虑 **SPICE**（备选，不优先，因其 HTML5 客户端成熟度与部署成本不占优）。
> - 调研呼应：vmdashboard 用 noVNC token 链路（本平台已落地，见 docs/10 §1）；KvmDash 走 SPICE + spice-html5（见 docs/10 §2）；Cockpit 底层是 libvirt-dbus 无自带 Web 终端，靠 guest 内 sshd 由 Cockpit Shell 提供（与上表结论同源）。
