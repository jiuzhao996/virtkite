### 1.3 libvirt 接入方式：go-libvirt 直连 RPC

本平台采用 **digitalocean/go-libvirt（纯 Go）** 直接对接 libvirt RPC 协议，通过本地 unix socket（`/var/run/libvirt/libvirt-sock`）连接 `qemu:///system`。选型对比（论文素材）：

| 对比项 | go-libvirt 直连 RPC（本平台） | virsh / qemu-img 命令封装 | libvirt-go（CGO 绑定） |
|---|---|---|---|
| 实现方式 | 纯 Go 直接调 libvirt RPC（unix socket） | `exec.Command` 调系统命令 | 调用 libvirt C API 的 Go 绑定 |
| 依赖 | 无 CGO、无需 C 头文件 | 无需额外依赖 | 需 libvirt-dev 头文件 + cgo |
| 代码量 | 中等，类型化 API | 小、可读性强 | 多、样板代码多 |
| 技术深度 | 直接体现 libvirt API 调用 | 隔命令行一层 | 最底层 |
| 跨平台分发 | 单二进制，无 cgo | 单二进制 | 需匹配 libvirt 版本 |

> 结论：`virsh` 本质是 libvirt 官方命令行客户端，内部也是调 libvirt API；但为了论文「直接调用 libvirt RPC API」的技术叙事与类型化编程体验，本平台选用 go-libvirt 纯 Go 直连。建盘通过 libvirt **存储池/存储卷 API**（`StorageVolCreateXML`），域管理通过 `DomainDefineXML` / `DomainCreate` 等，不再依赖 qemu-img 与 virsh 命令。

典型调用（`service/virt` 封装层）：
```go
// 连接 libvirt RPC（unix socket）
u, _ := url.Parse(string(libvirt.QEMUSystem))
l, _ := libvirt.ConnectToURI(u)

// 存储池建卷（对应 virsh vol-create-as，qcow2 格式）
pool, _ := l.StoragePoolLookupByName("vmops")
l.StorageVolCreateXML(pool, volXML, 0)

// 域生命周期（对应 virsh define / start / shutdown / undefine）
l.DomainDefineXML(domainXML)
l.DomainCreate(dom)
l.DomainShutdown(dom)
l.DomainGetState(dom, 0)
```

## 5. 技术选型对比（论文素材）

### 5.1 后端：Go vs Python vs Java

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| Go | 单二进制、低内存、并发 | 生态较新 | ✅ 选用 |
| Python | 开发快 | 依赖重、部署繁 | 曾用于原型 |
| Java | 生态成熟 | 内存占用高 | 不选 |

### 5.2 虚拟化：KVM vs VMware vs VirtualBox

### 5.3 管理方案：virt-manager vs OpenStack vs Proxmox vs 本平台

| 方案 | 形态 | 内存/复杂度 | 功能侧重 | 与本文关系 |
|---|---|---|---|---|
| virt-manager（虚拟系统管理器） | 桌面 GUI 客户端（Python + GTK） | 极轻 | 单机 KVM：创建 VM、存储池、直接编辑 XML | 同为 libvirt 管理端，教学常用 |
| OpenStack | 巨型框架（nova/neutron/cinder 等数十组件） | 极重、吃内存 | 大规模公有/私有云 | 轻量化对比对象 |
| Proxmox VE | 独立操作系统 + Web 界面 | 中等 | 中小集群虚拟化 | 功能对比对象 |
| **本平台 vmops** | Web 平台 + virsh 封装（单二进制） | 轻量 | 轻量私有云管理 + 审计 | 本文 |

> 定位：本平台介于 virt-manager 与 Proxmox 之间 —— Web 化、可多宿主机纳管，但资源占用低、部署为单二进制，适配受限硬件场景。
